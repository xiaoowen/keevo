# Keevo 修订模型规范

- **版本**：0.3（草案）
- **状态**：已按 2026-11-18 两轮模型评审修订（[第一轮处理记录](../docs/reviews/2026-11-18-model-review-response.md)、[第二轮处理记录](../docs/reviews/2026-11-18-model-review-round2-response.md)）。M1 的本地数据模型直接基于本规范；M2 的同步复用同一套合并规则。
- **相关文档**：
  - 加密格式：[crypto.md](crypto.md)
  - 同步文件格式与流程：[../docs/sync.md](../docs/sync.md)

## 1. 目标

1. **不丢数据**：并发的修改不会被静默丢弃——未处理的冲突版本一直保留，直到用户处理（§4.3、§5.4）。顺序覆盖的旧值在历史保留期内可以恢复（§7）。
2. **确定性**：只要拥有相同的头修订和修订图，所有设备都必须算出完全相同的合并结果，与合并顺序、分组方式、到达顺序、本地清理进度无关。
3. **因果优先**：在因果上更晚的修改总是胜出，不受设备时钟误差影响。只有真正并发的修改才按时间戳决定胜负。
4. **离线可用**：合并只需要本地数据，不需要任何协调方。

## 2. 术语

| 术语 | 定义 |
|---|---|
| 对象（object） | 条目或保险库，由 `object_id` 标识 |
| 修订（revision） | 对象在某一时刻的完整状态，写入后不可变，由 `rev_id`（16 字节随机）标识 |
| 父修订（parents） | 生成该修订时，对象的全部头修订 |
| 修订图 | 由修订与父修订关系构成的有向无环图（DAG） |
| 祖先 | 沿父修订关系可以到达的修订。本文中"r 是 s 的祖先"包括 r = s |
| 头（heads） | 对象中不是任何其他修订祖先的修订。没有并发修改时只有一个 |
| 设备 ID（`device_id`） | 16 字节随机，每台设备每个账户生成一次 |
| 记录（record） | 对象内部的最小合并单元，见 §4 |

## 3. 混合逻辑时钟（HLC）

- **格式**：HLC 是一个 64 位无符号整数。
  - 高 48 位：Unix 毫秒时间戳。
  - 低 16 位：逻辑计数器。
  - 按整数大小比较先后。
- **生成**：本地每次需要新时间戳时：
  ```
  hlc = max(now_ms << 16, last + 1)
  last = hlc
  ```
- **接收**（M2）：读到其他设备的修订时，若远端 HLC 的物理时间不超过本机时钟 + 24 小时，`last = max(last, 远端 hlc)`；超过时不推进本机时钟，否则一个极端值会让本机此后的时间戳全部饱和。
- **时钟异常提示**：远端 HLC 的物理时间比本机时钟快 5 分钟以上时，提示用户"某台设备的时钟可能不准"。远端值本身照常参与合并，不做任何截断，因为截断会破坏合并的确定性。
- **耗尽**：`last` 已是最大值、无法再递增时返回 `clock_exhausted`，拒绝写入，不得重复发出同一个时间戳。
- **持久化**：`last` 必须持久化。重启后从 `max(持久化的值, 本地所有修订中物理时间不超过本机时钟 + 24 小时的最大 hlc)` 恢复。

## 4. 对象状态：记录映射

每个修订的明文包含一个**记录映射** `RecordKey → RecordVersion`（每个键的当前版本），以及一个**并发版本映射** `RecordKey → [RecordVersion]`（§4.3）。

### 4.1 记录键

| `RecordKey` | 含义 | 值 |
|---|---|---|
| `attr:<name>` | 单值属性：`title`、`favorite`、`archived`、`trashed`、`icon` 等 | 属性值 |
| `tag:<name>` | 一个标签 | 无值（存在即带有该标签） |
| `section:<section_id>` | 分区 | 标签名、排序键 |
| `field:<field_id>` | 字段，包括网址、TOTP、自定义字段 | 类型、标签名、值、用途、所属分区、排序键 |

- 字段与分区的 ID 都是 16 字节随机数，在创建时生成，此后保持不变。
- **排序键**用分数索引字符串（fractional indexing），这样并发的重排也能确定性地合并。排序键相同时，按 ID 字节序排列。
- **概要**（overview：标题、副标题、网址、标签）不单独合并，每次写入修订时由记录映射重新计算。

### 4.2 记录版本

```
RecordVersion {
  value      // 记录的值；tombstone 时为空
  deleted    // 是否为墓碑：删除记录也是一个版本，必须保留
  hlc        // 写入该版本时的 HLC
  rev        // 写入该版本的修订 rev_id
}
```

**写入规则**：
- 创建新修订时，未修改的记录及其并发版本原样复制，`hlc` 与 `rev` 保持不变。
- 修改或删除的记录：写入新的 `hlc`，`rev` 设为新修订的 `rev_id`，并清除该键的全部并发版本——新版本写于全部头之后，因果上覆盖了它们。
- **删除记录必须写成墓碑**（`deleted = true`），不能直接移除。否则其他设备无法区分"被删除"和"从未存在"。

### 4.3 并发版本

- **含义**：某个键上与当前版本互不覆盖、但没有被选为当前值的版本。它们由合并（§5.1）产生，写入修订时随记录映射一起保存。
- **不变量**：
  - 每个列表非空，按 `rev` 字节序严格升序；
  - 不含与该键当前版本相同 `rev` 的版本；
  - 值的类型与键匹配。
- **只有并发版本、没有当前版本的键**：只允许删除状态键 `attr:trashed` 与 `attr:purged`（§5.2），读取时视为不存在。其他键出现这种情况时返回 `malformed`。
- **为什么需要**：合并的结果是全部候选的极大元集合。如果合并修订只保存胜者，落选的版本——尤其是携带"已覆盖某个旧值"这一因果信息的墓碑——就会丢失，之后再与其他头合并时，结果取决于先合并了哪几个头（评审 2026-11-18 F4）。

## 5. 合并

当对象有多个头时，按下面的算法计算**合并视图**。

### 5.1 选择每个记录的胜出版本

对每个在任一头的记录映射或并发版本映射中出现过的 `RecordKey`：

0. **核对出处**：每个版本声称的写入修订 `rev` 必须是它所在头的祖先（含自身）。不满足的版本丢弃，该键记为**完整性问题**。
1. **收集候选**：取各头中该键的当前版本与全部并发版本，按 `rev` 去重。
   - 同一 `rev` 出现内容不同（`hlc` 或值不同）的版本时，保留 `(hlc, 值的规范编码)` 最大者，并把该键记为完整性问题。规范编码见 `vault-format.md` §1；这样结果仍与输入顺序无关，而不是"首次为准"。
   - 正常写入（§4.2）不会产生这两类问题。它们只可能来自损坏的数据或恶意的已登记设备，界面应提示用户查看该条目的历史。
2. **去掉被因果覆盖的版本**：如果候选 v 的 `v.rev` 是另一个候选 w 的 `w.rev` 的真祖先，说明 w 是在看到 v 之后写入的，去掉 v。剩下的称为**极大元**，两两并发。
3. **选出当前版本**：
   - 极大元中既有墓碑又有非墓碑时，只在非墓碑中选（"宁可多保留"）。
   - 取 `(hlc, origin_device(rev), rev)` 最大者，后两项按字节序比较。克隆设备或 HLC 饱和时前两项可能相同，`rev` 保证这是全序。
4. **输出**：当前版本写入记录映射；其余极大元（包括被丢弃的墓碑）按 `rev` 升序写入并发版本映射。

修订图本身也要核对：
- 父修订列表按集合处理（按字节序排序、去重），最多 256 个；
- 同一 `rev_id` 出现不同的父修订或来源设备时，拒绝该修订（`revision_conflict`），不做"首次为准"的处理；
- 父修订必须先于子修订加入（`missing_parent`），因此修订图中不会出现环。

### 5.2 删除与修改并发：撤销删除

有两个**删除状态键**，都按普通记录参与 §5.1 的"取极大元"：
- `attr:trashed`：回收站状态，由移入回收站的修订写入。
- `attr:purged`：永久删除。墓碑修订（§6）没有内容，合并时**视为在 `attr:purged` 上写了一个版本**：`hlc = 0`，`rev` 为该墓碑修订，值为 `true`。这样对象是否已删除也进入合并状态，分组合并时不会丢失（第二轮评审 G2）。

在 §5.1 得出各键的当前版本之后，依次执行：

1. **回收站**：若 `attr:trashed` 的当前版本不是墓碑，设 D 为它的 `rev`。只要有任何一个非删除状态键的当前版本不是墓碑、且其 `rev` 与 D 并发（既不是 D 的祖先，也不是 D 的后代），就说明有修改与移入回收站并发：撤销，把 `attr:trashed` 的当前版本移入并发版本映射。
2. **永久删除**：取 `attr:purged` 全部未被覆盖、不是墓碑的版本（当前版本与并发版本）。
   - 只要其中**有一个**版本 D，没有任何非删除状态键的当前版本与之并发，删除成立，合并结果为"已删除"；
   - 否则撤销删除，把 `attr:purged` 的当前版本移入并发版本映射。

被撤销的删除版本**移入并发版本映射，而不是丢弃**。它们不再是当前值，但仍是之后合并的候选：如果丢弃，分组合并时更早的删除版本会失去"已被覆盖"的信息而重新生效。

撤销删除时合并结果标记 `resurrected`，界面在冲突面板中提示："这个条目在另一台设备上被删除，但这里有新的修改，已为你保留"。

### 5.3 性质

- **确定性**：结果只依赖头集合、各头的记录映射与并发版本映射、修订图，与输入顺序无关。
- **交换律、结合律与幂等性**：对**纯合并**成立，包括对象是否存在。
  - 纯合并：把一组头的合并视图原样写成修订，不附带任何编辑。
  - 合并状态是各头版本并集的极大元（删除状态也在其中，§5.2），"取并集、再取极大元"满足结合律：先纯合并一部分头，再与其余头合并，结果与一次合并全部头相同。前提是同一 `rev` 对应同一内容；不满足时见 §5.1 步骤 1。
  - 实现可以缓存或写回合并视图，但必须连同并发版本一起保存，**不得只保存胜者**。
  - `resurrected` 是对本次合并的提示，不属于合并状态：对象墓碑头并入合并修订后，提示就不再出现。
- **写时收敛不是纯合并**：实际写入的修订还包含用户的操作——编辑、冲突处理，以及确定"撤销删除"（§5.4）。这些操作改变了输入，结果自然可以不同于把原来的头一次合并；性质只对纯合并成立。
- **不需要历史内容**：合并只读取头修订的内容，以及修订图中的祖先关系。因此本地清理旧修订的内容（§7）不会影响合并结果。

### 5.4 读时合并，写时收敛

- **合并结果不自动写回**：多个头会一直保留，直到用户编辑该对象。这样避免多台设备各自写入合并修订，互相触发而来回震荡。
- **编辑时收敛**：
  - 用户编辑时，新修订的 `parents` 设为全部头，以合并视图（含并发版本）为基础。
  - 写入前，只有并发版本、没有当前版本的删除状态键（撤销删除后的 `attr:trashed`、`attr:purged`）写入墓碑，把"已撤销删除"确定下来。否则引发撤销的那次并发修改日后被覆盖时，旧的删除会重新生效。
  - 这是一个**用户操作**：界面必须在冲突面板中说明"保存即确认恢复这个条目"，而不是只保存用户正在改的字段。
  - 写入后只剩一个头，但**冲突不会因此自动解除**：并发版本随修订保留，直到
    - 用户编辑该键：新版本覆盖全部并发版本；或
    - 用户在冲突面板中选择保留某个版本：把该版本的值作为新版本写入。
  - 合并结果为"已删除"的对象不可编辑，不写回。
- **界面要求**：存在冲突时，客户端必须在编辑界面展示冲突面板。

### 5.5 冲突与并发版本

存在并发版本不等于需要用户处理：

- **冲突**：某个键的并发版本中，至少有一个的值与当前值不同。界面提示用户处理。
- **值相同的并发版本**（例如两台设备把同一字段改成了同一个值）：不提示，但仍要保存，因为它们携带后续合并需要的因果信息。

条目概要中的 `conflicts` 标记由此计算（`vault-format.md` §3），列表只解密概要即可标出冲突。被撤销的删除不算字段冲突，由 `resurrected` 表示。

### 5.6 完整性问题的含义

§5.1 步骤 0–1 报告的完整性问题只表示**本次合并的候选中观察到的矛盾**：
- 它不持久化。写入修订后，矛盾的另一份内容不再是候选，提示随之消失；
- 提示消失**不代表**历史已被认证。仅凭祖先关系也无法发现"复制时篡改了祖先修订的原值"；
- 因此界面必须在保存前展示完整性问题，保存即视为用户已知晓；
- 持久、可验证的出处由 M2 的签名设备日志负责（`docs/sync.md` §4–§5）。

## 6. 删除对象

1. **移入回收站**：写一个新修订，把 `attr:trashed` 设为删除时间。
2. **永久删除**：在回收站中保留 30 天后，或用户手动清空时，写一个**墓碑修订**：
   - `deleted = true`，不含记录映射，也就不含任何秘密；
   - 父修订为全部头。
   - 合并时它等同于在 `attr:purged` 上的一个版本（§5.2）。
3. **删除成立后残留的内容**（M2）：如果删除成立，但仍有其他头携带内容（例如同步带来了与删除同时的旧分支），这些头修订不会被清理（§7）。客户端此时写一个新的墓碑修订，父修订为全部头，使内容修订成为可清理的历史。这是一次新的删除操作，而不是纯合并；之后才到达的并发修改照常撤销它。
4. **墓碑的清理**：墓碑修订本身只有在所有未撤销设备都已体现它之后，才能被清理（M2，见 `docs/sync.md`）。

## 7. 大小、历史与清理

### 7.1 大小预算

- **单个记录值**：编码后不超过 256 KiB，更大的内容用附件。
- **父修订**：每个修订最多 256 个。
- **条目详情**：必须放进一个信封，即编码后不超过 16 MiB（`crypto.md` §8）。
- **合并后超出**：保留全部并发版本之后，合并状态可能超过 16 MiB，尽管每个头各自都没有超过（第二轮评审 G5）。此时：
  - 读取、查看历史、导出全部版本照常；
  - 普通保存返回 `item_too_large`，不写入任何东西；
  - 客户端提供**精简**：在一次写入中处理冲突（保留选中的版本），并删除用户选中的字段，使结果放得进一个信封；
  - **绝不静默丢弃**任何并发版本来满足大小限制。
- **头的数量**：没有硬上限，因为丢弃头就会丢数据。一个对象的头超过 64 个时，界面提示"该条目的并发修订异常多"。

### 7.2 历史保留

- **默认保留**：每个对象保留最近 20 个修订，以及按本机**有效时间**计 90 天内写入或收到的全部修订，取两者的并集。两个数值都可配置。
- **有效时间**（第二轮评审 G3）：
  - 由本机保存，每次写入或清理时推进：前进量等于墙上时间的增量，但单次最多 1 天；墙上时间倒退时不变。
  - 因此时钟被调快、长期不使用、时钟倒退后再校正，都只会让保留期变长，不会提前清理。
  - 代价是长期不用后，保留会比日历上的 90 天更久。
  - 修订作者的时钟不影响保留。
- **迁移**：旧版本数据库中年龄未知的修订，按迁移时的有效时间计。
- **清理**：其余修订只清除内容，保留 `rev_id`、`parents`、`origin_device`。合并只用到这些元数据和头修订的内容。
- **永不清理**：
  - 头修订。未处理的并发版本保存在头修订中，因此不受清理影响。
  - 修订图本身。祖先判断依赖它；每个修订只需几十字节。
- **承诺范围**：顺序覆盖的旧值在保留期内可以恢复；超出保留期后只保留元数据。"90 天"指本机有效时间，不是严格的日历时间。产品文案不得承诺"永久保留全部历史"。
- **"恢复到此版本"**：把历史修订的记录值作为一次新的编辑写入，即产生一个新修订，而不是回退修订图。

## 8. 设备 ID

- 每台设备在创建或加入账户时生成 `device_id`，并保存一个由 Secure Enclave 密钥包裹的本机标记（Keevo 不使用钥匙串，ADR-0003）。
- 如果启动时标记不存在或解不开，必须生成新的 `device_id`。解不开通常说明数据库被恢复到了另一台 Mac（那台 Mac 的 Secure Enclave 用不了这把密钥），也可能是标记被删除或损坏。这一机制不能发现同一台 Mac 上的数据库副本。之后的修订使用新 ID；已有修订保持不变。

## 9. 一致性测试要求

实现必须通过以下测试：

| 测试 | 内容 |
|---|---|
| 交换律 | 对随机生成的修订图与并发编辑，任意排列、重复输入，结果都相同 |
| 结合律 | 随机挑选一组头纯合并并写成修订，再与其余头合并，反复直到只剩一个头；每一步的合并状态都与一次合并全部头相同。另有对象墓碑与回收站的确定性反例 |
| 幂等 | 合并结果再与任一输入合并，结果不变 |
| 因果优先 | 因果上更晚的修改即使 HLC 更小（模拟时钟回拨），仍然胜出 |
| 不丢数据 | 未处理的并发版本在任意次无关编辑与清理之后仍能取得；顺序覆盖的旧值在保留期内能在某个保留的修订中找到 |
| 清理无关性 | 清理任意非头修订的内容后，合并结果不变 |
| 删除与修改并发 | 符合 §5.2；撤销删除并编辑后，删除不会因引发撤销的修改日后被覆盖而重新生效 |
| 出处校验 | 声称写于非祖先修订的版本、同一 `rev` 内容不同的版本：结果与输入顺序无关，并报告完整性问题 |
| 修订图 | 未知父修订、以自身为父、元数据不一致的重复修订都被拒绝；父修订顺序不同视为相同 |
| 历史保留 | 墙上时钟前跳、倒退再校正、从旧 schema 迁移之后，保留期内的修订都不被清理 |
| 大小 | 合并后超过信封上限的条目可读取、普通保存失败且不写入、精简后可保存 |

后续会在 `spec/test-vectors/revisions-v1.json` 中提供合并测试向量。
