# Keevo 规范评审说明

感谢你愿意评审 Keevo 的规范。这份说明告诉你：要评审什么、按什么顺序读、我们最担心哪些地方、哪些问题已经知道不必再报，以及怎样反馈。

- **评审对象**：`spec/` 下的 4 份 1.0 规范（2026-11-18 冻结），以及实现它们的 Rust 代码。冻结之后的评审重点是：实现是否符合已冻结的规范，以及冻结范围之外的新格式（见 [README.md](README.md)）
- **已完成的评审**：2026-11-18 的四轮模型评审，报告与处理记录都在 [docs/reviews/](../docs/reviews/)。其中的发现都已处理；欢迎你检验这些修复是否正确，但不必重复报告原问题
- **预计时间**：核心部分（§3 的必读项）约 1 天；全部约 2–3 天
- **请在反馈中注明你评审时的提交哈希**（`git rev-parse HEAD`）

## 1. Keevo 是什么

Keevo 是开源、本地优先的个人密码与开发者凭证保险库。首发 macOS 与 Chrome 扩展。

**核心安全目标**：
- 主密码加 128 位账户密钥，共同派生解锁密钥（2SKD）。
- 全部数据（包括元数据）端到端加密。
- 同步通过 iCloud 云盘或任意同步文件夹进行，**存储提供方以及任何能写入同步文件夹的人都被视为不可信**。

完整的威胁模型见 [docs/security.md](../docs/security.md) §1–§3。评审时最好以那里的"攻击者模型"为准：

| 在范围内 | 不在范围内（非目标） |
|---|---|
| 密文窃取者 | 已取得 root、或能注入 Keevo 进程的恶意软件 |
| 不可信的存储提供方 | 硬件键盘记录器 |
| 恶意网站 | 已解锁设备上的胁迫 |
| 其他浏览器扩展 | — |
| 本机同一用户的恶意进程（尽量提高门槛） | — |

## 4. 我们最希望你回答的问题

每条都标了出处。你只需回答"成立 / 不成立 / 有条件成立"并说明理由；当然也欢迎指出我们没想到的问题。

### 4.1 crypto.md

**C1. 2SKD 的组合方式（§6）**

```
K_p  = Argon2id(NFKD(password), salt_p, m, t, p, 32)
K_s  = HKDF-SHA-256(IKM = SK, salt = account_id, info = "keevo/v1/secret-key", L = 32)
AUK  = HKDF-SHA-256(IKM = K_p ‖ K_s, salt = account_id, info = "keevo/v1/auk", L = 32)
```

- 用 HKDF 处理拼接，而不是像 1Password 那样做异或，是否有问题？
- `account_id` 是公开的随机值，用作 HKDF 的 salt 是否合适？
- 即使主密码很弱，2SKD 能否把离线破解难度维持在至少 2¹²⁸？这依赖于账户密钥由 CSPRNG 生成、且不与密文存放在一起。

**C2. KDF 参数的上下限与防降级（§5、§7.2）**

- **参数值**：默认 m = 256 MiB、t = 3、p = 4；硬性下限 64 MiB / 3 / 1；上限 4 GiB / 32 / 16。
- **防降级机制**：参数以明文存放，再通过密钥集 AAD 中的 `binding = SHA-256(label ‖ epoch ‖ kdf_params)` 绑定。
- **请判断**：能写入同步文件夹的攻击者，替换参数或整个账户文件时，除了让解锁失败（拒绝服务）之外，还能否得到任何东西？例如口令猜测的预言机、更弱的派生结果。
- **实现上的已知限制**：参考实现中 Argon2 的多个 lane 是串行计算的（未启用并行特性），所以解锁耗时随 p 线性增长。这影响按设备校准，但不影响安全性。

**C3. `kid(AUK)` 写在信封头部（§6）**

```
kid(AUK) = HKDF(AUK, salt = account_id, info = "keevo/v1/auk-kid", L = 16)
```

- **用途**：在解密前识别"密码错误"。
- **我们的论证**：攻击者本来就能用 AEAD 校验来验证口令猜测，而每次猜测的成本始终由 Argon2id 主导，所以它不额外降低安全性。
- **请确认**：这个论证是否成立，以及 16 字节是否引入任何多目标攻击的便利。

**C4. 加密信封与 AAD（§8）**

- **结构**：XChaCha20-Poly1305，nonce 为 192 位随机数。AAD 是定长 132 字节，包含：
  - `version`、`alg`、`kid`（与头部重复，使头部也被认证）；
  - `object_type`、`part`、`part_index`；
  - `account_id`、`vault_id`、`object_id`、`rev_id`；
  - 32 字节的类型专属 `binding`。
- **请寻找**：存储提供方能否在**不持有密钥**的情况下完成任何"移植"或"替换"攻击。例如：
  - 同一条目不同修订之间互换概要与详情；
  - 把保险库密钥的包裹信封挪给另一个保险库；
  - 把旧修订的密文冒充成新修订。
- **AAD 字段是否完整**：还有没有应该纳入 AAD 的上下文？

**C5. 长度填充（§8.3）**

- **规则**：明文先加 4 字节长度前缀，再按 max(256, Padmé(n)) 补零；解填充严格校验。
- **请判断**：泄露程度对密码管理器是否可接受，例如能否推断密码长度或备注长短。最小桶 256 字节是否合适？

**C6. 每个修订重新包裹同一把条目密钥（vault-format.md §4）**

- **做法**：条目密钥 IK 在条目创建时生成，之后每个修订都用新的 `rev_id` 上下文、新的随机 nonce 重新包裹同一把 IK，概要与详情也都用这把 IK 加密。
- **请判断**：同一把密钥在条目的整个生命周期内加密大量消息，是否有问题？例如随机 nonce 的碰撞界限，以及条目被频繁编辑的情况。

**C7. 账户密钥的编码（§4）**

- **编码**：128 位随机数，经 Crockford Base32 编码，加上 GF(32) 上的 RS(28,26) 校验符号。
- **校验的作用**：只用于检出输入错误，不提供任何安全性。
- **请确认**：编码与解析（含 NFKC 规范化、O/I/L 容错）不会损失熵，也不会让两个不同的密钥解析为同一个值。

**C8. 域分隔**

所有 HKDF `info` 与哈希标签都以 `keevo/v1/` 开头，请确认它们两两不同、不存在可被混用的上下文。

### 4.2 ipc.md

**I1. 配对的短认证串（§4.2）**

- **生成**：`SAS = HKDF(handshake_hash, info = "keevo/v1/ipc-sas", L = 6)`，即 48 位，计划映射为 6 个单词（M0 原型显示为 12 位十六进制）。用户需在两端比对一致后确认。
- **请判断**：对需要实时介入的中间人（每次配对只有一次机会），48 位是否足够？取 handshake hash 是否正确？

**I2. Noise 的用法（§4.1、§4.3）**

- **基本用法**：配对用 `Noise_XX_25519_ChaChaPoly_SHA256`，已配对后的会话用 `Noise_IK_…`。
- **prologue**：`"keevo/v1/ipc" ‖ 0 ‖ 用途 ‖ 0 ‖ 扩展来源`，用来防止一个扩展的配对被另一个扩展使用。
- **请判断**：
  - IK 第一条消息被重放会有什么后果？我们的负载为空，重放只会让服务端开始一次新握手。
  - IK 的身份隐藏性质在本场景中是否重要？
  - 扩展的静态私钥存于 `chrome.storage.local`（磁盘上不加密），这是否可接受？我们的论证是：攻击者还必须同时通过 §3 的操作系统层校验。

**I3. 最小披露与"被攻破的扩展"（§5.2）**

- **服务端规则**：只返回与 URL 匹配的条目概要；`fill` 时再次校验 URL 与条目是否匹配。
- **局限**：URL 由扩展提供。如果扩展本身被攻破，它可以谎报 URL，从而取走任意站点的密码。
- **请判断**：这个残余风险是否可以接受？在我们的威胁模型里，被攻破的扩展本就能读取页面上已填写的值。另外，填充前要求 Touch ID（规范中的可选设置）是否应改为默认开启？

**I4. 操作系统层的对端校验（§3）**

- **服务端校验 socket 对端**：通过 `LOCAL_PEERTOKEN` 取得 audit token，再按代码签名要求判定。
- **native host 校验父进程**：取父进程的 pid，再按代码签名判定是否为已知浏览器（Google Chrome，Team ID `EQHXZ8M8AV`）。
- **请判断**：基于 pid 的父进程校验是否存在可利用的竞态，例如父进程退出后 pid 被复用？

### 4.3 revisions.md（推荐）

**R1. 合并的确定性与"不丢数据"（§5）**

- **规则**：
  - 因果上更晚的版本胜出；并发版本按 `(hlc, origin_device)` 取最大；并发时非墓碑优先于墓碑；
  - 删除与修改并发时撤销删除，"并发"指既非祖先也非后代（§5.2）。
- **请判断**：能否构造出违反交换律、结合律、幂等性，或导致某个值不再存在于任何保留修订中的反例？参考实现带有 300 组多设备随机模拟测试。

**R2. 已登记设备的恶意行为**

- 记录版本里的 `rev` 与 `hlc` 由写入设备自报。一台已登记、持有密钥的设备，可以把 `hlc` 设得极大，从而赢得所有**并发**冲突；但赢不了因果上更晚的修改。
- 它还能否通过伪造 `rev`（声称在某个修订中写入）影响因果判断？
- 我们目前的立场是：同一账户的设备彼此信任，撤销设备才是对策。请判断这个立场是否合理。

### 4.4 网址匹配（推荐）

`url_match.rs` 中的规则：
- 主机相同，或页面主机是保存主机的子域（以 `.` 为界）；
- HTTPS 条目不填充到 HTTP 页面；
- IP 地址与 `localhost` 要求端口完全一致；
- 带用户名或密码的网址一律拒绝；
- 主机名由 WHATWG URL 解析器规范化。

**请寻找**能让保存为 `https://github.com` 的条目被填到非 `github.com` 页面的输入。测试中已覆盖：`@` 用户信息、同形字、`github.com.evil.example`、`javascript:`、`data:` 等。

## 6. 如何复现

```bash
git clone https://github.com/xiaoowen/keevo && cd keevo
cargo test --workspace                       # Rust 工具链按 rust-toolchain.toml 自动安装（1.97.1）

# 测试向量由独立的 Python 实现生成（argon2-cffi + libsodium），可单独复核
python3 -m venv .venv
.venv/bin/pip install --require-hashes --no-deps -r spec/reference/requirements.txt
.venv/bin/python -I spec/reference/generate_vectors.py --check

# 模糊测试（需要 nightly 与 cargo-fuzz）
cd fuzz && cargo +nightly fuzz run envelope_open -- -max_total_time=60
```

## 7. 反馈方式

- **可能构成漏洞的问题**：请走 [SECURITY.md](../SECURITY.md) 的私密渠道（GitHub 私密漏洞报告），不要公开。
- **其他意见**：可以提 issue，也可以直接回一份文档。

**每条发现请包含**：
1. **位置**：文件与章节，或代码路径与行号。
2. **问题**：发生了什么、在什么前提下发生。
3. **影响**：攻击者能得到什么。
4. **严重程度**：严重 / 高 / 中 / 低 / 建议。
5. **建议**（如有）。

**严重程度参考**：

| 级别 | 含义 |
|---|---|
| 严重 | 无需用户凭据即可解密保险库内容，或静默篡改数据 |
| 高 | 在威胁模型范围内泄露秘密，或绕过来源绑定 |
| 中 | 需要较强前提的攻击、元数据泄露、可利用的拒绝服务 |
| 低 | 纵深防御不足 |
| 建议 | 规范的清晰度、命名、文档 |

评审结论将连同我们的处理方式一起公开，在你同意的前提下署名致谢。
