## 1. 范围与拓扑

```
Chrome 扩展 ──Native Messaging(stdio)──▶ keevo-native-host ──Unix socket（keevo.sock）──▶ Vault Service（Keevo.app）
keevo CLI ──────────────────────────────────────────────Unix socket（cli.sock）──────▶ （同上，见 cli.md）
```

本规范定义：

1. 两段链路的分帧格式；
2. 操作系统层的对端身份校验；
3. 扩展与 Vault Service 之间的端到端加密：配对与会话；
4. 会话内的请求与响应。

CLI 与 Vault Service 之间的协议、会话授权见 [cli.md](cli.md)；对端校验使用本规范 §3.1 的同一机制。

## 2. 分帧

| 链路 | 帧格式 | 上限 |
|---|---|---|
| 浏览器 ↔ native host | 由 Chrome 定义：4 字节**本机字节序**长度 + UTF-8 JSON | 发往浏览器 1 MiB；来自浏览器 64 MiB，但本协议把单帧限制为 1 MiB |
| native host ↔ Vault Service | 4 字节**大端序**长度 + 内容 | 1 MiB |

- 长度为 0 或超过上限时，接收方必须立即断开连接，不能尝试恢复。
- **应用消息的容量**（第四轮评审 J4）：外层帧最多 1 MiB，但每条 Noise 消息最多 65,535 字节，减去 16 字节认证标签，**会话内一条 JSON 消息的明文最多 65,519 字节**。v1 不分页、不分片：
  - 放不进一条 Noise 消息的响应，改为返回 `response_too_large`，连接保持可用。例如凭据过长、无法自动填充时，扩展提示用户在 Keevo 中复制；
  - `candidates` 最多返回 20 个条目，标题与副标题各保留前 200 个 Unicode 标量值（只用于显示），保证响应放得进一条消息；
  - 超过容量的请求返回 `bad_request` 并断开。正常的请求都远小于这个上限。
- Vault Service 的 socket 位于数据目录 `~/Library/Application Support/Keevo/ipc/`，目录权限 0700。Keevo 不绑定开发者团队，不使用 App Group 容器（ADR-0003）。

## 3. 对端身份校验（操作系统层）

### 3.1 Vault Service 校验 socket 对端

1. 通过 `LOCAL_PEERTOKEN` 取得对端的 audit token，再以 `kSecGuestAttributeAudit` 属性调用 `SecCodeCopyGuestWithAttributes` 得到对端代码对象。不得只凭 PID 标识对端（PID 可被复用）。
2. **固定 cdhash 校验**：Keevo 不绑定任何开发者团队，所有产物都是临时签名，没有 Team ID 可供校验（ADR-0003）。改为：
   - **构建时**先签名 `keevo-native-host` 与 `keevo` CLI，取得它们的 cdhash，再把这些值**编译进主程序**，最后签名主程序；
   - 对端必须满足代码签名要求 `cdhash H"<其中之一>"`；
   - **运行时不从磁盘读取**辅助程序的 cdhash。否则同用户进程只需替换一个辅助程序，下次启动时服务就会信任替代品（第二轮评审 G6）。信任锚因此是正在运行的主程序本身。
3. 校验失败时立即断开，并记入本地安全日志。
4. **更新**：更新替换整个应用包，并重启 Vault Service（Sparkle 更新后重新启动应用）。重启之前，旧服务会拒绝新版本的 host；扩展遇到连接失败时等待片刻再重试。不在旧服务运行期间从磁盘重新加载白名单。
5. CLI 连接的是另一个 socket，同样按固定的 cdhash 校验（[cli.md](cli.md) §2）。
6. **信任边界**：本层只防"任意外部程序连接 socket"。同用户进程替换磁盘上的 Keevo 主程序，等于替换 Keevo 本身，属于非目标（`docs/security.md` §1）。

### 3.2 native host 校验父进程

- **浏览器侧限制**：host 清单中的 `allowed_origins` 只包含 Keevo 扩展 ID，由浏览器负责执行。
- **父进程校验**：host 启动时检查父进程的代码签名，Team ID 必须在白名单中（Google Chrome、Microsoft Edge、Brave 等，具体值在实现中维护，并在每个版本发布前核实）。不在白名单中时，host 立即退出。
- **来源参数**：Chrome 以扩展来源（`chrome-extension://<id>/`）作为第一个参数启动 host。host 把它原样转发给 Vault Service，作为配对记录的一部分。
- **父进程校验只是纵深防御，不是身份证明**（评审 2026-11-18 F2）：它检查的是查询时该 PID **当前**运行的代码，而不是创建 host 的进程。同用户的恶意进程可以先建立管道、派生出稍后执行 host 的子进程，再把自己 `exec` 成签名浏览器（PID 不变），host 看到的父进程就是浏览器，而管道与来源参数都由攻击者选择。该机制已用 Apple 签名的 `/bin/sleep` 复现；尚未在真实 Chrome 与正式签名的 host 上验证完整攻击链。
  - 因此，本协议**假设**落盘的扩展静态私钥可能被同用户进程读取并用于冒充已配对的扩展，由 §5.2 的按站点授权兜底。
  - 能把创建者身份、进程实例与通信端点绑定在一起的 OS 机制仍在调研（§7）；找到之前不得把本节写成安全保证。

> **实现状态**（M1.3）：
> - §3.2 父进程校验：已实现，按代码签名（`crates/keevo-macos`）。白名单目前只有已在构建机上核实的 Google Chrome（Team ID `EQHXZ8M8AV`）。

## 4. 端到端加密

**native host 只转发密文**，不参与加密，也看不到任何内容。

### 4.1 Noise 参数

| 用途 | 握手模式 | 套件 |
|---|---|---|
| 首次配对 | `XX` | `Noise_XX_25519_ChaChaPoly_SHA256` |
| 已配对后的会话 | `IK` | `Noise_IK_25519_ChaChaPoly_SHA256` |

- **角色**：扩展是发起方（initiator），Vault Service 是响应方（responder）。
- **prologue** 为 `"keevo/v<协议版本>/ipc" ‖ 0x00 ‖ 握手用途 ‖ 0x00 ‖ 扩展来源`（协议版本是十进制，v1 为 `"keevo/v1/ipc"`）：
  - 握手用途为 `"pair"` 或 `"session"`；
  - 扩展来源即 native host 收到的参数，例如 `chrome-extension://abc…/`。

  任何一方看到的扩展来源不一致，握手都会失败，因此一个扩展的配对无法被挪给另一个扩展使用。
  - 协议版本同样写在 prologue 中：双方对版本的认识不一致时握手失败，中间人改动 `hello` 中的版本（降级）不会成功（§5.5）。
  - 配对承诺与 SAS 的派生标签（`keevo/v1/ipc-pair-commit`、`keevo/v1/ipc-sas`）在 v2 中不变。
- **双方的静态密钥**：
  - 扩展的静态密钥在首次配对时生成，存于 `chrome.storage.local`。
  - Vault Service 的静态密钥在首次启动时生成，由 Secure Enclave 密钥包裹后存入数据目录（不使用钥匙串，ADR-0003）。

### 4.2 配对（XX）

1. 扩展生成 32 字节随机数 `nonce`，组成第 3 条消息的负载，并计算**配对承诺**：

   ```
   third      = nonce (32) ‖ 显示名的 UTF-8 字节（0–256 字节）
   commitment = SHA-256("keevo/v1/ipc-pair-commit" ‖ 扩展静态公钥 (32) ‖ third)
   ```

   `third` 是固定的二进制格式，不用 JSON：承诺覆盖的是**实际发送的字节**，因此不存在"同一语义、不同编码"（第二轮评审 G1）。
2. 扩展发起 XX 握手，共 3 条消息：
   - 第 1 条：扩展 → Vault Service，负载**恰好**是 32 字节的 `commitment`，否则 Vault Service 返回 `bad_request` 并断开。
   - 第 2 条：Vault Service → 扩展，负载为空；非空时扩展断开。
   - 第 3 条：扩展 → Vault Service，负载为 `third`。
3. Vault Service 读完第 3 条消息后，用握手得到的扩展静态公钥与收到的**原始负载字节**重新计算承诺。以下任一情况返回 `bad_request` 并断开：
   - 与第 1 条消息的承诺不一致；
   - 负载短于 32 字节，或显示名部分超过 256 字节、不是合法 UTF-8。
4. 握手完成后，双方计算短认证串：

   ```
   SAS = HKDF-SHA-256(IKM = handshake_hash, salt = "", info = "keevo/v1/ipc-sas", L = 6)
   ```

   6 个字节按 **SAS 词表 v1** 映射为 6 个词，按字节顺序显示（从左到右、从上到下，带序号 1–6）。
   - 词表：[`sas-wordlist-v1.tsv`](sas-wordlist-v1.tsv)，256 行，第 b 行（从 0 起）是字节 b：`两位小写十六进制\t英文词\t中文词`，UTF-8，LF 换行。文件的 SHA-256 为 `59265fd73d43cedc81dd462957e576b0e6099dfb0766af8ea78fbff9f4a02a1a`。
   - 同一个字节的英文词与中文词互为翻译。两端都**同时**显示中文词与英文词，不随界面语言切换，因此用户无论看哪一种都能对上。
   - 词表的性质（由 `crates/keevo-ipc` 的测试与 `scripts/check-sas-wordlist.swift` 检查）：
     - 中文词恰好两个汉字，全部 512 个字互不重复：两个不同的词不会共用任何一个字；
     - 中文词去掉声调后的拼音互不相同，念出来也不会混淆（多音字取默认读音）；
     - 英文词为 3–9 个小写字母，前 3 个字母互不相同，任意两个词的编辑距离至少为 2；
     - 都是具体、常用、中性的名词；按英文词的字母顺序排列。
   - 词表只是显示映射，不改变握手与 48 位的安全界限。发布后不再修改；改动必须使用新的词表版本，两端同时更新。两端版本不一致时用户看到的词不同，会按不一致拒绝，是安全的方向。
5. 两端同时显示 SAS，用户在 Keevo.app 中确认两边一致。
6. 用户确认后，Vault Service 保存配对记录：
   - 扩展的静态公钥；
   - 扩展来源；
   - 浏览器信息；
   - 显示名：去除控制字符（Cc）与格式字符（Cf，包括双向文字控制符与零宽字符）后，取前 64 个 Unicode 标量值。扩展与 Keevo.app 用同一规则，两边显示的名称一致；承诺按清洗前的原始字节计算。显示名只是标签，不能替代 SAS。
     Cf 按 Unicode 15.1 的固定列表，不随实现所用的 Unicode 版本变化：U+00AD、U+0600–U+0605、U+061C、U+06DD、U+070F、U+0890–U+0891、U+08E2、U+180E、U+200B–U+200F、U+202A–U+202E、U+2060–U+2064、U+2066–U+206F、U+FEFF、U+FFF9–U+FFFB、U+110BD、U+110CD、U+13430–U+1343F、U+1BCA0–U+1BCA3、U+1D173–U+1D17A、U+E0001、U+E0020–U+E007F；
   - 配对时间（Unix 毫秒）。

   扩展保存 Vault Service 的静态公钥。
   - **配对记录的保护**：存入加密的保险库数据库，与条目同等保护。Vault Service 在解锁时把它们读入内存，此后直到进程退出都留在内存中（锁定时也留着，以便已配对的扩展查询 `status`）。
   - 进程启动后、首次解锁前，配对记录不可读，IK 握手一律返回 `locked`。
   - **配对只在解锁时进行**：保险库锁定时（包括首次解锁前），XX 的第 1 条消息直接返回 `locked`。配对需要在原生界面确认，并写入加密数据库，两者都要求已解锁。
   - **确认时仍须是同一次解锁**（第四轮评审 J5）：配对开始时记下解锁代次（每次解锁得到一个新值）。用户确认后、保存之前，在持有保险库锁的情况下再读一次；已锁定，或锁定后又解锁过，都按拒绝处理（`locked`），不保存配对。
   - **保存成功才算配对**：配对记录写入数据库成功后，才向扩展发送 `paired`；写入失败按拒绝处理（`pairing_rejected`）。
   - **撤销只在解锁时进行**："设置 → 浏览器"位于解锁之后。撤销立即从内存删除，并写入数据库。写入失败时，这次撤销作为"待提交的撤销"保留在内存中：之后每次解锁，先应用待提交的撤销，再使用从数据库读出的记录，并重试写入，直到成功。
   - 不把配对记录放在只用 Secure Enclave 包裹的文件里：不需要用户在场的包裹无法阻止同用户进程解开再重新包裹，提供不了授权记录的完整性（第二轮评审 §4.2）。
7. **时限**：从 Vault Service 收到第 1 条消息的时刻起算 60 秒，覆盖握手与用户确认。
   - 超时后到达的第 3 条消息、超时后的确认都视为拒绝：返回 `pairing_rejected`，双方都不保存任何东西。用户拒绝时同样处理。
   - Vault Service 按这个**绝对**截止时间读写 socket：每一次底层读写之前都重新计算剩余时间，到期即断开，释放连接与配对闸门。只在每帧开始时设一次相对超时不够，对端可以每隔一会儿送一个字节，让每次读取都重新等待（第三轮评审 H5）。
   - 原生确认界面同样在截止时间关闭，并按拒绝处理。
8. **尝试次数**：
   - 收到第 1 条消息时，Keevo.app 立即显示"有浏览器正在请求配对"。这样每一次尝试都对用户可见，包括在第 3 条消息之前就放弃的尝试；
   - 同一时刻最多进行一个配对；每小时最多开始 10 次。超出时返回 `pairing_limited`；
   - 计数点是 Vault Service 处理第 1 条消息（随后发出第 2 条消息）：每发一次，对方就拿到一个新的服务端贡献。第 1 条消息无效的尝试也计数，宁可多计；
   - **计数只在一次服务运行内有效**：计数保存在内存中，Vault Service 重启后清零。不做持久化，是因为能拦截本机 IPC 的攻击者是同用户进程，它既能结束 Keevo，也能改写任何本机计数文件。对此的防护是第一条：每次尝试都对用户可见；
   - **扩展一侧**：每次配对尝试都由用户在扩展中主动发起，扩展不得自动重试配对。

**安全界限**（评审 2026-11-18 I1、第二轮评审 G1）：中间人要让用户确认，需要两段握手的 SAS 相同。

- **前提**：
  1. 双方的 `nonce` 与临时密钥每次新生成、不可预测、不重用；
  2. 承诺具有隐藏性（32 字节随机 `nonce`）与绑定性（SHA-256 抗碰撞）；
  3. 发起方在第 2 条消息之后再也没有可调整的字节——第 3 条负载已被承诺，且只有一种编码；
  4. SAS 的派生（HKDF-SHA-256）表现为随机函数；
  5. 用户在可信的两端完整比较全部 48 位。
- **推导**：
  - 攻击者冒充 Vault Service 与扩展握手时，必须在第 2 条消息中定下自己的全部贡献，而扩展一侧的握手结果还取决于第 3 条消息才公开的 `nonce`。
  - 攻击者冒充扩展与 Vault Service 握手时，第 1 条消息已承诺第 3 条消息的全部内容，而 Vault Service 的临时密钥在承诺之后才发送。
  - 因此一段握手完成后，另一段的 SAS 对攻击者是均匀随机的。
  - 攻击者唯一的自由是**重复尝试**：每次重新开始服务端握手，都得到一个新的服务端贡献，可以在发出第 3 条消息之前算出该段的 SAS，不符就放弃。
- **结论**：
  - **一次固定的扩展尝试**：设攻击者为这次尝试取得的服务端贡献数为 Q_s，它被错误确认的概率不超过 Q_s · 2⁻⁴⁸，再加上密码学假设失效的概率。第 8 条把 Q_s 限制为每次服务运行每小时 10 次，且每次都对用户可见。
  - **一段时间内的全部尝试**：攻击者可以让一个服务端握手保持待确认，同时作为响应方应对用户在扩展中重新发起的多次尝试（第三轮评审 H8）。设这段时间内服务端贡献共 Q_s 个、用户发起的扩展尝试共 Q_e 次，保守的界限是 Q_s · Q_e · 2⁻⁴⁸。
  - 例如一小时内 Q_s = 10、Q_e = 10，约为 3.6 × 10⁻¹³。
  - 多会话、自适应的攻击者下界限同样成立，非形式化论证见 [docs/analysis/ipc-pairing.md](../docs/analysis/ipc-pairing.md)；机器检查的模型（Tamarin / ProVerif）列为 M2 外部审计的一部分。

### 4.3 会话（IK）

1. 扩展用已保存的 Vault Service 公钥发起 IK 握手，共 2 条消息，负载均为空；接收方必须检查，非空即断开。
2. Vault Service 读完第 1 条消息后得到扩展的静态公钥：
   - 进程启动后尚未解锁过、配对记录还不可读：返回 `locked` 并断开（§4.2 第 6 步）；
   - 不在配对记录中，或来源与记录不符：发送错误帧（§5.3）并断开。
3. 握手完成后进入传输模式。每个方向的 nonce 都严格递增，任何重放或乱序都会导致解密失败并断开。
4. **会话生命周期**：
   - **锁定**：传输会话可以跨越锁定保留，授权不能。锁定时 Vault Service 推送 `locked` 事件（§5.2），不断开会话；锁定期间会话内只回答 `status`，其余请求返回 `locked`。
   - 会话最长存活 24 小时，之后必须重新握手。
   - native host 进程退出时，会话随之结束。

### 4.4 撤销

用户在"设置 → 浏览器"中解除配对后：
- Vault Service 删除配对记录，并立即断开该扩展的所有会话；
- 会话层在处理**每个**请求前都重新核对配对记录（公钥存在、来源一致），因此即使断开与请求之间存在竞态，撤销后的请求也一律返回 `not_paired` 并断开；
- 此后该扩展的 IK 握手都会失败，扩展提示重新配对；
- 撤销与锁定无关：重新解锁保险库不会恢复被撤销的配对；
- 配对记录写盘失败时，内存中的撤销仍立即生效，但必须提示用户"撤销可能在重启后失效"。
- **线性化点**：撤销以"在配对记录锁内删除记录"为准。之前已取得该锁的请求照常完成；之后取得锁的请求一律拒绝。已经发出、或已写入内核缓冲区的响应无法收回。
- 会话在建立后、发出任何内容之前登记，供撤销时主动断开；无法登记（例如取不到 socket 句柄）时立即断开该连接（第二轮评审 G7）。这同样适用于 XX 配对：用户确认、会话建立之后，先登记，再发送 `paired`（第三轮评审 H6）。

## 5. 消息

**v1 的消息集合是封闭的**：§5.1–§5.4 列出的就是 v1 的全部消息、字段与事件。任何新增（新方法、新字段、新事件、新错误码）都必须使用新的协议版本，在 `hello` 中协商；v1 的实现收到不认识的消息一律返回 `bad_request`。v2 的新增见 §5.5，同样是封闭的。

**只接受规范编码**（第四轮评审 J7）：每条 JSON 消息——控制帧、HostHello、会话内的请求与响应——都必须恰好是它的规范编码，否则视为 `bad_request`。规范编码的规则与 `vault-format.md` §1.1 相同：
- 字段按本节示例中的顺序；
- 不输出空白；
- 可选字段（例如 `fill` 结果中的 `totp`）缺省时不输出，不能写成 `null`；
- 请求的 `id` 是 0 到 2³²−1 之间的整数。

### 5.1 扩展 ↔ native host（明文控制层）

```json
{ "t": "hello", "v": 1 }                         // 扩展 → host：协议版本（v2 的扩展发送 2，§5.5）
{ "t": "pair", "d": "<base64url，无填充>" }        // 扩展 → 服务：XX 配对的第一条握手消息
{ "t": "session", "d": "<base64url，无填充>" }     // 扩展 → 服务：IK 会话的第一条握手消息
{ "t": "noise", "d": "<base64url，无填充>" }       // 双向：其余握手消息与传输消息
{ "t": "error", "code": "<错误码>" }              // 服务或 host → 扩展，随后断开
```

- **host 的职责**：
  - 收到 `hello` 后连接 Vault Service，先发送 `HostHello`（§5.4）。
  - 之后把扩展的每一帧原样放进 socket 帧转发，并把服务的回帧原样转回。
  - host 只检查帧大小与 JSON 结构，不解析 `d` 的内容。协议逻辑全部集中在 Vault Service，这样经过签名的 host 二进制攻击面最小。
- **握手用途由第一条消息的帧类型决定**：
  - `pair` 用于配对（XX），`session` 用于会话（IK）。
  - 同一连接中只能出现一次，出现在其他位置一律视为 `bad_request`。
- **配对确认**：XX 握手完成后，Vault Service 等待用户确认 SAS（§4.2）。
  - 确认后，发送加密的 `{"event": "paired"}`，此后才接受请求。
  - 拒绝或超时后，发送 `{"t": "error", "code": "pairing_rejected"}` 并断开。

### 5.2 会话内（Noise 传输层加密）

**请求**：

```json
{ "id": 1, "method": "status" }
{ "id": 2, "method": "candidates", "params": { "url": "https://github.com/login" } }
{ "id": 3, "method": "fill", "params": { "item_id": "<id>", "url": "https://github.com/login" } }
```

**响应与推送**：

```json
{ "id": 1, "result": { "locked": false } }
{ "id": 2, "result": { "items": [{ "item_id": "<id>", "title": "GitHub", "subtitle": "octocat" }] } }
{ "id": 3, "result": { "username": "octocat", "password": "…", "totp": "123456" } }
{ "id": 3, "error": { "code": "locked" } }
{ "event": "paired" }
{ "event": "locked" }
{ "event": "unlocked" }
```

v1 的事件只有这三个：`paired`（配对完成）、`locked`、`unlocked`。

**最小披露原则（Vault Service 强制执行）**：

| 规则 | 说明 |
|---|---|
| 候选只返回概要 | `candidates` 只返回与 `url` 匹配的条目（匹配规则见 architecture.md §5.3），且只含标题与副标题 |
| `candidates` 的频率限制 | 同一配对在任意 10 分钟内查询的不同站点（规范化为 `scheme://host[:port]`）超过 60 个时，返回 `not_authorized`；重复查询同一站点、非 http(s) 网址不计数。本时间窗内第一次被拒时在 Keevo.app 中提示。计数只在内存中。这是实现策略，阈值可调，线上格式不变（M1.3 评估结论见 §6） |
| `fill` 再次校验 | 再次检查 `item_id` 与 `url` 是否匹配，不匹配时返回 `url_mismatch`，绝不返回秘密 |
| `fill` 按站点授权 | 见下文。网址匹配只能防钓鱼，不能防冒充的扩展：后者可以为每个条目提供与之匹配的网址 |
| `fill` 可要求用户在场 | 按用户设置要求 Touch ID |
| 锁定时只回状态 | 锁定状态下，除 `status` 外的所有请求都返回 `locked` |

**`fill` 的按站点授权**（评审 2026-11-18 F2、I3；M1.3 已实现）：

1. **首次确认**：某个配对**第一次**为某个条目在某个站点取用凭据时，Vault Service 在 Keevo.app 的原生界面请用户确认，显示：
   - 站点（规范化后的 `scheme://host[:port]`）；
   - 条目标题与用户名；
   - 发起请求的配对（显示名、浏览器）。

   用户确认后记住 `(配对, 条目, 站点)`；拒绝或 60 秒内未确认时返回 `not_authorized`，不返回任何秘密。
   - 检查顺序：先按"`fill` 再次校验"核对网址（不匹配直接返回 `url_mismatch`，不询问用户），再看是否暂停、是否已授权，最后才取出秘密。
   - 等待确认期间：同一连接上的其他 `fill` 返回 `not_authorized`。确认后重新核对配对记录、锁定状态、网址与频率限制；等待期间锁定时返回 `locked`。
   - 一次只显示一个确认界面（配对与授权共用）；排队的请求到截止时间仍未显示，按拒绝处理。
2. **授权的存储与失效**：授权与配对记录存在一起，撤销配对时一并删除；用户可在"设置 → 浏览器"中逐项撤销。
   - 实现：每个配对一条本机记录（`crypto.md` §8.8，`kind` 为 `authorization`，`id` 为扩展静态公钥），明文为 `{"v":1,"items":[{"item_id":…,"site":…,"granted_at_ms":…}]}`。先写数据库，成功后才生效；写入失败按拒绝处理。
   - 重新配对不恢复旧授权；读入时丢弃不属于任何现存配对的授权。
3. **频率限制**：同一配对在任意 10 分钟内取用凭据的不同条目超过 5 个时（即第 6 个不同条目；已授权的也计入，重复取用同一条目不重复计数），拒绝这次请求（`not_authorized`），暂停该配对的 `fill` 并在 Keevo.app 中提示；用户确认后恢复并清空计数。计数只在内存中，Keevo.app 重启后清零。阈值为初始值，M1 实测后调整。
4. **原生界面不可被扩展伪造**：确认只出现在 Keevo.app 中，不出现在扩展或网页里。

### 5.3 错误码

| 错误码 | 含义 |
|---|---|
| `unsupported_version` | 协议版本不支持 |
| `not_paired` | IK 握手时，扩展的静态公钥不在配对记录中；或会话中途配对被撤销（§4.4） |
| `pairing_rejected` | 用户拒绝、确认超时，或配对记录保存失败（§4.2） |
| `pairing_limited` | 已有配对正在进行，或配对尝试过于频繁（§4.2 第 8 步） |
| `locked` | Vault Service 已锁定；或配对开始后保险库被锁定、已不是同一次解锁（§4.2 第 6 步） |
| `response_too_large` | 响应放不进一条 Noise 消息（§2） |
| `url_mismatch` | 条目与网址不匹配 |
| `not_found` | 条目不存在 |
| `bad_request` | 消息格式错误，包括配对承诺不符、握手负载不合规定 |
| `not_authorized` | 用户拒绝本次 `fill` 的站点授权、授权超时，或该配对因频率限制被暂停；`candidates` 查询的站点过多（§5.2）；v2 中用户拒绝 `update`、`save` 超过频率限制，或同一连接上已有请求在等待（§5.5）；v3 中 `search` 没有得到允许（§5.6） |
| `service_unavailable` | host 无法连接 Vault Service（应用未运行） |

### 5.4 native host → Vault Service 的首帧（明文）

```json
{ "v": 1, "client": "native-host", "extension_origin": "chrome-extension://…/", "browser": "com.google.Chrome" }
```

- `v` 是扩展在 `hello` 中请求的协议版本，host 原样转发（§5.5）。
- **为什么能信任**：这一帧来自已通过 §3.1 代码签名校验的 host。
- **用途**：其中的扩展来源同时用作 Noise prologue 的一部分，以及与配对记录的比对。

### 5.5 协议 v2：保存与更新

**版本协商**：
- 扩展在 `hello` 中发送它要使用的版本（v2 的扩展发送 `2`）。host 只接受自己认识的版本，把它原样写进 `HostHello` 的 `v`；Vault Service 不支持时返回 `unsupported_version` 并断开。
- 扩展收到 `unsupported_version` 后，改用低一个的版本重新连接（v3 → v2 → v1；会话直接重连；配对需要用户重新发起，扩展不得自动重试配对，§4.2 第 8 步）。v1 会话中没有保存与更新，v2 会话中没有 §5.6 的方法。
- 版本写在 Noise prologue 中（§4.1），由握手认证。配对记录与版本无关：v1 建立的配对在 v2 会话中照常使用。
- **每个版本的消息集合都是封闭的**：会话协商出的版本里没有的方法，一律按 `bad_request` 处理并断开（例如 v1 会话中的 `save`）。

**新增请求**（字段顺序即规范编码的顺序）：

```json
{ "id": 4, "method": "save", "params": { "url": "https://news.example/login", "username": "reader", "password": "…" } }
{ "id": 5, "method": "update", "params": { "item_id": "<id>", "url": "https://github.com/settings", "password": "…" } }
```

**结果**：两者成功时都只返回条目 ID，不返回任何其他内容。

```json
{ "id": 4, "result": { "item_id": "<id>" } }
```

v2 没有新增事件与错误码。

**规则（Vault Service 强制执行）**：

| 规则 | 说明 |
|---|---|
| 参数上限 | `password` 为 1–4096 字节，`username` 最多 1024 字节，`url` 必须是 http(s)；不满足时返回 `bad_request`，连接保持可用 |
| 锁定时 | 返回 `locked` |
| `save` 只保存站点 | 新条目放在第一个保险库中：类型为登录，标题是站点的主机名（含端口，去掉开头的 `www.`），网址是规范化后的站点 `scheme://host[:port]`，不保存路径与查询（其中可能有令牌） |
| `save` 不需要确认 | 只新增条目，不覆盖已有数据。为了让每次写入都可见，Keevo.app 在保存后显示提示（"「配对名」保存了新的登录"） |
| `save` 的频率限制 | 同一配对在任意 10 分钟内最多保存 5 个条目，超过时返回 `not_authorized`。计数只在内存中 |
| `save` 后的授权 | 保存成功后，记下这个配对为新条目在该站点的授权（§5.2）：凭据本来就是扩展提供的，之后填充不再询问 |
| `update` 再次校验 | 条目必须与 `url` 匹配（不匹配返回 `url_mismatch`，不存在返回 `not_found`） |
| `update` 每次都要确认 | 覆盖已有数据：Keevo.app 的原生界面显示站点、条目标题与用户名、发起请求的配对，60 秒内未确认按拒绝处理（`not_authorized`）。新密码与原来相同时界面会说明，但返回给扩展的结果与是否相同无关，扩展无法借此核对密码。确认后再核对一次条目与站点；旧密码留在条目的修订历史中 |
| 一次一个 | 同一连接上已有请求在等待（填充授权、写操作）时，新的写操作返回 `not_authorized` |

**扩展何时询问用户**（实现约定，不属于线上格式）：
- 用户提交带密码的表单后，扩展在页面顶部的保存栏（扩展源 iframe，与页内菜单相同的点击劫持防护）中询问。提交的密码只留在 Service Worker 的内存中，3 分钟后丢弃。
- 刚由 Keevo 填入、没有改动的密码：不询问。
- 当前网站没有同一用户名的条目：询问"保存"。
- 修改密码的表单（有 `autocomplete="new-password"` 的字段，或有两个以上密码框），且有同一用户名的条目：询问"更新"。普通登录表单不询问更新：扩展拿不到已保存的密码，无从判断是否改过；协议也不提供"核对密码"的方法，那会成为冒充者的猜测接口。

### 5.6 协议 v3：搜索全部条目、打开 Keevo、请求解锁

扩展弹窗的"搜索全部条目"、"在 Keevo 中打开"与锁定时的"用 Touch ID 解锁"（设计稿"扩展 · 弹窗：搜索、生成密码、新建登录与解锁"）。版本协商与 §5.5 相同：v3 = v2 的全部内容 + 下面三个方法，`status` 的结果多一个字段。消息集合同样封闭。

**新增请求**（字段顺序即规范编码的顺序）：

```json
{ "id": 6, "method": "search", "params": { "query": "git", "ask": false } }
{ "id": 7, "method": "open", "params": { "item_id": "<id>" } }
{ "id": 8, "method": "open", "params": {} }
{ "id": 9, "method": "unlock" }
```

**结果**：

```json
{ "id": 6, "result": { "items": [{ "item_id": "<id>", "title": "GitLab", "subtitle": "me@example.com" }] } }
{ "id": 7, "result": { "locked": false, "touch_id": true } }
```

- `search` 的结果与 `candidates` 相同：只含标题与副标题，最多 30 个，同样截短。
- `open`、`unlock` 与 `status` 返回同样的状态。v3 会话中 `status` 多一个 `touch_id`：现在能否用 Touch ID 解锁（已启用，且这次不要求输入主密码）。扩展据此决定锁定时的按钮文字；v1、v2 会话中没有这个字段。
- 没有新增事件与错误码。

**规则（Vault Service 强制执行）**：

| 规则 | 说明 |
|---|---|
| `search` 需要允许 | 每次解锁后，某个配对第一次搜索时，Keevo.app 的原生界面显示配对与搜索词，请用户允许；60 秒内未确认按拒绝处理（`not_authorized`）。允许记在内存中，绑定这次解锁的代次：锁定后再解锁即失效，撤销配对时清除 |
| `ask` | 还没有允许时，`ask: false` 直接返回 `not_authorized`，不打扰用户（扩展在用户输入时这样搜索）；`ask: true` 才请用户允许。同一连接上已有请求在等待时返回 `not_authorized` |
| `search` 的参数 | 搜索词去掉首尾空白后为 1–128 个字符，否则返回 `bad_request`，连接保持可用。锁定时返回 `locked`；等待允许期间锁定或换了一次解锁，返回 `locked` 且不记下允许 |
| `search` 的范围 | 不在回收站中的全部条目，按标题、副标题与登录网址的主机名匹配，不区分大小写；标题以搜索词开头的排在前面 |
| 搜索结果不能填充 | 其他网站的条目仍受 `fill` 的网址核对约束（`url_mismatch`）；扩展只提供"在 Keevo 中打开" |
| `open` | 给出条目时，解锁状态下核对条目存在（不存在返回 `not_found`），再请 Keevo.app 显示主窗口并选中它；锁定时也可调用，只显示锁屏 |
| `unlock` | 锁定时请 Keevo.app 显示锁屏，说明是哪个配对在等待；可以用 Touch ID 时直接请求验证。不等待解锁完成，立即返回状态；已解锁时什么也不做 |
| 抢占焦点的频率 | `open` 与 `unlock` 会让 Keevo.app 来到前台，同一配对两次之间至少间隔 1 秒（`open`）与 30 秒（`unlock`，与命令行工具、SSH 一致）；间隔内的请求照常返回状态，只是不打扰 Keevo.app |

**Keevo.app 与扩展的配合**（实现约定，不属于线上格式）：
- Keevo.app 来到前台时，扩展弹窗随之关闭。用户在 Keevo 中允许搜索、或在 2 分钟内完成解锁后，Keevo.app 激活发起请求的浏览器（配对记录中的 bundle ID），扩展随即重新打开弹窗（`chrome.action.openPopup`），恢复搜索词或显示条目。
- Vault Service 目前不推送 `locked` / `unlocked` 事件（§7），扩展在请求解锁后每秒查询一次 `status`，最多 2 分钟。
- 生成密码在扩展内进行（WASM，与 Keevo.app 同一份实现 `keevo-generator`），不经过本协议；"新建登录"使用 v2 的 `save`。

## 6. 安全性质与残余风险

| 威胁 | 防护 |
|---|---|
| 其他扩展冒充 Keevo 扩展 | 浏览器的 `allowed_origins` 限制；扩展来源写入 prologue 与配对记录 |
| 本机恶意进程直连 socket | §3.1 代码签名校验；即便连上，没有已配对的静态私钥也无法完成 IK 握手 |
| 恶意进程启动 native host | §3.2 父进程校验，**仅为纵深防御**：可被 fork→exec 绕过 |
| 中间人篡改或重放 | Noise 认证加密；nonce 严格递增 |
| 首次配对被中间人截获 | SAS 由用户确认；配对承诺与尝试次数限制（§4.2）。对一次固定的扩展尝试，被错误确认的概率不超过 Q_s · 2⁻⁴⁸，Q_s 在同一次服务运行内每小时不超过 10；一段时间内的全部尝试为 Q_s · Q_e · 2⁻⁴⁸。每次尝试都对用户可见 |
| 扩展的静态私钥被窃取（例如同用户进程从浏览器配置目录读出），再绕过 §3.2 冒充扩展 | **按站点授权**（§5.2）：未授权的站点需要用户在原生界面确认；频率限制；敏感操作可要求 Touch ID；用户可随时撤销配对 |
| 冒充的扩展写入保险库（v2） | `update` 每次都在原生界面确认，旧密码留在历史中；`save` 只新增条目，有频率限制，每次都在 Keevo.app 中提示；结果只含条目 ID，不泄露任何内容 |
| 冒充的扩展枚举全部条目（v3） | `search` 每次解锁后都要用户在原生界面允许，并显示搜索词；`ask: false` 不会弹出确认，冒充者无法借此打扰用户。允许之后，同一次解锁内与 `candidates` 一样只返回概要 |
| 冒充的扩展反复抢占焦点、弹出 Touch ID（v3） | `open` 与 `unlock` 按配对限频；解锁只在 Keevo.app 中完成，扩展拿不到主密码，也不能代替用户通过 Touch ID |
| 降级到 v1（v2） | 协议版本写在 prologue 中，改动版本会让握手失败（§4.1、§5.5）；即使降级成功，也只是失去保存与更新 |
| 冒充 Vault Service（扩展一侧） | 配对时 Keevo.app 中必然弹出确认窗口，扩展的配对界面提示"没有出现就不要继续"。**不防**同用户进程：它可以替换 host 清单、直接充当服务发送 `paired`，也能不经提示地解开服务静态私钥（`crypto.md` §8.7 用途 0x03）。见残余风险 |

**残余风险**：
- 冒充成功的攻击者可以取得用户**已授权**的站点的凭据，速度受频率限制约束。
- `candidates` 不需要授权，冒充者可以逐个猜测网址，得知用户在哪些站点有账户以及对应的用户名。**M1.3 评估结论**：增加频率限制（§5.2，10 分钟内 60 个不同站点）。它挡不住有耐心的攻击者（每小时仍可查询约 360 个站点），主要价值是让枚举变得可见：超过阈值时 Keevo.app 提示用户，用户可以解除配对。阈值远高于正常使用（只在用户打开弹窗、菜单或提交表单时查询）。
- 冒充 Vault Service 的同用户进程能看到扩展查询的网址；在 v2 中还能收到用户请求保存或更新的密码。这与 `docs/security.md` A7 一致：同用户恶意进程不在防护范围内，Keevo 不把扩展一侧的连接当作对抗它的边界。分析见 [docs/analysis/ipc-pairing.md](../docs/analysis/ipc-pairing.md) §5。
- 用户允许搜索之后（v3），同一次解锁内，冒用这个配对的攻击者也能搜索全部条目的标题与用户名，不受 `candidates` 的站点数限制。允许绑定解锁代次，锁定即失效；确认界面显示搜索词，用户没有在扩展中搜索时应拒绝。
- 冒充的扩展（v2）可以在频率限制内新增条目，例如为某个网站保存攻击者自己的账户，诱导用户之后用它登录。Keevo.app 对每次保存都有提示，条目也可在保险库中查看与删除。
- Noise 依赖（snow 0.10）内部的 DH 私钥与 ChaCha 密钥副本没有清零（见 `docs/security.md` §9）。
