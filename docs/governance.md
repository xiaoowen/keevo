# 开源治理与透明度

## 1. 许可证

**现状**：仓库根目录使用 MIT 许可证。

**建议**：在接受第一个外部贡献之前定下来。之后再更换许可证，需要征得所有贡献者的同意。

| 组件 | 建议许可证 | 理由 |
|---|---|---|
| `crates/*` 核心库、`spec/` | MIT OR Apache-2.0（Rust 生态惯例） | 鼓励第三方实现兼容的客户端，方便审计与复用；格式规范完全开放 |
| `apps/macos`、`apps/browser-extension`、`keevo-cli` | GPL-3.0-or-later + App Store 附加许可（GPL 第 7 条） | 防止出现闭源的分叉客户端；附加许可保证将来可以上架 App Store / Mac App Store |
| 将来的 `server/`（暂缓） | AGPL-3.0-or-later | 防止有人修改服务端后作为闭源 SaaS 提供 |

- **备选**：全部保持 MIT。最简单、采用门槛最低，代价是无法阻止闭源分叉。
- **贡献协议**：App Store 附加许可从第一天起写进许可证，贡献者提交的代码自然适用，因此用 **DCO**（提交时 `Signed-off-by`）即可，不需要 CLA。

## 2. 透明度承诺

- **公开**：设计文档、威胁模型、加密规范与测试向量、审计报告全文、已知限制。
- **可验证**：
  - 可复现构建（先从扩展做起）。
  - 发布签名。
  - 构建来源证明（SLSA，通过 GitHub artifact attestations）。
  - SBOM。
- **网络请求清单**：公开列出客户端可能发起的每一个网络请求、触发条件和发送的数据（见 §5）。
- **透明度报告**：如果将来提供官方托管服务，定期发布透明度报告（如政府数据请求的数量与处理结果）。

## 3. 安全漏洞处理

- **入口**：根目录的 `SECURITY.md`，以及网站上的 `/.well-known/security.txt`。
- **私密渠道**：GitHub Private Vulnerability Reporting，外加 PGP 加密邮件。
- **SLA**：
  - 首次响应 ≤ 2 个工作日。
  - 严重漏洞修复目标 ≤ 14 天。
  - 修复发布后公开安全公告（GHSA + CVE），并致谢报告者。
- **漏洞赏金**：1.0 后启动。
- **安全港声明**：对善意的安全研究不追究法律责任。

## 4. 供应链安全

- **Rust**：
  - `cargo-vet`：导入 Mozilla、Google 等机构的公开审计记录。
  - `cargo-deny`：许可证白名单、禁止特定 crate、限制重复依赖。
  - `cargo-audit`：RustSec 安全公告。
- **JavaScript**：
  - npm 锁文件，CI 使用 `npm ci --ignore-scripts`（禁止依赖的安装脚本）。
  - 扩展的运行时依赖尽量控制在 10 个以内（M0 为零，只有 TypeScript 与类型定义两个开发依赖）。
- **GitHub Actions**：
  - 第三方 Action 固定到提交 SHA。
  - 工作流声明最小 `permissions`。
  - 发布任务使用受保护环境，并需要人工审批。
- **签名**：
  - 维护者的提交与 tag 都要签名。
  - macOS 产物使用临时签名并启用 Hardened Runtime，不公证（ADR-0003）；发布 SHA-256 校验和。
  - Sparkle 更新使用 EdDSA 签名。
  - 发布产物使用 Sigstore 签名。
- **更新安全**：客户端校验更新签名，禁止降级到旧版本。

## 5. 隐私承诺（产品层面）

- **零遥测**：客户端不发送任何使用数据。
- **仅在用户启用后才会发生的网络请求**：

| 请求 | 触发条件 | 发送的数据 |
|---|---|---|
| 更新检查 | 默认开启，可关闭 | 当前版本号 |
| HIBP 泄露密码查询 | 用户在安全中心开启 | 密码 SHA-1 哈希的前 5 位（k-匿名），带填充 |
| 网站图标 | 用户开启 | 域名 |
| 同步 | 用户开启同步 | Keevo 自身不发起任何网络请求，只把加密文件写进 iCloud 云盘或用户选择的文件夹，由系统或云盘客户端负责传输 |

- **错误报告**：只在用户手动导出时生成脱敏诊断包，由用户自行决定是否提交。

## 6. 社区与协作

- **决策**：重大技术决策写 ADR（`docs/adr/`），公开讨论；大功能先走 RFC。
- **路线图**：在 GitHub Projects 上公开。
- **贡献入口**：
  - Issue 与 PR 模板。
  - `good first issue` 标签。
  - 中英双语文档。
- **代码所有权**：安全敏感路径（`crates/keevo-crypto`、`crates/keevo-ipc`、`spec/`）在 CODEOWNERS 中要求安全负责人审查；涉及密码学的改动需要两人批准。
- **发布密钥**：至少由两名维护者分别持有，避免单点。

## 7. 可持续性（待决策）

长期运营的开源项目需要稳定的资金。下面这些模式都不影响开源与自托管承诺，可以组合使用：

- 捐赠：GitHub Sponsors / Open Collective。
- 可选的官方托管同步服务：依赖自托管服务端，随服务端一起再议；如果提供，必须运行与自托管完全相同的开源代码。
- 面向小团队的付费支持。

**原则**：任何商业化都不得削弱自托管能力，也不得把安全功能放到付费墙后面。
