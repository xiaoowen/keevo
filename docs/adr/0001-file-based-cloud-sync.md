# ADR-0001：先做基于文件的云同步，暂缓自托管服务端

- **状态**：已采纳；默认的 iCloud 位置由 [ADR-0002](0002-icloud-drive-folder-without-team.md) 修订
- **日期**：2026-11-17

## 背景

Keevo 需要多设备同步。最初的规划是在 M2 交付自托管服务端 `keevo-server`。

调整后的需求有两点：
- **优先支持 iCloud 等云同步**，让用户用已有的云存储就能同步，不必自己运行服务。
- **自托管服务端先不做**。

## 决策

1. M2 的同步方案改为**基于不可变文件的加密日志**：
   - 每台设备只往同步文件夹里追加自己签名的加密日志段。
   - 各设备在本地合并。
2. 存储位置：
   - **默认推荐 iCloud**，使用 Keevo 专属的 iCloud 容器。
   - 同时支持**任意文件夹**：Dropbox、OneDrive、Google Drive、坚果云等桌面客户端同步的文件夹，以及 Syncthing、NAS、外置硬盘。
3. 同步引擎通过 `SyncStore` 抽象与存储解耦。将来的 WebDAV、S3 直连以及自托管服务端都作为新的 `SyncStore` 实现接入。
4. 自托管服务端暂缓、不排期，已有思路保留在 [future/self-hosted-server.md](../future/self-hosted-server.md)。

## 备选方案

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| **A. 文件日志（采纳）** | 一套实现覆盖 iCloud、所有云盘和自托管存储；Keevo 自身零网络请求；单写者加不可变文件，天然避开云盘的写冲突 | 实时性取决于云盘客户端；需要应对未下载文件、乱序到达等云盘行为 | 采纳 |
| B. CloudKit 私有数据库 | 原生推送通知、记录级原子操作，iCloud 体验最好 | 只能服务 iCloud，其他云盘还得另写一套；数据模型与 Apple 深度绑定，不利于跨平台 | 不采纳。如果 iCloud 文件同步在实测中不够可靠，可以作为 iCloud 专用的 `SyncStore` 再评估 |
| C. 直连各云盘 API（Dropbox、Google Drive、OneDrive） | 不需要安装云盘客户端，iOS 上也能用 | 每家都要单独实现 OAuth 和 API；Keevo 需要联网、管理第三方令牌；攻击面和维护成本都高 | 不采纳。后续只做 WebDAV 和 S3 两个通用协议 |
| D. 自托管服务端 | 实时推送、可强制审批新设备、支持共享协调 | 用户必须自己部署和维护；需要单独审计服务端 | 暂缓 |

## 影响

**安全**：
- 威胁模型中的"恶意服务器"改为"不可信的存储提供方，或任何能写入同步文件夹的人"。
- 完整性保护从"签名的保险库头"改为"每台设备一条签名的日志哈希链，加上高水位线"。
- 2SKD 变得更加关键：加密后的密钥集就放在用户的云盘里。
- 云盘会保留文件历史版本，因此新增"应急轮换"能力：重新加密全部数据，让旧密钥彻底失效。

**数据格式**：
- 条目修订从递增的整数修订号改为 `rev_id` 加父修订列表组成的修订图。
- 字段带混合逻辑时钟时间戳。
- 这些都在 M1 落地，开启同步时无需迁移。

**范围**：
- M2 移除服务端、OPAQUE 和 Docker 相关工作。
- M2 新增 iCloud 集成、云盘行为适配、局域网配对加入，以及模拟各种云盘行为的测试。

**已知局限**：无法强制审批新设备；暂不支持与他人共享；同步延迟取决于云盘。这些都会在产品中如实告知用户（见 [sync.md §9](../sync.md#9-局限会在产品中如实告知用户)）。
