# 浏览器配对的多会话安全分析

- **对象**：`spec/ipc.md` §4.2 的配对（Noise XX + 配对承诺 + 48 位 SAS，由用户在 Keevo.app 中确认）。
- **问题**：§4.2 的"安全界限"只论证了"一次固定的扩展尝试"与"一段时间内的全部尝试"两种情形。攻击者可以同时打开多个会话、交错推进、根据已看到的内容决定下一步（多会话、自适应）。本文论证在这种攻击者面前，界限 Q_s · Q_e · 2⁻⁴⁸ 仍然成立，并写明它不覆盖什么。
- **性质**：这是手写的非形式化论证，不是机器检查的证明。用 Tamarin 或 ProVerif 建模列为 M2 外部审计的一部分。

## 1. 模型

**参与者**：
- 诚实的扩展 X：用户每在扩展中点一次"与 Keevo 配对"，就开始一次扩展尝试（发起方）。每次尝试新生成临时密钥与 32 字节配对随机数 `nonce`。
- 诚实的 Vault Service S：每处理一次第 1 条消息、发出第 2 条消息，就开始一次服务尝试（响应方），每次新生成临时密钥。
- 攻击者 A：完全控制 X 与 S 之间的通道（例如替换了 native host），可以无限次地开启会话、转发、修改、丢弃、交错，并据已看到的一切自适应地决定下一步。

**用户**：只在以下情况下确认配对：Keevo.app 显示一个待确认的配对，扩展弹窗同时显示一组配对码，两者的 6 个词逐个相同。这是对攻击者最有利的假设：用户不会拒绝"碰巧相同"的配对码。

**实现约束**（都由 Vault Service 或扩展强制执行，见 §4.2）：
1. S 同一时刻最多一个配对；每次服务运行每小时最多开始 10 次（计数点是发出第 2 条消息）。
2. 每次服务尝试都对用户可见（收到第 1 条消息时即显示"有浏览器正在请求配对"）。
3. 扩展不自动重试配对；弹窗只显示最近一次尝试的配对码。
4. 配对从第 1 条消息起 60 秒内必须完成确认，并且必须是同一次解锁。

**计数**：Q_s 为攻击者在考察的时间段内取得的服务尝试数，Q_e 为用户在这段时间内发起的扩展尝试数。

**攻击者获胜**：S 保存了一条配对记录，其扩展静态公钥不是 X 的。也就是用户确认了一个由攻击者充当扩展的服务尝试。

## 2. 假设

- **H1（随机预言机）**：SHA-256 与 HKDF-SHA-256 表现为随机预言机。SAS = HKDF(握手哈希 h)，取 48 位。
- **H2（新鲜性）**：诚实方的临时密钥与 `nonce` 均匀随机、互相独立、从不重用。
- **H3（承诺）**：commitment = SHA-256(标签 ‖ 扩展静态公钥 ‖ third) 具有隐藏性（`nonce` 为 256 位随机数）与绑定性（SHA-256 抗碰撞）。
- **H4（Noise）**：Noise XX 与 IK 在 Gap-DH 假设下，满足文献中对这两种模式的认证与保密性质（Noise Explorer 对这两种模式的分析）。本文只用到：完成的 XX 握手中，双方的握手哈希 h 覆盖 prologue、双方的临时公钥、加密后的静态公钥与全部负载密文。
- **H5（编码唯一）**：第 3 条消息的负载 third 是固定的二进制格式，没有第二种编码（第二轮评审 G1）。

## 3. 定理

在上述模型与假设下，攻击者获胜的概率不超过

  Q_s · Q_e · 2⁻⁴⁸ + ε，

其中 ε 是 H1–H5 之一被攻破的概率。按实现约束，一小时内 Q_s ≤ 10；若用户这一小时内发起 Q_e = 10 次扩展尝试，约为 3.6 × 10⁻¹³。

## 4. 论证

**第 1 步：只有"成对"的会话可能导致获胜。** 用户每次确认时，比较的是 Keevo.app 中**唯一**待确认的服务尝试 j（约束 1）与扩展弹窗中**最近**的扩展尝试 i（约束 3）。所以每次获胜都对应一对 (i, j)：
- j 中充当扩展的是攻击者（否则保存的就是 X 的公钥，攻击者没有获胜）；
- 用户确认时 SAS_e(i) = SAS_s(j)。

若 i 与 j 的消息被原样转发（没有中间人），两边的 h 相同，保存的是 X 的公钥，不算获胜。下面只考虑 j 中攻击者充当扩展、i 中攻击者充当服务的情形。

**第 2 步：服务尝试 j 的 SAS 在它被决定时对攻击者均匀随机。**
- 在 j 中，攻击者是发起方。它在第 1 条消息中发送临时公钥 e_A 与 commitment_A。
- 由 H3 的绑定性，此后它能让 S 接受的第 3 条消息，其中的静态公钥与 third 都已被 commitment_A 确定：静态公钥与 third 一起进入承诺，S 按收到的原始字节重算（H5）。
- S 在收到第 1 条消息**之后**才生成临时密钥 e_S（H2），h_j 是 (e_A, commitment_A, e_S, s_S, 已确定的静态公钥与 third) 的函数。
- 由 H1，在 e_S 生成的那一刻，SAS_s(j) 是独立于此前全部记录的均匀 48 位值。攻击者唯一的选择是放弃 j 再开一次，这计入 Q_s。

**第 3 步：扩展尝试 i 的 SAS 在它被决定时对攻击者均匀随机。**
- 在 i 中，攻击者是响应方。X 先发送临时公钥 e_X 与 commitment_X；commitment_X 由 H3 的隐藏性不泄露 `nonce`。
- 攻击者必须在第 2 条消息中定下自己的全部贡献（临时公钥、静态公钥、负载），之后才收到第 3 条消息。
- 第 3 条消息的负载 third_X 含有 X 新生成的 `nonce`，它的密文进入 h_i。
- 由 H1 与 H3，在第 3 条消息发出的那一刻，SAS_e(i) 是独立于此前全部记录的均匀 48 位值。

**第 4 步：对每一对，相等的概率不超过 2⁻⁴⁸，与攻击者的自适应选择无关。** 固定一对 (i, j)，考察两个 SAS 中**较晚**被决定的那个：
- 由第 2、3 步，它在被决定的那一刻，独立于此前的全部记录均匀分布。较早的那个值属于"此前的全部记录"。
- 因此两者相等的概率恰为 2⁻⁴⁸，无论攻击者此前如何交错、选择、放弃会话。
- 攻击者可以在看到两个值之后再决定是否把这一对呈现给用户（例如让服务尝试保持待确认，或丢弃它），但这只能**挑选**已经相等的一对，不能**制造**相等。

**第 5 步：对所有对取并集。** 可能被用户比较的对，至多 Q_s · Q_e 对。由并集界，存在任何一对相等的概率不超过 Q_s · Q_e · 2⁻⁴⁸。获胜要求用户确认的那一对相等，因此获胜概率不超过这个值，再加上假设被攻破的概率 ε。∎

## 5. 不覆盖的内容

- **人的因素**：论证假设用户逐个比较全部 6 个词。只比较前两个词时，有效位数降为 16，界限相应变为 Q_s · Q_e · 2⁻¹⁶。界面要求逐个核对、两端同时显示中英文，但无法强制。
- **攻击者冒充服务（扩展一侧）**：本文分析的是 S 的配对记录（攻击者冒充扩展）。扩展收到 `paired` 即保存服务公钥，自己这一侧没有确认：
  - 能替换 host 清单的同用户进程，可以充当服务完成 XX 并直接发送 `paired`，完全不经过 Keevo.app。此时 Keevo.app 中不会出现任何确认窗口，唯一的防线是用户注意到这一点。扩展的配对界面因此写明"Keevo 中会弹出确认窗口；如果没有出现，请不要继续"。
  - 同用户进程还能不经提示地解开服务静态私钥（`spec/crypto.md` §8.7 用途 0x03 不要求用户在场），从而在已配对之后冒充服务。
  - 冒充服务的攻击者能看到扩展查询的网址；在协议 v2 中，还能收到用户在网页上提交、请求保存或更新的密码。
  - 这属于 `docs/security.md` A7 的残余风险（同用户恶意进程），已写入 `spec/ipc.md` §6。
- **已配对之后**：IK 会话的安全性直接依赖 H4 与静态私钥的保密。扩展静态私钥被窃取时，由按站点授权（§5.2）兜底，不在本文范围内。
- **实现缺陷**：本文论证的是规范，不是代码。实现与规范的一致性由测试（含 `spec/test-vectors/ipc-v1.json` 的跨实现向量）与评审保证。
- **机器检查**：Tamarin / ProVerif 模型尚未建立。

## 6. 与实现的对应

| 论证中用到的约束 | 实现 |
|---|---|
| 同一时刻最多一个待确认的服务尝试；每小时最多 10 次 | `keevo-ipc` 的 `PairingGate`（`review2_g1_pairing_attempts_are_limited` 等测试） |
| 第 3 条负载被承诺、只有一种编码 | `pairing_commitment`；服务按原始字节重算（`review2_g1_any_byte_change_in_third_message_is_rejected`） |
| 每次服务尝试对用户可见 | `Output::PairingStarted` → Keevo.app 的"有浏览器正在请求配对" |
| 扩展不自动重试、弹窗只显示最近一次 | `apps/browser-extension/src/background.ts`：配对只由用户点击发起，新尝试先断开旧连接 |
| 60 秒、同一次解锁 | `PAIRING_TIMEOUT`、按绝对截止时间读写（H5）、确认时核对解锁代次（J5） |
| SAS 的派生与显示 | `Handshake::sas`；`spec/test-vectors/ipc-v1.json` 的 `sas` 与 `sas_words` |
