# 本地存储与云同步

> 为什么选择"基于文件的加密日志"，而不是 CloudKit、云盘 API 直连或自建服务端：见 [ADR-0001](adr/0001-file-based-cloud-sync.md)。

## 1. 原则

- **本地数据库是这台设备的事实来源**：每台设备都保存一份完整副本。
- **所有读写都在本地完成**：同步在后台进行，离线可以无限期工作。
- **同步可选**：M1 纯本地；M2 提供 iCloud 与文件夹同步。
- **不需要任何服务器**：
  - Keevo 只负责把加密文件写进一个文件夹，由 iCloud 或云盘客户端负责在设备间搬运。
  - Keevo 自身不发起任何同步网络请求。
- **存储位置和提供方都不可信**：
  - 它们只能看到不透明的密文文件。
  - 任何篡改、注入、回滚都会被检测到。
- **格式从 M1 起就为同步设计**：修订图、记录级时间戳、墓碑。M2 开启同步时不需要做数据迁移。

## 2. 本地存储模型（SQLite）

```sql
-- 所有 *_ct 列都是 Envelope 密文（见 security.md §7）
CREATE TABLE account (
  id              BLOB PRIMARY KEY,
  format_version  INTEGER NOT NULL,
  epoch           INTEGER NOT NULL,     -- 修改主密码或轮换密钥时递增
  kdf_params      BLOB NOT NULL,        -- 算法、m、t、p、salt（不是秘密，但纳入 AAD）
  keyset_ct       BLOB NOT NULL         -- 由 AUK 加密的账户密钥集
);

-- 条目和保险库的每一次修改都是一个不可变的修订
CREATE TABLE revision (
  rev_id          BLOB PRIMARY KEY,     -- 随机 128 位
  object_id       BLOB NOT NULL,        -- 条目 ID 或保险库 ID
  object_type     INTEGER NOT NULL,     -- item | vault
  vault_id        BLOB NOT NULL,
  parents         BLOB NOT NULL,        -- 父修订 ID 列表
  origin_device   BLOB NOT NULL,
  origin_seq      INTEGER,              -- 尚未写入同步日志时为 NULL
  wrapped_key_ct  BLOB,                 -- 条目：VK 包裹的 IK；保险库：ASK 包裹的 VK
  overview_ct     BLOB,                 -- 条目概要 / 保险库名称与图标
  details_ct      BLOB,                 -- 条目的全部字段（保险库为空）
  deleted         INTEGER NOT NULL DEFAULT 0,   -- 墓碑
  pruned          INTEGER NOT NULL DEFAULT 0    -- 内容已清理，只保留祖先关系
);
CREATE INDEX revision_by_object ON revision(object_id);

-- 每个对象当前的"头"修订（没有并发修改时只有 1 个）
CREATE TABLE head (
  object_id       BLOB NOT NULL,
  rev_id          BLOB NOT NULL,
  PRIMARY KEY (object_id, rev_id)
);

CREATE TABLE attachment (
  id              BLOB PRIMARY KEY,
  item_id         BLOB NOT NULL,
  wrapped_key_ct  BLOB NOT NULL,        -- 由条目密钥包裹的附件密钥
  meta_ct         BLOB NOT NULL,        -- 文件名、类型、大小
  chunk_count     INTEGER NOT NULL
);

-- M2：已知设备与防回滚高水位线
CREATE TABLE device (
  id              BLOB PRIMARY KEY,
  cert            BLOB NOT NULL,        -- 由账户签名密钥签发的设备证书
  revoked_after   INTEGER,              -- 撤销后，只接受序号不超过此值的段
  high_seq        INTEGER NOT NULL DEFAULT 0,   -- 见过的最高段序号
  high_hash       BLOB                          -- 该段的哈希
);
```

**明文列只保留合并与校验必需的 ID 和标记**。修改时间、归档状态、回收站状态都在 `overview_ct` 中加密存放。

**写入**：
- 每次修改都在一个事务内完成：新建一个修订，其 `parents` 为该对象当前的全部头，然后更新 `head` 表。
- **条目历史就是修订链**。每个条目默认保留最近 20 个修订的内容（可配置），更早的修订标记为 `pruned`，只保留 ID 和祖先关系。头修订永远不会被清理。

**其他**：
- **附件**：分块以文件形式存放在 `attachments/<id>/<n>`，不进 SQLite。
- **搜索索引只在内存中**：解锁后从概要构建，锁定时销毁。1 万个条目的概要解密加建索引，目标在 200 ms 以内。
- **本地备份**：用 SQLite 在线备份 API 生成一致的副本（仍然是密文），连同附件目录一起保存。每日一次；导入、迁移、批量删除前额外备份；默认保留 30 份。

## 3. 修订模型与合并

精确定义见 [spec/revisions.md](../spec/revisions.md)，这里只概述。

### 3.1 修订图与记录

- 修改只追加新修订，从不原地改写。
- **单设备或没有并发修改时**：每个条目只有一个头，修订是一条直线。
- **两台设备在离线期间修改了同一条目时**：会出现两个头，需要合并。
- **记录**：条目由一组"记录"组成，包括属性、标签、分区和字段。每个记录版本都带两项信息：
  - 写入它的修订 `rev`；
  - 混合逻辑时钟时间戳 `hlc`：设备之间系统时间不一致时，也能给出合理的先后顺序。
- **删除也是一个版本**：删除的记录保留为墓碑，以便与"从未存在"区分。

### 3.2 合并：因果优先，读时合并，写时收敛

逐个记录选出胜出版本：

| 情况 | 处理 |
|---|---|
| 一个版本在因果上晚于另一个（写入它的修订已经看到了另一个版本） | 晚的胜出，**不看时间戳**，因此不受时钟误差影响 |
| 两个版本并发，都没有看到对方 | `hlc` 更大的胜出（相同时按设备 ID 决定）；条目标记"有冲突待查看"，落选的值仍在其修订中，可以一键恢复 |
| 并发的删除与修改（字段或整个条目） | 保留修改，撤销删除，并提示用户 |
| 一方新增字段，另一方删除了它所在的分区 | 保留新增的字段，分区随之恢复 |

**结果的确定性**：合并只取决于头修订的内容与修订图，与合并顺序和本地历史清理进度无关，所有设备都会得到相同结果。

**读时合并，写时收敛**：
- 合并视图在读取时计算，不自动写回，避免多台设备互相触发写入、来回震荡。
- 用户下一次编辑该条目时，新修订以全部头作为父修订，多个头随即收敛为一个。

**原则：宁可多保留，绝不静默丢失。**

### 3.3 删除与墓碑

1. **删除**：条目进入回收站。回收站只是条目的一种状态，照常同步。
2. **变成墓碑**：30 天后或用户手动清空回收站时，写入一个 `deleted = 1` 的修订，内容为空。
3. **清理墓碑**：只有当所有未撤销设备的日志都已体现这个墓碑之后，墓碑才可以被清理。

## 4. 同步文件夹格式

### 4.1 目录结构

```
<同步位置>/
└── keevo-<account_id 前 8 位>/
    ├── keevo.json                          # 明文清单：格式版本、account_id（随机生成，不含个人信息）
    ├── account/
    │   └── <epoch>-<device_id>.kacct       # 账户文件：KDF 参数 + AUK 加密的密钥集，账户签名
    ├── devices/
    │   └── <device_id>.kdev                # 设备证书，账户签名
    ├── logs/
    │   └── <device_id>/
    │       └── <seq，10 位补零>-<hash16>.kseg   # 日志段：只追加、不可变
    ├── snapshots/
    │   └── <device_id>-<seq>-<hash16>.ksnap     # 快照
    └── blobs/
        └── <hash 前 2 位>/<hash>.kblob          # 附件分块（按内容寻址）
```

文件名中只有随机 ID、序号和哈希，不会泄露条目名称、网站或保险库名称。

### 4.2 不变量

这些规则保证即使云盘行为不可靠，同步也不会出错：

1. **单写者**：每台设备只创建和删除自己名下的文件，包括自己的 `logs/<device_id>/`、自己写的快照和自己的设备证书。因此不同设备之间不存在写冲突。
2. **文件不可变**：文件一旦写入就不再修改。所有"修改"都通过新增文件完成。
3. **原子写入**：先在同目录写一个以 `.` 开头的临时文件，`fsync` 后再重命名为正式文件名。读取方忽略所有临时文件和不符合命名规范的文件。
4. **自校验**：文件名包含内容哈希，内容经过 AEAD 加密和设备签名。校验失败时视为"还没同步完整"，稍后重试；多次失败则告警。
5. **与到达顺序无关**：合并结果只取决于读到了哪些修订，与文件到达的顺序和时间无关。

### 4.3 日志段

本地的修改在空闲 2 秒后打包成一个段（持续修改时最长 30 秒打包一次），写入自己的日志目录：

```
Segment {
  format_version
  device_id
  seq            // 本设备的段序号，从 1 开始单调递增
  prev_hash      // 上一段文件的 SHA-256，形成本设备的哈希链
  hlc
  frontier       // 写入时已合并的各设备最高序号 {device_id: seq}，用于因果判断与清理
  entries        // 修订（与本地 revision 行相同，内层仍是由各自密钥加密的 Envelope）
                 // 以及账户级操作：撤销设备、轮换保险库密钥等
}

文件内容 = Envelope_SyK( Segment ‖ Sig_device(Segment) )
```

- **外层加密**：外层用账户同步密钥 SyK 加密整个段，存储提供方连"哪些条目被修改了"都看不到。
- **签名**：由设备密钥签名，设备密钥位于 Secure Enclave，不可导出。其他设备核对签名是否来自一个已登记且未撤销的设备。
- **本机留副本**：每台设备在本地保留自己尚未被快照覆盖的段。如果发现同步文件夹里的段丢失，会自动补写。

### 4.4 快照与清理

- **何时写快照**：一台设备读到的、尚未被快照覆盖的段超过 500 个或 10 MB 时写一个快照。快照包含：
  - 所有对象当前头修订的完整密文；
  - 每个对象最近 100 个修订的 ID（祖先关系）；
  - 快照覆盖到的 `frontier`。
- **快照的用途**：新设备和长期离线的设备先加载最新的有效快照，再回放它之后的段，不需要从头回放全部历史。
- **清理**：
  - 设备可以删除自己的旧段，前提是这些段已被某个快照覆盖，且该快照已存在超过 30 天。这段缓冲期留给正在下载的设备。
  - 每台设备只保留自己最近 2 个快照。
- **长期离线的设备**：即使离线超过 30 天，本地未同步的修改也不会丢失。它会照常写出新段；新段里的修订引用的父修订 ID 仍在快照的祖先关系中，可以正常合并。

### 4.5 账户文件与设备证书

**账户文件 `.kacct`**：
- 内容：`epoch`、KDF 参数（明文，因为解锁之前就需要），以及由 AUK 加密的密钥集。AAD 绑定 `account_id`、`epoch` 与 KDF 参数，最后由账户签名密钥签名。
- 修改主密码或轮换密钥时，写一个 `epoch` 更大的新文件。
- 两台设备同时修改主密码时，取 `epoch` 更大的；`epoch` 相同则取 HLC 更新的，并在另一台设备上提示用户。

**设备证书 `.kdev`**：
- 内容：设备 ID、设备公钥（P-256）、创建时间、加密的设备名，由账户签名密钥签发。
- 没有账户密钥的人无法伪造设备，因而也无法写入任何能被其他设备接受的段。

## 5. 同步流程

- **开启同步**：
  1. 在所选位置创建目录。
  2. 写入 `keevo.json`、账户文件、本设备证书。
  3. 写入一个包含全部数据的初始快照。
- **写**：本地修改 → 打包成段 → 原子写入。
- **读**：
  1. 监听文件变化：iCloud 用 `NSMetadataQuery`，其他文件夹用 FSEvents；另外每 60 秒以及应用激活时全量扫描一次。
  2. 需要时请求下载文件。
  3. 校验哈希、签名和哈希链。
  4. 解密后把修订合并进本地数据库。
  5. 更新该设备的高水位线。
- **防回滚**：
  - 某设备在文件夹里的最高序号低于本地记录的高水位线，或者同一序号出现了不同的哈希，就说明数据被回滚、被篡改，或者设备被克隆。
  - 此时暂停接收该设备的段，并告警。
  - 本地副本不受影响。
- **状态展示**：设置中列出每台设备"最后一次同步过来的时间"，帮助用户发现某台设备长时间没有数据进来。

## 6. 同步位置

### 6.1 iCloud（默认推荐）

> 依据 [ADR-0002](adr/0002-icloud-drive-folder-without-team.md)：使用 iCloud 云盘中的普通文件夹，不需要任何开发者团队、证书或描述文件。

- **位置**：`iCloud 云盘/Keevo/`（磁盘路径 `~/Library/Mobile Documents/com~apple~CloudDocs/Keevo/`）。路径已知，因此新设备可以自动发现已有账户。
- **已实测可行**（[验证报告](spikes/2026-11-18-icloud-folder.md)）：未签名的进程即可完成写入、读取上传与下载状态、移除本地内容、按需下载、文件协调。
- **读写**：通过 `NSFileCoordinator` 协调，采用原子重命名（§4.2）。
- **变化监听**：用 FSEvents 加定期全量扫描。没有 iCloud 权限时，`NSMetadataQuery` 看不到任何文件（实测）。
- **未下载的文件**：开启"优化 Mac 储存空间"后，文件可能只在云端。读取前先检查 dataless 状态，需要时调用 `startDownloadingUbiquitousItem(at:)` 并等待，而不是直接读取（直接读取会阻塞，见 §6.3）。
- **账户变化**：监测 `ubiquityIdentityToken`（未签名进程也能取到）。用户退出 iCloud 或切换 Apple ID 时，暂停同步并提示。
- **文件夹可见**：用户可能误删、移动或改名。
  - 误删由哈希链与本机副本补救。
  - 文件夹找不到时暂停同步并提示，绝不自动新建空文件夹。
  - 文件夹内放 `请勿修改.txt` 说明用途。
- **iOS**：将来的 iOS 应用通过文件选择器授权访问同一个文件夹。
- **与 Apple 的关系**：开启"iCloud 高级数据保护"后，iCloud 云盘本身也是端到端加密的。Keevo 不依赖这一点，只把它当作额外一层防护。
- **将来的增强**：Keevo 有了自己的开发者账号后，可以改用专属容器 `iCloud.<bundle-id>`（数据对 Finder 隐藏），新增一个 `SyncStore` 实现即可，同步格式不变。

### 6.2 云盘文件夹与自托管存储

| 位置 | 方式 | 适合 | 注意 |
|---|---|---|---|
| Dropbox / OneDrive / Google Drive / Box / 坚果云等 | 选择其桌面客户端同步的本地文件夹 | 已经在用这些云盘，或需要跨 Apple ID 同步 | 需安装官方客户端；建议把该文件夹设为"始终保留在此设备" |
| Syncthing / NAS（SMB）/ 外置硬盘 | 任意本地或挂载的文件夹 | 完全自托管，数据不经过任何第三方 | 网络盘断开时自动暂停同步 |

- **所有位置走同一个实现**：iCloud 云盘与其他文件夹共用同一套格式、同步引擎和文件夹 `SyncStore`（见 [architecture.md §3](architecture.md#3-rust-workspace-模块)）。iCloud 只额外提供下载状态查询与"请求下载"。
- **一个账户同时只使用一个同步位置**。以后可以支持多个位置互为冗余（协议本身支持）。

### 6.3 云盘的不可靠行为及应对

| 行为 | 应对 |
|---|---|
| 文件尚未下载（iCloud 优化存储、云盘按需下载） | 读取前先检查是否只在云端（`SF_DATALESS` 或下载状态）。只在云端时请求下载并等待通知，下载完成前视为"还没到达"。**不要直接读取**：实测直接读取会自动触发下载并阻塞调用线程（0.3–1 秒，断网时更久）；任何读取都不在主线程进行 |
| 上传状态报错 | 实测文件在排队上传时会反复报 `NSCocoaErrorDomain 4355`（服务器暂不可用），上传完成后自动消失，所以 4355 视为暂时状态，持续数分钟才提示。配额不足（4354）立即提示 |
| 没有 iCloud 权限时监听变化 | `NSMetadataQuery` 看不到任何文件（实测结果为 0），文件夹模式改用 FSEvents 或目录监视（实测 12–14 毫秒收到通知），外加定期全量扫描 |
| 同步有延迟，文件到达顺序混乱 | 段带序号和哈希链，有缺口就等待补齐；合并结果与到达顺序无关 |
| 读到写了一半的文件 | 原子重命名；校验失败视为未完成，稍后重试 |
| 冲突副本（`xxx (1).kseg`、"conflicted copy"） | 单写者加不可变文件，正常情况下不会产生；不规范的文件名一律忽略并记入诊断信息 |
| 用户误删文件，或提供方回滚了文件夹 | 发现序号倒退或段缺失时告警；本机保留自己的段副本并自动补写；其他设备的数据也都完整保存在各自本地 |
| iCloud 或云盘空间已满 | 检测上传错误并提示；本地使用不受影响 |
| 设备被克隆（迁移助理、从备份恢复到另一台 Mac） | 设备密钥在 Secure Enclave 中且仅限本机，不会随迁移复制；恢复出来的 Mac 会自动作为新设备加入。若仍检测到同一设备 ID 的哈希链分叉，就停止接收并要求该设备重新登记 |

## 7. 新设备加入

1. 在新 Mac 上选择"加入已有账户"，然后选择同步位置：
   - 选 iCloud：在 `iCloud 云盘/Keevo/` 中自动发现已有账户。
   - 选文件夹：指向同一个文件夹。
2. 获取账户密钥（四选一）：
   - **局域网配对（推荐）**：
     1. 在旧 Mac 上选择"添加设备"，两台 Mac 通过 Bonjour 互相发现。
     2. 用 Noise XX 建立加密通道，两边显示相同的 6 个词，由用户确认一致。
     3. 旧 Mac 经 Touch ID 授权后，把账户密钥发给新 Mac。
   - **扫码**：用新 Mac 的摄像头扫描旧 Mac 屏幕上或应急包上的二维码。
   - **手动输入**：输入应急包上的账户密钥。
   - **iCloud 钥匙串（可选，默认关闭）**：账户密钥随 iCloud 钥匙串同步，同一 Apple ID 的新 Mac 自动获得。代价是：iCloud 钥匙串一旦被攻破，保护就退化为只剩主密码。开启前会向用户说明这一点。
3. 输入主密码 → 派生 AUK → 解开账户文件中的密钥集。
4. 新设备在 Secure Enclave 中生成设备密钥，签发设备证书并写入 `devices/`。
5. 加载最新快照，回放之后的段，建立本地副本。
6. 其他设备发现新的设备证书后弹出通知："新设备『MacBook Air』已加入"。如果这台设备不是你的，可以一键撤销并轮换密钥。

## 8. 撤销设备与密钥轮换

**撤销设备**：
- 撤销记录写进执行撤销那台设备的日志里，注明被撤销设备最后一个被接受的段序号。
- 之后所有设备都拒绝该设备序号更大的段。

**轮换密钥**：撤销只能阻止对方继续写入，挡不住它读取文件夹里的数据。所以撤销时，以及怀疑密钥泄露时，都需要轮换：

| 模式 | 做法 | 适用场景 |
|---|---|---|
| 修改主密码 | 只用新 AUK 重新加密密钥集，写一个新 `epoch` 的账户文件。很快完成 | 日常更换主密码 |
| 应急轮换 | 生成新的账户密钥、ASK、SyK、全部 VK 和 IK，**重新加密全部条目**，再写一个新快照 | 设备丢失或被撤销；怀疑主密码或应急包泄露 |

**为什么需要应急轮换**：
- iCloud 和各家云盘都会保留文件的历史版本。修改主密码后，用旧密码加密的旧账户文件仍然留在历史版本里。
- 只有应急轮换能让已泄露的旧密钥彻底失效。

## 9. 局限（会在产品中如实告知用户）

- **延迟**：几秒到几分钟，取决于 iCloud 或云盘客户端，不如专用服务器实时。
- **提供方能看到的信息**：文件数量、大小（已填充到长度桶）、写入时间、设备数量。看不到任何内容。
- **新设备无法强制审批**：任何同时拥有主密码、账户密钥和文件夹访问权的人都能加入。Keevo 只能在其他设备上发出通知。
- **撤销收不回已经同步过去的数据**：撤销设备只能阻止它继续写入，它已经拿到的数据收不回来，必须配合应急轮换。
- **暂不支持与他人共享保险库**：多人共享需要一个协调方，留给后续设计（见 [roadmap.md §6](roadmap.md#6-m4-方向)）。

## 10. 后续演进

- 多个同步位置互为冗余，例如 iCloud 加 NAS。
- WebDAV（Nextcloud、群晖、坚果云）和 S3 兼容存储的直连实现，适合 iOS 和不想安装云盘客户端的场景。
- 自托管服务端（暂缓，见 [future/self-hosted-server.md](future/self-hosted-server.md)），它将作为又一种 `SyncStore` 实现，并补上实时推送、设备审批和共享协调等能力。
