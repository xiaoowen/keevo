## 4. 逐条处理

### G1：配对承诺与尝试次数

- **核实**：同意。承诺覆盖的是解析后的字段，而握手哈希覆盖实际发送的密文字节。JSON 的键顺序、空白、转义都会改变 SAS 而不改变承诺。评审还指出，发出第 1 条消息、收到第 2 条后就放弃的尝试对用户不可见，这一点也成立。
- **修复**：
  - 第 3 条消息改为 `nonce (32) ‖ 显示名的 UTF-8 字节`，承诺按收到的原始字节核对，不再有第二种编码。显示名部分不超过 256 字节，且必须是合法 UTF-8。
  - 收到第 1 条消息即输出 `PairingStarted`，由 Keevo.app 显示"有浏览器正在请求配对"。
  - 所有连接共用一个 `PairingGate`：同一时刻最多一个配对，每小时最多开始 10 次，超出返回 `pairing_limited`。计数点是服务发出第 2 条消息。
  - 截止时间在收到第 1 条消息时立即记录；服务把它用作 socket 的读超时，到期即断开，释放连接与闸门。
  - 显示名清洗增加 Unicode 格式字符（Cf，包括双向文字控制符和零宽字符），按 Unicode 标量值截断。扩展通过 `ExtensionClient::display_name` 使用同一个函数。
- **规范的安全界限**：
  - 写出了全部前提：新鲜性、承诺的隐藏性与绑定性、无后发可变字节、SAS 派生的随机函数假设、用户完整比较 48 位。
  - 结论改为"约 Q · 2⁻⁴⁸，Q 为攻击者取得的服务端贡献数"。规范不再声称"每次尝试只有 2⁻⁴⁸"。
- **另一个附带问题**：评审发现代码注释仍写着"从握手完成起计算"，已修正。

### G2：对象墓碑与写时收敛

- **对象墓碑**：确认。复现测试修复前失败——一次合并得到"已删除"，分组合并得到存活文档。
  - 修复：每个墓碑头在合并时视为在保留键 `attr:purged` 上写了一个版本（`hlc = 0`，`rev` 为墓碑，值为 `true`）。它与 `attr:trashed` 走同一套规则：删除被撤销时，这些版本移入并发版本随合并状态保存。
  - 墓碑修订的存储格式不变，仍不含任何内容。
  - 修复后两个反例与 300 组随机分组模拟都通过。
- **回收站反例**：同意评审"不单独证明新增恢复规则是错误的"的判断。在仓库中验证了：回收站在**纯合并**下与一次合并一致（`review2_g2_trash_survives_grouped_pure_merge`）。差异只来自写入时的 `settle_for_write`，这是一个用户操作。
- **规范的处理**：`revisions.md` §5.3 改为：结合律对纯合并成立，包括对象是否存在；写时收敛包含用户操作（编辑、处理冲突、确定恢复），不是纯合并。§5.4 要求界面说明"保存即确认恢复"。
- **删除成立后的残留内容**：评审提到永久删除与未解决并发值的关系，这里有一个连带问题。删除成立但仍有携带内容的头时，这些内容不会被清理。§6 新增规则：客户端再写一个墓碑，父修订为全部头。这是一次新的删除操作，M2 随同步实现。
- **其他**：解码器现在只允许删除状态键只有并发版本（评审 §4 的一项）。

### G3：历史保留的时间模型

- **核实**：同意。墙上时钟前跳与迁移都会提前清理。
- **修复**：存储层维护**有效时间**，每次写入或清理时推进：前进量等于墙上时间的增量，单次最多 1 天；墙上时间倒退时不变。修订的保存时间与清理截止时间都用有效时间计。
  - 时钟前跳、倒退再校正、长期不用，都只会让保留变长。
  - 代价是长期不用后，保留会比日历上的 90 天更久。规范如实写明了这一点。
- **迁移**：v1 → v2 时，已有修订按迁移时的有效时间计。
- 两个复现测试按评审的构造写入仓库，修复后通过。

### G4：读取前限长与 KDF 预算

- **数据库读取**：修订与账户在读取前，先用只在 WHERE 子句里计算 `length()` 的查询检查各列长度，不会读入 BLOB 内容。
  - 若与内容列放在同一个 SELECT 中，SQLite 产生这一行时就已经读入了整个 BLOB，因此不能合并成一次查询。
  - 上限：信封列不超过 `MAX_ENVELOPE_LEN`，ID 恰好 16 字节，KDF 参数恰好 29 字节，父修订最多 256 个。
  - 写入用同一套上限，保证写进去的一定读得出来。
- **KDF**：
  - 在 Argon2 调用处加进程级互斥，覆盖任意多个保险库实例。
  - `unlock_confirmed_expensive_kdf` 改为接收用户确认过的那组参数，派生前与数据库中的参数比较，不一致就不派生。新增 `Vault::kdf_params` 供界面展示。
  - 预算数值在规范中标为初始值，M1.1 按设备校准。

### G5：大小预算

按 §3 的决定实现：
- `ItemDoc::encode_for_write` 在写入前检查大小，超出返回 `ItemTooLarge`，核心层与 FFI 透传。
- 新增 `Vault::compact_item`，在一次写入中处理冲突并删除指定记录。
- 单个记录值上限 256 KiB，写入与解码都检查。
- 复现测试：70 个并发修订各写一个接近 256 KiB 的备注，合并后约 17.5 MiB。验证可以读取，普通保存失败且不写入，精简后可以保存。

### G6：cdhash 的信任根

- **核实**：同意。原规范在运行时从磁盘读取辅助程序的 cdhash，是循环信任。
- **修复**：规范改为构建时先签名辅助程序，把 cdhash 编译进主程序，再签名主程序；运行时不从磁盘读取。
  - 更新时替换整个应用包并重启服务。重启之前，旧服务拒绝新的 host 是预期行为，扩展稍后重试即可。
  - 评审指出 `security.md` 的非目标里没有 ADR 引用的"替换程序"条款，这一点成立。按 §3 的决定补上，并写明只替换辅助程序无效。
- **实现**：cdhash 的编译与打包随 M1.1 的应用打包实现。

### G7：会话登记

- **核实**：同意代码审查结论。`try_clone` 失败时原来会静默返回，连接继续工作。
- **修复**：
  - 会话在发送任何内容之前登记，`emit` 之后再登记一次，覆盖用户确认配对的情况。
  - 登记失败或发现配对已撤销时，立即断开连接。
  - 连接结束时总是 `shutdown`。
- **规范**：§4.4 写明线性化点（在配对记录锁内删除）与"已发出的响应无法收回"。
- **测试**：评审用子进程降低文件描述符上限来触发这个分支，不适合放进常规测试，因此没有新增回归测试。改动是显式的失败分支，可以直接审查。

### G8：完整性告警

- **决定**：不持久化矛盾证据，而是明确它的含义（`revisions.md` §5.6）：
  - 它只表示本次合并的候选中观察到的矛盾；
  - 保存前必须展示，保存即视为用户已知晓；
  - 提示消失不代表历史已被认证。
- **理由**：持久且可验证的出处需要认证摘要，属于 M2 签名设备日志的职责。在格式层另存一份证据，既不能证明出处，又会让"任意编辑都不能解决"的状态长期残留。
- 评审另外指出"单头中被篡改的祖先原值"无法发现，同意，同样留给 M2。

## 5. §4 规范与实现的不一致

| 差异 | 处理 |
|---|---|
| 承诺只覆盖解析字段 | G1，第 3 条消息改为二进制，承诺原始字节 |
| nonce 的 base64 变体未写明 | 第 3 条消息不再使用 base64，问题不复存在 |
| "规范 JSON"没有定义 | `vault-format.md` §1 定义**规范编码**：字段按规范列出的顺序，缺省字段省略，无空白，写明字符串转义规则与整数格式。没有采用 RFC 8785，因为那需要先转换成通用 JSON 值，会在不清零的内存中多复制一份秘密；现有的结构体编码已经满足上述规则 |
| 解析时的重复键 | 记录映射与并发版本映射遇到重复键一律拒绝；整数限定在 ±(2⁵³−1) |
| `(hlc, origin)` 相同时没有最终决胜规则 | 规范与代码统一为 `(hlc, origin, rev)` |
| 任意键都可以只有并发版本 | 只允许 `attr:trashed`、`attr:purged`，解码器强制执行 |
| 对象存在性不属于极大元集合 | G2 |
| 90 天的例外 | G3 |
| 数据库入口未限长；KDF 只是实例级互斥 | G4 |
| 并发版本没有可容纳保证 | G5 |
| 注释仍称"从握手完成起算" | 已改 |
| 比较规范编码时的明文副本没有清零 | 改为保存在 `Zeroizing` 中，且只在同一 `rev` 出现不同内容时才计算 |
| `RevisionGraph` 接受环与未知父修订（评审 §5） | `insert` 要求父修订已存在，父修订列表按集合比较；拒绝未知父修订与自环 |
| HLC 极值让本机时钟饱和（评审 §5） | 远端值比本机时钟快 24 小时以上时不推进本机时钟；时钟耗尽时 `next` 返回错误，而不是重复发出同一个值 |
| `spec/ipc.md`、`docs/security.md`、`noise.rs` 中残留的证书与钥匙串表述 | 已改为实际方案 |

## 6. ADR-0003 与发布

| 评审意见 | 处理 |
|---|---|
| SE 包裹对同用户进程不提供保护（已实测跨进程解包） | `crypto.md` 新增 §8.6，定义本机包裹格式，并逐项写明提供和不提供的保护。ADR、`security.md` A7 与 §8 同步更新 |
| 服务静态私钥的影响不等于账户密钥 | ADR 单列一行：取得它可冒充 Vault Service 与扩展握手，没有"还需主密码"这一层；作为 A7 的残余风险接受 |
| 配对记录"同上"与 IPC 的加密数据库要求冲突 | 配对记录与站点授权改为存入加密的保险库数据库，解锁时读入内存；进程启动后首次解锁前，IK 返回 `locked`（`ipc.md` §4.2、§4.3）。M1.3 实现 |
| 设备标记"比钥匙串更可靠"缺乏依据 | 删除比较级，写明它能发现与不能发现的情况 |
| spike 的包裹参数不能直接当规范 | §8.6 定义了版本、用途、HKDF 的 salt 与 info、AAD、失败行为 |
| 混淆了 Library Validation 的启用与放行 | 改为保留默认的 Library Validation，静态链接 Rust 核心；评审的实测结果写入 ADR 与 spike 报告 |
| "不使用任何 entitlement"过于笼统 | 改为不使用需要团队授权的受管能力；本地 entitlement 与运行时例外同样不用，但不再说成都需要团队签发 |
| 校验和与签名被当成等价的来源保证 | 改为：来源与完整性靠 Sigstore，验证时固定签名身份与 OIDC issuer；校验和只核对与可信摘要是否一致；Sparkle 公钥编译进应用；可执行的验证步骤 M3 定稿 |
| 能力表措辞过于绝对 | Gatekeeper 放行流程标为待验证；Safari 改为"正式支持"做不了；iOS 改为支持政策；钥匙串一行写明需要访问组权限的具体能力 |

## 7. 回答评审者的问题

| # | 问题 | 回答 |
|---|---|---|
| 1 | §5.3 是否包含对象存在状态？ | 包含。墓碑头以 `attr:purged` 版本进入合并状态，结合律对纯合并成立（G2） |
| 2 | `settle_for_write` 的恢复是否算用户明确操作？ | 是。界面必须在冲突面板中说明"保存即确认恢复这个条目"（revisions §5.4） |
| 3 | 超过 16 MiB 时是否拆分存储？ | 不拆分。读取与导出照常，普通保存拒绝，提供一次写入完成的精简，绝不静默丢弃（G5） |
| 4 | 90 天指什么？迁移与时钟前跳如何处理？ | 指本机有效时间：单次最多前进 1 天，倒退不变；迁移按迁移时间计；时钟前跳只会延长保留（G3） |
| 5 | "每次尝试"如何计数？是否采用唯一编码？ | 按服务发出第 2 条消息计数，收到第 1 条消息即对用户可见，同时最多一个、每小时最多 10 次；第 3 条消息采用唯一的二进制编码。跨实现测试向量与 SAS 词表一起在 M1.3 提供（G1） |
| 6 | 配对记录与站点授权放在 SE 文件里吗？ | 不放。存入加密的保险库数据库，ADR 已改正 |
| 7 | 启动时读取 cdhash 的信任锚是什么？ | 主程序本身：cdhash 在构建时编译进去。不保证安装目录对同用户不可写，因此把替换主程序写入非目标；更新时服务重启（G6） |
