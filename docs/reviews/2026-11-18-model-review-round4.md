## 1. 冻结结论

**评审提交：`16c787ddf3c881fd0a0b7d555937b4af566c8415`。** 评审开始执行 `git rev-parse HEAD` 得到此值，工作区原先干净。范围为 `git diff 6f49829..16c787d` 的 31 个文件，以及四份规范之间的整体一致性。本文所有生产源码行号均指 `16c787d`，不指临时副本中追加测试后的行号。

**结论：有条件冻结。`16c787d` 不能按作者提议的完整范围立即冻结。** 第三轮的 23 个测试移植后全部通过，说明原来的具体反例多数已修复；但这不足以支持新的普遍性承诺。本轮确认了多 `Store` 实例提前清理新历史、保留键导致上限以内仍不能精简、超过墓碑父上限后无法完成重建，以及写入后不能解码的记录键。另有跨文档容量和解析边界尚未定稿：合法记录不一定能通过 `fill` 返回，附件、部分 IPC 消息和版本演进仍被同时列作“冻结”和“M1 待定义”。没有发现无需密钥即可解密保险库或绕过 Noise 来源绑定的新攻击。

### 冻结前必须修改的规范条文

1. **补全大小策略的闭合性，不能再用提高上限代替证明。** `revisions.md` §7.1 必须覆盖 `attr:purged` 的并发恢复墓碑，以及超过 65,536 个头的状态；明确可执行的精简／重建／永久删除规则，删除“旧条目总能被永久删除”的错误保证。分批写墓碑属于新的删除操作，不能未经论证当作纯合并。见 J2。
2. **为有效时间补上数据库所有权前提。** `revisions.md` §7.2 目前描述的是进程时间，代码实际维护每个 `Store` 的独立时间原点。应选择并规定“同一数据库只有一个计时及写入所有者”，或定义多实例共享、不会使新记录年龄跳变的协议；同时更正“有效时间至少等于真实经过时间”的反向表述。旧 schema v2 的墙上时间不能被无条件宣称为已保守迁移。见 J1。
3. **固定 JSON 的接受集合和比较字节。** `vault-format.md` §1–§3 应明确对象／数组形态、可选字段的缺省与 `null`、整数词法与越界错误、嵌套枚举的唯一合法形态；不得把 Serde 的额外接受行为当作未写出的规范。补全字段必选性、缺省值和比较值编码的符合性表。墓碑比较编码和已有字段顺序本轮已明确，无需推翻它们。见 J7。
4. **决定 IPC 应用消息的真实容量。** `ipc.md` §2、§5.2 应同时写出外层帧、Noise 密文和应用明文的上限，定义过大凭据／候选列表的行为。如果 M1 需要分页或分片，其消息格式须在冻结前定义；也可明确选择有界返回和既定错误，不能靠实现届时自行增加字段。见 J4。
5. **形成逐项冻结清单，并修正版本规则。** `spec/README.md` 的“0.x 允许不兼容变更”与本次冻结定义相冲突；文档版本 `0.4`、JSON `v=1`、Envelope `0x01`、IPC `v=1` 及域标签中的 `v1` 必须区分。附件引用与分块、CLI 授权帧、未定推送事件等，要么现在定稿，要么明确排除并承诺将来的独立版本／迁移，不能把“整个文档”与“未决事项”一起冻结。还应补齐 Vault、Item 各 part 的 AAD 上下文赋值表。见 J8。

这些是冻结前的设计决定，不是给实现留一个任意改变格式的接口。可以继续以当前代码开展 M1；完成上述条文、核对其没有引入新的接受集合或合并语义矛盾后，才可把相应 v1 格式标为冻结。

## 4. 新发现

### J1．中：独立的 Store 时间原点会提前清理另一个实例的新历史

**位置：** `spec/revisions.md` §7.2；`crates/keevo-store/src/lib.rs:220`、`:646`、`:679`。

**问题与前提：** 同一数据库同时有两个 `Store`，两者不必同时执行 SQL。每个实例第一次调用 `effective_now` 时各自缓存 `(max(stored_ms), Instant)`，而不是共享数据库时间。长期运行但没有新修订落盘的实例 A，比稍后取旧数据库最大值为原点的 B 计得更快。A 随后用自己的时间清理 B 的新记录，会把 A 在 B 写入之前经过的时间也算成这些记录的年龄。

**复现：** `r4_two_store_clocks_must_not_age_fresh_writes`：

1. 打开空数据库 A，调用 `effective_now()`，基准为 0。
2. 等待 220 ms，保持 A 打开。
3. 打开同一数据库 B；其最大保存时间仍为 0。用 B 连续写入 25 个链式修订。
4. 用 A 执行 `prune(object, 20, 200)`。从 B 开始写入至检查只有约 5.7 ms，A 却清除了最早 5 个修订的内容。

测试把保留期缩为 200 ms，仅为了不等待 90 天；没有改变生产计时算法。对真实 90 天，A 长期运行而数据库最大保存时间没有同步推进，随后 B 写入时存在相同推导。它不是通过篡改数据库来“证明能够删除数据库”。

**影响：** 在多实例使用条件下，仍在承诺保留期内的历史内容丢失。当前 VaultService 使用一个互斥保护的 Vault，测试没有证明其默认单实例部署会自然触发；但 Store／Vault 打开接口没有排他所有权，规范也没有这个前提，用户要求的多实例情形不满足保证。

**相关边界：** 单实例依次关闭、重新打开通常只会少计最后一次写入以后的运行时间；本轮重启和 v1 迁移测试通过。保存时间超过 `2^53` 时的现有启动测试通过，但实现是在第一次取最大值时建立基准，并非每次清理验证全部保存时间；负值、部分记录损坏等也不是完整的保守故障检测。规范已把本机数据库改写排除在保证外，不把这些可直接删库的情形另报攻击。旧 v2 的 `stored_ms` 含义本轮改变、schema 版本未变；旧算法已经可能使墙上时间差大于真实年龄，因此“取旧最大值继续计时就不会提前清理”不具一般性证明，应标记迁移／重置未知年龄，或明确不支持旧开发数据库。

**严重程度与置信度：中／已确认。** 有真实双连接、真实经过时间的失败测试；90 天情形是同一算法的逐步推导。没有秘密泄露证据。

**建议：** M1 可选择最简单的数据库独占所有者，并让进程内全部 Store 引用同一个时间状态；跨进程也要排他。若要支持多个计时者，需在同一时序协议中分配保存时间和清理水位，不能各自缓存旧最大值后相加。不能简单改成每次“数据库最大值 + 本实例已运行时间”，那会重复累计。

**是否阻碍冻结：** 阻碍原样冻结 §7.2 的承诺。单一所有者的规范前提要先写明，具体锁和迁移可以在 M1 实现；不必改变共享密文字节。

### J2．中：大小策略仍不闭合，重建也不是失败原子的操作

**位置：** `spec/revisions.md` §5.2–§5.4、§6、§7.1；`crates/keevo-format/src/item.rs:247`、`:282`、`:298`；`crates/keevo-core/src/vault.rs:560`、`:613`、`:640`；`crates/keevo-store/src/lib.rs:76`、`:400`。

**A．上限之内，保留键仍可能无法精简。** “4096 个键，每键只剩一个墓碑，约 6.3 MiB”的算术估算是合理的；问题是操作不一定能把每键变成一个墓碑。`attr:purged` 的当前版本和并发版本都允许为恢复墓碑。它们可以值相同、没有字段冲突，但仍须作为极大元保留。`settle_for_write` 只处理没有当前版本的键；对已有当前墓碑的 purged 不操作。`resolve` 和 `delete` 则一律拒绝该保留键。

可以构造如下合法因果关系，无需篡改认证数据：

1. 初始条目 A 上，永久删除 D 和普通编辑 E 并发。
2. 多个分支都看到 D、E，写时确认恢复，分别产生 `R_i`：各自写入 purged 的恢复墓碑，普通字段沿用 E。这些 `R_i` 互不为祖先。
3. 以每层不超过 4096 个父的合并修订逐层收敛；已有 purged 当前墓碑，普通编辑不会替它清除并发恢复墓碑。取两个末端头，每个携带 130,000 个互不覆盖的恢复墓碑和共同当前版本、共同普通记录；每个详情仍小于 16 MiB。
4. 合并两头后，极大元就是这两组的并集。头数仅 2，键数仅 2，按 §7.1 应属“精简总能成功”的范围。
5. 删除共同普通记录后，purged 的 260,000 个并发墓碑仍在；客户端无法 resolve／delete 它，settle 也不改变它。

`r4_reserved_tombstone_concurrency_must_be_compactable` 独立验证了两个输入各自能 `encode_for_write` 和 `decode`（各 **8,840,253** 字节），并集状态经过 settle、删除普通键后仍为 **17,680,228** 字节，得到 ItemTooLarge；处理 purged 得到 ReservedKey。测试直接构造已由极大元规则确定的结果，没有运行 26 万节点的完整图合并；上面的分层图是对其可达性的推导，不宣称进行了该规模的性能测试。

这一状态可尝试重建为新条目，因此不是数据在任何工具下都不可恢复；它推翻的是“上限之内精简总能成功”，并暴露仅按头数／键数决定是否提供重建的缺口。大量恢复分支是很强的前提，不能写成日常发生概率很高。

**B．65,536 个墓碑父不是头数总上限。** 每个分支都只有一个父，仍能累积 65,537 个兄弟头。Store 没有禁止它，规范也没有对象头总上限。`r4_tombstone_parent_cap_does_not_bound_heads` 在内存数据库逐个插入这 65,537 个头，全部成功；以全头为父写墓碑则得到 **TooLarge**。这项测试验证存储元数据边界，不把测试中的占位密文当作经过加密验证的内容；把各行替换成各自独立认证的小条目修订，不改变父数量结论。

`purge_item` 必须一次以全部头为父，所以旧条目此时不能按现有 API 永久删除。`rebuild_item` 即使先成功复制当前值，也会在这一步失败。提高上限只能推迟反例，不能证明“总能”。分批删除是否接受、如何处理中途失败和迟到编辑，必须成为规范中的新操作；不能称其为不改变语义的分组合并。

**C．重建复制和删除分两次提交。** `rebuild_item` 在 `vault.rs:655` 提交新对象，随后 `:656` 才删除旧对象。`r4_failed_rebuild_does_not_leave_an_unreported_copy` 在临时数据库用触发器使墓碑插入失败；rebuild 返回 Err、没有交回新 ID，但对象数已从 **1 变为 2**。普通 I/O 失败也可能落在这两个提交之间；重试会继续复制。这不是秘密泄露，但界面不能把该 Err 理解为操作完全没有发生。

**影响：** 强前提下的保存／删除可用性问题，且当前重建失败会留下未返回 ID 的副本。没有静默丢弃未解决版本的测试证据，也没有无密钥伪造合法修订的证据。

**严重程度与置信度：中／已确认。** A 的文档与操作边界、B 的存储边界、C 的故障提交结果均有实测；大图可达性用上述构造论证。C 单独的影响较低，不另上调级别。

**建议：**

- 明确精简可在用户确认下把全部已恢复的 purged 墓碑因果覆盖为一个新的恢复墓碑，或者把这类状态明确纳入可重建范围；保留纯合并不得丢极大元的规则。
- 对任意头数定义一个有终止性、可恢复的删除／重建协议，或在接收规则中规定可执行的硬边界及超限导出／恢复行为。若选择限制头数，要说明到达顺序、同步拒绝和恢复，不可让合法远端版本被静默丢弃。
- 新对象及旧对象墓碑在一个事务中提交；若不能原子提交，需持久化重建任务／新 ID，并提供可恢复的部分成功结果。仅在复制前预检父数仍不能处理随后发生的 I/O 失败。

**是否阻碍冻结：是。** 容量策略和超限删除语义须先定稿；事务实现可在 M1 补，但不能把尚未决定的操作语义留给冻结后自行发明。

### J3．中：写入校验漏掉记录键名称，普通编辑可以保存无法再读取的条目

**位置：** `spec/vault-format.md` §2 名称限制；`crates/keevo-format/src/record.rs:66`、`:286`、`:301`；`crates/keevo-format/src/item.rs:162`、`:205`；`crates/keevo-core/src/vault.rs:878`。

**问题与前提：** 反序列化 RecordKey 会检查名称，但公开的 `RecordKey::Tag(String)`／`Attr(String)` 构造不检查。新加入的 `encode_for_write → validate` 只验证值、并发结构、保留键和键数；没有再检查名称。这条路径也可经公开的普通 `Edit::AddTag` 到达，无需直接修改 ItemDoc 的内部映射。

**复现：** `r4_invalid_tag_must_not_create_unreadable_revision` 创建一个正常条目，然后执行 `update_item(item, [Edit::AddTag("")])`。保存返回 **Ok(())**，随后 `item(item)` 解密后的 JSON 不能通过 RecordKey 解析。`r4_write_boundary_validates_record_key_names` 也确认编码成功、解码失败。超过 256 字节的标签及不合法属性名走同一缺少验证的路径；该测试在空标签断言失败时停止，对其余名称不冒称已经逐个运行成功。

**影响：** 错误用户输入或调用者输入可使条目最新头无法打开、编辑、精简或经依赖 `item()` 的重建接口恢复；旧修订仍在，不能据此声称全部历史永久丢失。未证明现有 SwiftUI 已暴露空标签输入，但公共核心接口确实持久化了不符合自己读取规则的数据。

**严重程度与置信度：中／已确认。** 这是本次补“写入边界验证全部不变量”时仍遗漏的旧路径，不是声称本提交才新增了 AddTag。

**建议：** 让 RecordKey 有统一名称校验；set、delete 和 encode_for_write 对 records／concurrent 的所有键均使用它，包括无值墓碑。即使使用受限构造器，持久化边界也应复核。错误必须在写入新修订之前返回。

**是否阻碍冻结：不要求改现有格式条文，可在 M1 修复实现；但修复前不能把写入符合性标为通过，也不应处理真实数据。** 若打算改变名称的接受范围，则应在冻结前决定，而不是顺应当前意外接受的非法写入。

### J4．低：合法记录和候选响应可能超过单条 Noise 消息容量，IPC 未定义处理方式

**位置：** `spec/vault-format.md` §1、§2.3；`spec/ipc.md` §2、§5.2；`crates/keevo-crypto/src/noise.rs:19`、`:308`；`crates/keevo-ipc/src/service.rs:560`。

**问题与前提：** 记录值允许 256 KiB，IPC 外层帧允许 1 MiB；实际每条 Noise 密文最多 **65,535** 字节，减去 16 字节 tag，应用 JSON 明文最多 **65,519** 字节。服务把完整响应一次序列化后交给 `Transport::encrypt`，没有分页／分片。外层 1 MiB 是上限，不是每条 Noise 都可承载 1 MiB 的保证；规范缺的是应用如何处理两层容量差。

**复现：** `r4_legal_record_size_must_fit_fill_response` 完成正常配对，让已授权到后端的 fill 返回 70,000 个普通 ASCII 字符作为密码。其字段编码远小于 256 KiB，响应也远小于外层帧上限，但服务返回明文控制错误 **bad_request** 并关闭连接。大候选列表存在同一序列化路径，未另行实测其数量阈值。

**影响：** 合法保存的数据不能自动填充，合法查询可能被错误判作协议错误。没有绕过认证或泄露秘密；主要是可用性和跨实现契约问题，旧实现中已经存在，因本轮冻结前整体检查而列出。

**严重程度与置信度：低／已确认。** 单条 fill 反例有实测，候选列表影响为相同代码路径的推导。

**建议：** 明确三层限长和输出错误；决定只支持有界 fill／候选列表，还是增加分页或分片。分片必须有明确的请求关联、顺序、终止、总长和失败行为，不能仅在底层把一个 JSON 随意拆成多个 Noise 帧。若选择不支持超大自动填充，要写出可识别的结果及手工取用路径。

**是否阻碍冻结：是，限于 IPC 应用消息契约。** Noise 套件及现有握手字节无需因此改变；是否增加消息字段必须在消息格式冻结前决定。

### J5．低：只在第一条 XX 消息检查锁定，确认时没有复核

**位置：** `spec/ipc.md` §4.2 第 6 步；`crates/keevo-ipc/src/service.rs:294`、`:383`；`crates/keevo-service/src/server.rs:204`。

**问题与前提：** 首帧在解锁状态下通过，之后保险库锁定，确认回调仍返回 true。第三帧处理和 `confirm_pairing` 不检查锁定，服务等待确认期间也不持有 vault 锁；回来时只锁 pairings。内存／开发文件存储能够继续保存配对。

**复现：** `r4_lock_during_pairing_must_prevent_save` 在收到第二条消息后把后端锁定，继续送第三条消息；状态机仍输出 ConfirmPairing。确认后保存记录并进入 Established。不是重复报告“正式加密配对数据库未实现”，而是验证本轮刚加入的“只在解锁时配对”边界没有覆盖中途锁定。

**影响：** 锁定时产生新的配对授权记录，与规范生命周期不一致。会话内非 status 请求仍返回 locked，所以没有证明能读取锁定保险库的秘密。实际 UI 是否在锁定时自动关闭确认、正式存储是否会拒绝，是本轮没有实现可验证的附加条件，不能假定它们已经补上状态机的检查。

**严重程度与置信度：低／已确认。** 状态机行为已运行；完整生产 UI 下能否发生仍待集成验证。

**建议：** 锁定时取消待配对；确认提交前，在与锁定转移一致的锁／解锁代次下复核，并让配对保存事务使用这个状态。仅检查当前布尔值还应考虑“锁定后又解锁”的旧对话是否允许继续。沿用现有拒绝错误即可，不需要新增握手字段。

**是否阻碍冻结：不阻碍已有握手和消息字节；M1 完成配对生命周期前必须修复。**

### J6．低：本机重包的逐文件改名不满足声明的失败原子性

**位置：** `spec/crypto.md` §8.6 的 `device_id` 变化与重新包裹顺序。

**问题与前提：** 规范要求“全部新包裹写临时文件、fsync、改名替换，最后写设备标记”，并承诺“中途失败时旧文件保持原样”。多个文件分别 rename 不是一个事务；该承诺不由这个顺序保证。

**可逐步复现的推导：** 初始 AUK、SK、Noise 包裹与设备标记都绑定旧 ID D。已取得明文后生成新 ID D' 的临时包裹；先把其中一个改名覆盖旧文件，随后在替换第二个文件或最后设备标记前失败／进程退出。磁盘此时同时含 D' 包裹、D 包裹及旧标记。第一份旧包裹已经被覆盖，并未“保持原样”；用旧 ID 验证新包裹会失败，而格式没有保存逐文件 AAD 所属代次。无须攻击代码，也没有依赖一次尚未运行的 Secure Enclave 实验来确认这一文件提交事实。

**影响：** 异常退出后可能额外要求应急包、主密码，或者误触发服务身份／设备身份重新生成；是否完全无法恢复取决于保留的旧 ID、备份和材料，没有据此声称全部保险库不可恢复。

**严重程度与置信度：低／已确认**（所写提交顺序不具有所承诺的原子性）；实际平台恢复后果仍有待实现和故障注入。

**建议：** 使用完整的代次目录／manifest 和一次提交指针切换；明确旧／新 device_id 的引导来源，保留上一代直到新代可验证，并定义崩溃后选择和回滚。或者明确允许混合代次并把每份包裹所需的 AAD 身份外显存储、认证和恢复；这也需要独立本机版本。逐文件 fsync 不能替代多文件提交设计。

**是否阻碍冻结：不阻碍拟冻结的共享格式。** 作者把 §8.6 排除是正确的；本项必须在该本机格式 M1.1 定稿前解决，不把其未实现本身另算漏洞。

### J7．建议：规范编码的主要缺口已补，但接受集合仍不能仅凭规范重现

**位置：** `spec/vault-format.md` §1–§3；`crates/keevo-format/src/item.rs:122`、`:176`；`record.rs:112`、`:147`；`json.rs:38`。

**已成立：** 记录值的对象字段次序、UTF-8、控制字符转义、小写十六进制、无空白、整数输出、墓碑 `null` 与 val 缺省的关系已经足以解释被测规范编码。r3 的七种值逐字节测试全部通过。无需为了采用 RFC 8785 而改掉这一固定模式。

**已确认的差异与空白：**

- 文档示例及结构是 JSON 对象，但 Serde 的结构体反序列化也接受 `[1,"login",{}]` 作为完整 ItemDoc。独立对象 schema 实现会拒绝它，当前 Rust 接受。
- 标签规定为字符串 `"tag"`，实际也接受 `{"tag":null}`。r4 分别运行了这两个拒绝断言，均失败。
- `purpose:null`、`section:null` 被接受，并在重新编码时省略；规范只明确 val 的 null／省略等价，其他可选字段需要明确同样还是不同处理。
- Rust 将 `{"int":-0}`、`0.0`、`0e0` 归为结构错误，而“所有整数范围 ±(2^53−1)”并没有确定收到这些 JSON 数字词法时的规则。只采用数学上的整数判断与只接受整数字面量会有不同接受集合。
- 对 `2^64`，解析在到达范围校验前失败，返回 **Malformed**；规范写的是整数越界 **ValueTooLarge**。错误差异是实测，不是安全整数范围已经被绕过。
- 示例不足以代替完整字段表：例如概要中缺失 conflicts 的缺省、不同文档的 required／nullable、嵌套结构是否必须为对象，都应在同一处列清楚。数组内容应按解析后的原顺序保留，不能由另一实现猜测是否排序。

**影响：** 另一语言可能拒绝 Rust 接受的文档，或采用不同错误与默认语义。没有证明这些别名能够绕过密文认证、制造密码碰撞或破坏当前同一 Rust 实现的比较确定性。

**严重程度与置信度：建议／已确认。** 这类接受集合和错误差异主要是冻结前的格式符合性问题，不夸大为已利用的安全漏洞。

**建议：** 增加规范性 schema／语法表和每种可选值的映射规则。建议拒绝没有必要的结构体数组和枚举别名，而不是把 Serde 的便捷表示带进长期格式；如果选择接受，则必须完整写明它们向规范值的映射。定义负零、指数、小数、超大整数、无效 Unicode 和未知字段的错误优先级；补跨语言的正负向量。生产编码器也要满足 J3 的写读闭合性。

**是否阻碍冻结：是，限于尚未明确的接受规则。** 已明确规则上的实现 bug 可在 M1 修复；不能把“今后读 Rust 或看某个测试才知道”作为冻结规范的一部分。

### J8．建议：拟冻结范围还包含会在 M1 决定的格式，版本政策与冻结定义冲突

**位置：** `spec/README.md` §规则；`spec/crypto.md` §8.2、§11；`spec/vault-format.md` §2.3–§2.4、§5–§7；`spec/revisions.md` §10；`spec/ipc.md` §1、§7。

**问题与依据：**

**影响：** 如果按原提议宣布全量冻结，后续团队可能被迫在“不兼容但仍叫 v1”和“第一次发布前就迁移”之间临时选择。这里没有密钥泄露攻击；是冻结清单尚不自洽。

**严重程度与置信度：建议／已确认。** 文档中当前存在的矛盾已确认；附件等未来一定会采用哪种布局没有定稿，不能断言所有可行方案都必然改变共享信封。

**建议：** 发布一份明确的格式清单，逐项列出 wire version、字段语义、保留编号、允许的扩展和迁移责任。当前范围可以是 Secret Key v1、KDF v1、Keyset v1、Envelope v1、当前 Vault／Item JSON v1、已定稿的合并规则和浏览器 IPC v1；排除的功能明确使用独立格式，或承认将来需要 v2。把各 M1 对象／part 的上下文赋值列成表。按站点授权、正式配对数据库和本机包裹可以在不改变现有浏览器握手的情况下完成，不应与附件等尚未定义的格式混在一起。

**是否阻碍冻结：是，必须先明确边界。** 不要求把所有 M2／M3 功能提前实现；要求停止把它们未定义的格式包含在冻结承诺中。

### 5.1 字节层面已核对的对应关系

| 内容 | 规范与实现的对应关系 |
|---|---|
| Envelope | `version(1) ‖ alg(1) ‖ kid(16) ‖ nonce(24) ‖ ct/tag`；头 42 字节。AAD 为 ASCII 标签、头前三字段、type／part／index、account／vault／object／rev、binding，合计 132 字节。独立向量一致 |

### 5.3 H8 概率界限的独立复核

在文中理想化前提下，固定一次诚实扩展尝试，攻击者与之比较的服务端贡献为 Q_s 个。对每次新的比较，另一侧未预测的贡献使 48 位 SAS 命中概率约为 `2^-48`；联合界为 `min(1, Q_s / 2^48)`，再加密码学假设失效项。若两侧分别可观察 Q_s、Q_e 个结果，候选配对至多 Q_s·Q_e，保守联合界为 `min(1, Q_s·Q_e / 2^48)`。当 Q_s=Q_e=10 时为约 `3.55×10^-13`。这些是条件化的机会计数，不是把 HKDF 输出无条件视作严格独立随机变量的完整密码学证明。

第 1 条消息前固定了承诺和发起方贡献；第 2 条服务端贡献生成前攻击者不能知道该段最终 SAS。第三条 nonce 和显示名字节均已承诺，静态公钥也在承诺中；固定消息状态下，第三条 Noise 密文没有 JSON 重编码自由度。nonce、临时密钥的新鲜性、承诺隐藏／绑定、握手哈希和派生的安全性，以及可信界面完整比较 48 位，都是必要前提。显示名只是标签，清洗前承诺／清洗后显示不会替代 SAS 校验。

`PairingGate::begin` 在生成第二条消息前计数；断开、失败和 Drop 只释放 active，不退还 starts。本轮跨连接测试没有找到免费取得第二个贡献的路径。`confirm_pairing` 在保存前释放 active，但调用方此时仍持有 pairings 锁，新的服务请求也要取得它；即便开始下一次尝试，它仍必须经过 begin、增加 Q_s，不是未计数贡献。计数的是服务状态机开始处理的完整首帧，不是 socket accept。

普通本机计数文件不能给 A7 提供跨重启、抗回滚的可信限频，作者选择只承诺单次运行内预算是可以接受的产品边界；“任何持久化都没有用”则过于绝对，持久化仍可约束普通重启，只是不等于防攻击者回滚。用户可见性和扩展不自动重试有帮助，但不构成跨任意重启的 Q_s≤10 保证。§6 必须与 §4.2 同步；正式 UI、跨实现握手和完整自适应多会话证明仍见下一节。

## 6. 仍未覆盖的部分

- **没有把四轮模型评审视作独立人工评审或形式证明。** 已确认项有测试或明确推导，未找到反例的部分只在列出的输入域内成立；项目不再安排人工评审是本轮背景，不会增强证据本身。
- **完整 Noise 独立实现和多会话自适应证明。** Rust 双端共用 snow／协议库。未做 48 位碰撞搜索，未证明真实用户在重复提示下的核对行为，也未独立生成完整 XX／IK 握手向量；现有 Python 向量只覆盖共享密码格式，不覆盖 IPC、本机包裹、JSON 合并。
- **真实 90 天、睡眠、跨进程数据库所有权及旧 v2 各种来源。** 双 Store 用真实短时长复现，不是等待 90 天；未进行 Mac 睡眠／唤醒实验。规范要求排除睡眠时，实现必须选择和验证满足该要求的目标平台时钟，不能仅因类型叫 Instant 就宣称跨平台行为已验证。旧 v2 的保守迁移未获得一般性证明。
- **大修订图资源复杂度。** 65,537 个头的存储实验已运行；26 万个恢复墓碑实验验证两个头的文档边界与精简操作，没有运行完整图合并。总头数、图规模、并发版本数与规范比较的总开销仍无完整性能预算；可在不改变既定语义下优化遍历／缓存，但不能用静默截断来解决。
- **M1 的 UI 与正式授权数据库。** 未验证 Touch ID、确认对话到期、锁定代次取消、待提交撤销的重载顺序、站点授权、频率限制、真实两端名称展示。本轮验证内存／开发文件行为，不把它们当成生产授权存储。
- **本机包裹生产格式和恢复。** 字段结构审读完成，缺原生实现、固定向量、指纹变化／锁屏／用户取消／崩溃恢复矩阵。J6 是提交规则的推导，不是一次已经执行的 Secure Enclave 故障实验；前两轮的平台实验没有在本轮全部重跑。
- **发布与更新完整性。** 没有新的正式应用包、helper cdhash 嵌入、Sigstore 发布证明或更新过程可验。ADR 本轮未改，继承前轮已明确的风险边界，不能据此宣称真实分发／Gatekeeper／受管设备流程通过。
- **未改动功能没有重新全面评审。** 网址匹配、root／注入等明确非目标、已列明的依赖清零缺口不作为本轮新发现；M2 接收验证、同步日志、墓碑回收和签名设备日志未实现部分也没有重新按“缺功能”报漏洞。若它们需要改变冻结范围，则应按 J8 单独版本化。

## 7. 给作者的问题

以下决定需要作者在规范定稿时明确。

1. **同一个数据库是否只允许一个 Vault／Store 所有者？** 若是，跨进程由哪一层强制，所有计时者如何共享原点？旧开发 schema v2 是明确不支持，还是要保守迁移其 stored_ms？
2. **如何处理 purged 当前墓碑下的大量并发恢复墓碑？** 是允许精简内部因果覆盖它们，还是在这种状态也提供重建？这个操作与“保存即确认恢复”的 UI 语义如何衔接？
3. **超过 65,536 个头后，旧条目的永久删除方案是什么？** 若选择分批墓碑，是否明确接受它作为多次删除操作，并规定迟到编辑、故障恢复和到达顺序行为？重建副本与旧条目墓碑能否同事务提交？
4. **v1 是否明确拒绝结构体数组和 tag 对象别名？** purpose／section／概要可选字段的 null、-0／指数／小数字面量，以及超过 i64 的整数，应分别返回什么？这是接受集合的决定，不能只交由语言库缺省。
5. **M1 是否必须自动填充超过单条 Noise 明文上限的凭据，并完整返回超大候选列表？** 若必须，分页／分片现在如何定义；若不必须，是否明确有界失败及可识别错误？
6. **冻结清单是否明确排除附件内容／引用、CLI 授权和未定事件？** 若这些仍属于 M1，如何保证不改变已冻结接受集合；否则是否接受独立版本和迁移？排序键生成算法是否保证与旧十进制字符串同域、保留字节序？
7. **本机包裹的代次和提交点是什么？** 旧 device_id 从何处取得，多份包裹混合代次时如何恢复，哪一次原子切换宣布新身份生效？这只需要在独立本机格式中解决，不应反向改写已有共享修订身份。
8. **配对中途发生锁定／再次解锁后，旧确认是否还有效？** 正式实现能否取消该对话并在同一解锁代次内提交配对？保存失败的错误、重新配对与待提交撤销的先后规则应一并明确。
