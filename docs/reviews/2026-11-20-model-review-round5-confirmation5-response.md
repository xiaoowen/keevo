## R1：没有完好的一份

**做法**：这一次按份数把阻塞标准（至少两份、最多 3 处改动，基础片段不超过 64 个字符）的全部情形分开，逐一说明由哪种候选覆盖，而不是只修这个反例。

| 份数 | 改动的分布 | 基础片段从哪里来 |
|---|---|---|
| 五份以上 | 3 处改动最多破坏 3 份，总有完好的两份 | 出现次数最多的片段（原有） |
| 四份 | 总有完好的一份 | 每一份所在的位置（原有，Q1） |
| 两三份 | 有完好的一份 | 同上 |
| 两三份 | 每一份都有改动，改在不同位置 | **新增**：基础片段夹在第一份与另一份之间。求两份的对齐，每处差异取其中一份的字符，枚举全部组合 |
| 两份 | 两份在同一位置都被改动 | **新增**：那个位置的字符两份都没有，逐个尝试常见口令中出现的字符（小写字母、数字与 `@$!#*._-`；大写字母改成小写只会让估计更低） |

三份时如果每一份都有改动，每份正好一处。两份改在同一位置时，第三份在那个位置是完好的，所以第一份与第三份之间仍能还原。

**基础片段超过 64 个字符**：不在这张表的范围内。这样的片段如果本身估计很低，它自己就是高度重复的，会被更短的周期或 LZ 分解覆盖。这一点是论证，不是枚举证明。

**性能**：新增的两种还原都需要逐个估计基础片段，debug 构建下很慢，所以只在需要时进行。
- 这类解释每一份都有改动，至少两处，代价至少 2 × (n × 95)² > 10⁶。它不会让密码落到弱密码（0–1 分）或主密码的下限（2 分）以下，只可能影响能否导出（4 分）。
- 因此只在其他估计仍在最高档时才还原；逐个尝试字符的那一步，一旦低于门槛就停下，能否导出已经确定。
- 它的代价是：这一类密码在 2 分与 3 分之间的显示，可能比更精确的估计高一档。这不影响任何判定。
- 逐个尝试字符只用于正好两份：三份时，第三份在那个位置是完好的，从差异中还原就够了。
- 已经找到的周期的倍数不再作为还原的候选：同一个解释，基础片段更长、代价更高。
- 用来还原的两份，差异不能超过一半。两份同一个基础片段只在少数几处不同；任意两段随机字符几乎处处不同。没有这一条，很短的片段总能"配上"，每个强口令都要做一遍还原：安全检查 1 万个条目一度要 247 秒，加上这一条后是 1.84 秒（此前 1.7 秒）。

release 构建下，这一类最慢的输入（按模型本来就在门槛之上，还原要全部做完）不超过 30 ms，打字时实时计算强度没有问题。debug 构建下慢 10–30 倍，所以我的变体族回归中，"模型上限"那一部分只取一个代表；评审的 2,336 组对照在 debug 下约 22 秒。
