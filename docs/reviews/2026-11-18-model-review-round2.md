# Keevo v0.2 规范第二轮独立评审

## 1. 评审版本与总体结论

**评审提交：`d3d2faf793fda3e587f850fa578b5a7c08584ecd`。** 开始及写报告前均运行 `git rev-parse HEAD` 核实；首轮基线为 `35c649b5bedeb3b5a95d1caf5e09af214a5ce283`，审查了 `git diff 35c649b..d3d2faf` 的 47 个文件。本报告的源码行号全部指 `d3d2faf`，不指临时副本追加测试后的行号。

**v0.2 暂不适合作为 M1 的基础冻结格式。** 普通记录的多值保留、请求前复核配对、密码学信封内部的长度检查已经改善，但配对承诺仍遗漏可改变 SAS 的消息编码，对象墓碑仍有分组合并反例，并发版本还可能让合法条目无法重新写入单个信封。历史保留在旧 schema 迁移和本机时钟前跳时也不能兑现 90 天承诺；ADR 的方向可以实现，但启动信任、配对记录保护和 Library Validation 的说明需要纠正。没有确认无需凭据解密保险库的攻击，也没有完成实际的 48 位 SAS 搜索；以下不把论证缺口等同于已经泄露秘密。

冻结前至少应完成：

1. 固定配对第 3 条消息的唯一编码或承诺其完整原始负载，重新给出包含尝试次数的 SAS 安全界限（G1）。
2. 决定对象删除信息如何参与可持久化合并状态，明确纯合并与写入恢复操作的不同语义，补上本文反例（G2）。这可能改变修订格式，不能留到冻结后解释。
3. 明确并发状态超过信封上限时的无损表示或拒收、隔离与恢复策略，以及每对象的资源预算（G5）。不能通过静默丢弃并发值满足长度限制。
4. 确定迁移时间和时钟异常的历史保留规则，补齐现有数据库读取入口的大小检查（G3、G4）。
5. 统一 ADR 与 IPC 的信任根、更新生命周期和授权记录保护要求，并把“规范 JSON”、缺省值及并列决胜规则写成跨实现可执行的规则（§4）。

已有加密信封的字节布局与 2SKD 不因本轮结果而需要重设计；这一判断不等于批准把整个 v0.2 协议、修订状态和发布方案一起冻结。可以继续 M1 原型开发，但应保留上述格式调整空间。

### G1．中：配对承诺没有约束第 3 条消息的编码，概率论证仍不成立

**位置：** `spec/ipc.md` §4.2，尤其第 119–123 行；`crates/keevo-crypto/src/noise.rs:26`、`:34`、`:273`；`crates/keevo-ipc/src/service.rs:358`；`crates/keevo-ipc/src/client.rs:155`。

**问题与前提：** 主动中间人可充当一段 XX 的 initiator，选择合法的第 3 条负载。承诺输入是固定标签、32 字节公钥、32 字节 nonce、最后的原始名称 UTF-8，**这个字段拼接本身没有长度歧义**；问题在于 JSON 被解析后才核对承诺，而 Noise hash 包含实际发送的密文字节。键顺序、空白、等价的字符串转义没有被承诺，也没有被接收端拒绝。

**复现：** 令 `N` 为同一 32 字节 nonce 的无填充 base64url 编码。分别发送下面两个第 3 条负载：

```json
{"name":"Chrome","nonce":"N"}
```

```json
{ "nonce" : "N", "name" : "\u0043hrome" }
```

其中 `N` 应替换为实际编码，不是字面单字符。两个名称解析后相同，公钥与 nonce 不变，故承诺相同。`r2_commitment_accepts_different_json_encodings` 确认服务对两者都输出配对确认；`r2_same_commitment_same_prefix_different_sas` 进一步固定双方静态密钥、临时密钥，确认第 1、2 条消息逐字节相同，而第 3 条编码和 SAS 不同。固定临时密钥仅用于临时测试，不修改公开生产 API。

这给攻击者在收到服务第 2 条消息之后留下离线候选空间。无需实际回滚诚实服务：攻击者可在自己的握手状态上计算候选，最终只发送一个选择后的第 3 条消息。测试验证的是这一自由度，不是完成整条中间人攻击。

**概率分析：** 对一个已经固定的目标 SAS，若可计算 `q` 个不同 transcript，并假设其 48 位输出近似独立均匀，命中概率为

```text
P = 1 - (1 - 2^-48)^q ≈ q / 2^48  （q 远小于 2^48）
```

只有 `q=1` 才得到规范所写的单次 `2^-48`。如果两侧候选都可以筛选，必须另外分析其依赖关系，不能未经证明就套用单目标界限，也不能把本测试直接宣称为已经实现生日攻击。60 秒限制了可投入的计算和网络时间，没有把 `q` 数学上变成 1；本轮没有测量 60 秒内的搜索吞吐量。

另一个独立的论证错误是“每次尝试都会产生用户可见请求”：`service.rs:386` 到收到有效第 3 条消息才请求确认。发送第 1 条、接收第 2 条后中止的试探不可见。即使修复 JSON 编码，也应把服务端贡献被采样的次数计入总优势，而不是只数弹出的确认框。

**影响：** 不能依赖当前承诺得到“每次用户配对误接受概率不超过 `2^-48`”的结论。没有证据表明现有硬件在规定时限内可以高概率骗过完整 SAS 比较，不能据此声称实用破解。

**严重程度与置信度：中／已确认**（编码自由度、可见性与现有概率论证失效）；**实际可利用的完整中间人攻击仍是疑虑**，缺少搜索成本、并发调度与真实 UI 验证。

**建议：** 优先让第 3 条使用唯一、严格拒绝别名的字节编码，或在第 1 条承诺公钥及完整原始第 3 条负载；两端严格检查相同规则。论证需显式写出：nonce 与临时密钥每次新鲜、不可预测且不重用；承诺的隐藏性和绑定性；所有后发可变字节均受约束；SAS 派生的伪随机假设；可信两端完整比较所有 48 位；并发、失败、中止与重试的计数边界。对最多 `Q` 个独立可筛选候选给出约 `Q/2^48` 加密码学失效项的界限，而不是以 UI 一次操作替代密码学尝试次数。新标签与既有用途没有发现域分隔碰撞。

名称清洗与时限的附带判断：承诺原始名称、保存清洗名称**不产生承诺绕过**，但不同原名可显示为同一名称。双方应显示同一清洗结果，明确按 Unicode 标量还是用户感知字符截断，处理双向格式字符；名称不能替代 SAS。时间从第 1 条而非握手完成起算是正确方向；当前代码实际在解析并生成第 2 条后设置 deadline，通常只相差握手处理时间，建议在接收首条时记录。仍需给 socket 读写和确认 UI 传递同一截止时间，以释放空闲会话，而不只是拒绝迟到输入。

### G2．中：对象墓碑未进入持久化合并状态，两个例外不能挽救结合律声明

**位置：** `spec/revisions.md` §4.3、§5.2–§5.4；`crates/keevo-format/src/merge.rs:132`、`:148`；`crates/keevo-format/src/item.rs:245`；`crates/keevo-core/src/vault.rs:525`。

**问题与前提：** 普通记录确实保存全部极大元。对有限有效 DAG、相同版本身份对应相同内容的记录集合，`Max(Max(A ∪ B) ∪ C) = Max(A ∪ B ∪ C)` 的理由成立：被丢弃元素的支配关系会传递。但对象墓碑不在这个集合里，`has_concurrent_record` 又只查看选中的当前非墓碑记录；因此不能把这个证明直接扩展到整个对象的存在性。

**对象墓碑反例：** 用下表构造图，标题的两个并发值满足 `HLC(W)=20 > HLC(A)=15`。R 可以是空文档；C 是保持 W 的后续修订。

| 修订 | 父修订 | 内容 |
|---|---|---|
| R | 无 | 基础文档 |
| W | R | 标题写为 W |
| D | W | 对象墓碑 |
| C | W | 仍携带写于 W 的标题 |
| A | R | 标题写为 A |

1. 一次合并头 `{D,C,A}`：当前标题为 W；W 是 D 的祖先，当前记录没有与 D 并发的修改，故返回 `doc=None`。落选的 A 虽仍是并发记录，也不参与这里的当前值判断。
2. 先合并 `{D,A}`：A 与 D 并发，返回存活文档 A；把这个存活结果写成 M，父为 `{D,A}`。
3. 再合并 `{M,C}`：W 胜过 A，但 D 已不是头，也没有被存入 M 的内容，故返回存活文档。

`r2_object_tombstone_grouping_should_preserve_deletion` 确认上述差异。中间写回的是**存活**结果，没有触犯“不写回已删除结果”的例外；最终差异是 `None` 与文档，不是 `resurrected` 提示。C 的不改标题可以对应保存操作；添加一个无关记录墓碑也不提供非删除的并发当前值，推导不依赖恶意数据或密钥伪造。

**回收站还需要区分纯合并与写入：** 另构造 R 的两个分支：D 写 `trashed=30`；A 改标题。C 是 D 的后代，再改标题且 HLC 胜过 A。

- 完整头 `{A,C}` 的胜出标题来自 D 的后代 C，仍在回收站。
- 先看 `{D,A}`，回收站被抑制并移入 `concurrent`；在此视图上写入 M 时，`settle_for_write` 为 `attr:trashed` 新增一个写于 M 的墓碑。之后与 C 合并，不再在回收站。

`r2_settle_for_write_is_not_a_pure_join` 确认差异。**这不单独证明新增恢复规则是错误的**：M 明确增加了一个恢复操作，输入操作集合已经改变。它证明 §5.3 不能把实际写时收敛一概称为不改变语义的结合运算。作者随机测试的编辑阶段调用了 `settle_for_write`，但第 384 行的“分组结合律”阶段没有调用它，这两类测试不能相互替代。

**影响：** 对象是否存在可以依赖中间合并是否写回；回收站状态还依赖隐式恢复操作是否发生。设备拿到完全相同的最终头集合仍可以算出相同结果，但这不等于不同分组历史具有相同语义。作者将首轮影响修正为“产品路径上自然发生”是成立的：用户可在只知道部分远端头时编辑，`Vault::revise` 随即持久化部分合并；不需要特意引入增量缓存。

**严重程度与置信度：中／已确认。** 这是持久化与删除语义问题，没有据此声称不持钥者能绕过 AEAD。

**建议：** 选择并规范一种模型：把对象删除／恢复也表示为可合并、可保留的因果状态；或显式限定“极大元结合律”仅适用于普通记录，并给对象删除定义另一套可验证语义。分别测试纯合并、带用户编辑的写入、写入触发的恢复。永久删除与未解决并发值的保留关系也须在 §7 明确，不能仅靠“对象墓碑视为不存在”的解释。补入确定性反例比继续增加同一生成器的随机种子更重要。

### G3．中：90 天历史保留对迁移数据和时钟跃变不成立

**位置：** `spec/revisions.md` §7；`crates/keevo-store/src/lib.rs:71`、`:400`、`:514`、`:615`；`crates/keevo-core/src/vault.rs:543`。

**问题与前提：** `stored_ms` 使用本机墙上时间，清理阈值也直接采用当前墙上时间减 90 天。v1→v2 迁移把所有已有行置为 0，代码注释承认仅按数量保留，但规范未给迁移例外。无需攻击者；升级、错误的系统日期及其纠正即可触发。

**复现：**

1. v2 内连续写入 25 个修订。用正常 `now−90天` 清理，删除 0 个；用 `now+1天` 作为截止值模拟当前时钟前跳 91 天，清理立即删除 5 个旧修订的内容。无需改变真实机器时钟。
2. 创建含 25 个既有修订的真实 v1 schema，设置 `user_version=1`，再运行当前 `Store` 初始化迁移。按正常 90 天规则清理，5 个既有修订内容被立即删除。

对应两个测试均以“应清理 0 个”为断言失败，实测均为 5。作者已有迁移测试不能代替这个含既有历史的案例。时钟恢复正常后被清理内容不会回来；单纯回拨通常延长保留，但在回拨期间写入、再校正时钟也可能使新内容突然过期。早于 Unix epoch 的时间被置为 0，同样不能支持无条件的实际经过 90 天承诺。

**影响：** 用户在声明的保留期内失去顺序覆盖旧值。正常时钟下的“最近 20 个 + 90 天”取并集和头修订豁免实现正确；问题不是远端作者通过 HLC 伪造年龄。

**严重程度与置信度：中／已确认。** 需要升级或时钟异常等前提；不是秘密泄露。

**建议：** 对迁移中年龄未知的内容保守赋迁移接收时间，或另存“未知年龄、暂不清理”状态。明确时间模型，结合持久化时间锚、运行期间的单调时间及异常跳变检测；出现不能证明已经足龄的情况时延后清理。跨重启绝对经过时间不能仅凭不可信墙上时钟严格保证，规范应坦诚写出前提，不要把改用本机时间等同于消除了时钟问题。

### G4．中：信封上限未覆盖现有数据库读取入口，KDF 预算不是进程级预算

**位置：** `spec/crypto.md` §5.3、§8.5；`crates/keevo-store/src/lib.rs:295`、`:551`；`crates/keevo-core/src/vault.rs:248`；`crates/keevo-ffi/src/lib.rs:168`、`:180`。

**问题与前提：** 不可信或损坏的数据库可到达本地打开、恢复路径。信封内部现在正确限制 `17,301,562` 字节，但 `Store::account` 和 `raw_revision` 先把 BLOB 读为 `Vec<u8>`；`Vault::open` 本身也会读账户。于是 `open()` 的拒绝发生在首次大块分配之后。这里审查的是已有 SQLite 入口，不是把尚未实现的同步入口再次列为缺失功能。

**复现：** 在临时内存数据库的修订中，把详情置为 `zeroblob(MAX_ENVELOPE_LEN+1)`，调用 `Store::revision`。`r2_database_envelope_size_should_be_checked_before_read` 断言应报错，实际返回包含整个 BLOB 的记录。测试只分配约 17 MB，未做耗尽内存实验；更大值沿相同读取分支处理。账户行的 `kdf_params`、`keyset_ct`，以及修订父列表也采用未经长度检查的读取。

**KDF 的独立边界：** 超预算返回 `KdfNeedsConfirmation` 的检查顺序正确；但 `&mut Vault` 和一个 `Mutex<Vault>` 只约束一个实例。FFI 的 `open_vault` 可以产生多个独立实例，并没有进程共享的 KDF 限流器。因而处理记录声称的“同一进程最多一次”不能由当前互斥锁推出。该结论来自 API 与锁作用域，不需要真的并行申请数 GiB 内存。

1 GiB、t=10、p=8 是有限格式内执行阈值，但不是经过验证的设备预算；仅 `m×t` 已约为默认 256 MiB、t=3 的 13.3 倍，不能直接换算成实测耗时。没有设备内存压力、延迟或全局并发约束时，不能称已完整解决拒绝服务；本轮不武断指定一个对所有 Mac 都合适的固定数字。

**影响：** 未认证输入仍可产生大块分配及重复昂贵派生。没有发现 KDF 参数单独篡改能使原密文在弱参数下通过认证，也没有发现新的低成本口令预言机。

**严重程度与置信度：中／已确认**（超长读取及并发约束作用域）；实际内存耗尽的规模未测量。

**建议：** 在 SQLite 列转换为自有缓冲区前检查长度；固定字段如 ID、29 字节 KDF 参数采用更小的专属限额，同时限制查询总量。规范的“数据库按文件大小限制”应改成“按单列信封和读取批次限制”，整个数据库当然可能超过一个信封。为自动 KDF 引入进程共享限流与设备校准预算，显式区分受信配置和未认证读取。未来确认 UI 应确认具体参数快照，避免确认后重新读取另一套更昂贵参数。

### G5．中：合法并发版本的合并结果可能超过可写格式上限

**位置：** `spec/revisions.md` §4.3、§7；`spec/crypto.md` §8；`crates/keevo-format/src/merge.rs:103`、`:197`、`:229`、`:267`；`crates/keevo-core/src/vault.rs:525`。

**问题与前提：** 每个输入信封都可合法解密，但每对象头数、每键并发版本数和合并后总大小没有预算。新的修复要求保留全部极大元，包括值相同而不提示冲突的版本；单个详情信封却仍只有 16 MiB 明文容量。这是组合后的格式可写性问题，不仅是给网络入口加单文件上限的问题。

**复现：** 同一根的 40 个并发修订各写一个 512 KiB 的相同 note，修订 ID 不同；每个文档都小于 16 MiB。合并后仍有 40 个版本，编码长 **20,975,138 字节**，公开 `seal` 返回错误。`r2_concurrent_growth_exceeds_serializable_limit` 实测确认。更少分支也能触发：两个各接近 9 MiB 的并发字段版本已足够超过单个信封上限，这是由长度相加得到的推导。

**影响：** 在该状态上编辑无关字段无法保存；用户必须先覆盖或处理造成膨胀的字段。值相同的版本按 §5.5 不显示冲突，更难解释为何普通保存失败。保留未解决版本的方向正确，但必须同时提供可写性和恢复路径，不能在满额时偷偷丢掉落选值。

修订图也没有总规模、父边数上限，且永久保留。每个头建立祖先集合有约 `H×(R+E)` 的遍历和最坏存储开销；每键候选的支配检测至多比较 `V²` 对，每次还可能遍历图。相同 `rev`、相同 HLC 的重复候选在排序比较时重复序列化完整值，即使值本来相同。这些是代码级上界，不是本轮测出的性能曲线；没有执行破坏性压力测试。“每个修订几十字节”只适合有限父数的紧凑表示，不能概括这些索引和内存对象。

**严重程度与置信度：中／已确认**（合法输入合并后无法写回）；超大图的实际拒绝服务阈值仍需基准。

**建议：** 在格式冻结前定义对象／字段／头集合的预算及超额状态，考虑内容寻址共享或独立存放并发版本；预算拒收也必须允许隔离、导出和无损处理。不要把一个合法并发值静默裁剪成“最近 20 个”。将祖先判断批量化、缓存重复值的规范编码，先比较版本和值是否相同，再做昂贵的排序决胜。用两个大分支、许多相同值分支和长祖先链分别测试。

### G6．低：从可替换的辅助程序建立 cdhash 白名单，没有定义启动信任根

**位置：** `spec/ipc.md:43`、`:46`、`:49`；`docs/adr/0003-no-apple-developer-team.md:46`；`docs/security.md` §1、A7。

**问题与前提：** 规范让服务启动时读取包内 host、CLI 的 cdhash，随即信任这些值。如果辅助程序路径可由同用户写入，而读取前没有锚定到可信主程序或已认证发布清单，攻击者只需替换其中一个辅助程序，下一次服务启动就会把替代物当作允许的对端。**并不要求替换主程序，更不等于向正在运行的 Keevo 注入代码。** 是否具备写权限取决于安装位置及所有权；规范没有限定只支持同用户不可写的安装。

**复现条件／推导：** 初始主程序可信 → 攻击者替换白名单来源路径下的 helper → 正常重启主程序 → 按 §3.1 从替代物读取 cdhash → 替代物满足新生成的要求。这个推导准确说明缺少认证来源的策略是循环信任；cdhash 读取器尚未实现，本轮没有声称攻破一个实际发布包。

同用户能替换整个应用确实可合理作为额外非目标，但 `docs/security.md:16` 实际列出的非目标是 root／内核、进程注入、硬件键盘记录及胁迫，没有 ADR 所引用的磁盘程序替换条款。应明确边界，不能用未写入的例外证明策略成立。

另一个确定的生命周期问题是：服务已缓存 H_old，更新器把包内 helper 更新成 H_new，而旧服务仍运行；H_new 被旧策略拒绝。反过来，在旧服务运行期间重新从新磁盘文件读取白名单，又扩大了它接受的版本集合。“一起更新，所以始终一致”需要协调退出、重启或版本化安装的前提。

**影响：** 按文字实现会削弱 OS 对端白名单，并可能在更新后拒绝正常连接。Noise 配对及原生站点授权仍是独立边界，本轮没有证明通过这一缺口读取未授权密码。

**严重程度与置信度：低／已确认**（规范缺失信任锚及更新前提的推导）；真实发布包中的替换可行性为**疑虑**，尚缺打包、安装权限与更新代码。

**建议：** 在可信主程序内固定或认证同版本辅助程序清单，或以已运行主程序的可信身份核验相应资源封印，而不是只相信当前磁盘路径里的签名；普通 adhoc 签名本身不认证发布者。定义安装权限、首次信任和升级／降级策略，更新时协调服务退出或使用版本目录。若明确排除包内任意文件替换，也应把这个前提写进威胁模型并说明本层只防任意外部二进制连接。

### G7．低：会话登记失败时没有关闭连接，撤销的主动断开保证不完整

**位置：** `crates/keevo-service/src/server.rs:132`、`:140`、`:146`、`:157`；`spec/ipc.md` §4.4。

**问题与前提：** `stream.try_clone()` 失败时 `register` 静默返回，原 socket 和 `Established` 状态继续工作，登记表没有这条连接。文件描述符压力可以触发该分支。

**复现：** 在独立测试进程把文件描述符上限设为 128；先完成握手、创建 socket 对，再打开 `/dev/null` 到新描述符分配失败；确认 `try_clone()` 失败，执行 `register`，然后 `revoke`。释放测试用描述符后，对端读取等待 50 ms 返回 `WouldBlock`，不是关闭后的 EOF。`r2_registration_clone_failure_should_close_connection` 实测失败。仅限制测试子进程，没有修改系统资源上限。

**并发边界核实：**

- 正常登记持有 sessions 锁后再查 pairings；撤销先删除配对、释放 pairings 锁，再遍历 sessions。这没有形成同时反向持锁的死锁：先登记会被撤销扫描到，先撤销会被登记复查挡住。两个顺序及 32 次同时开始的测试均通过。
- 请求处理在 `server.rs:132` 的 pairings 锁作用域内完成，撤销也取同一锁。因此请求与撤销有明确先后：先获得锁的请求可能已经读取并构造了响应；撤销完成后取得锁的新请求会被拒绝。这一点在当前服务中成立，不能仅凭状态机拿到一个任意 `&dyn PairingStore` 就宣称所有调用者自动拥有同样的原子性。
- 已经处理、排入发送路径或写入内核缓冲区的响应不能靠撤销收回，应在协议中明确线性化点。“撤销后不再授权新请求”与“用户点按钮后不可能再收到任何既有字节”是不同保证。
- 当前流程还在首次 `emit` 后才登记；阻塞写会延迟登记和复查。这个窗口本身没有证明可处理后续秘密请求，但不能支持所有情况下立即主动关闭。

**影响：** 资源异常时仍留有未登记、未主动关闭的连接。**每请求复查仍会阻止撤销后新请求读取密码**，因此不沿用首轮 F1 的高危结论。

**严重程度与置信度：低／已确认。**

**建议：** 登记失败即关闭连接并让 `handle` 结束；把已建立连接的登记安排到可能阻塞的首次输出之前，并保持复查原子性。为 I/O 和确认过程设取消机制。保留每请求配对复查，不以连接表替代它。

### G8．建议：完整性告警是瞬时派生结果，不能代表持续的来源验证

**位置：** `spec/revisions.md` §5.1、§5.3；`crates/keevo-format/src/merge.rs:50`、`:176`；`crates/keevo-format/src/item.rs:144`、`:330`；`crates/keevo-core/src/vault.rs:427`、`:453`、`:525`。

**问题与前提：** 对同一键、同一 rev 的不同内容，当前算法确定地保留一个版本并产生 `integrity_issues`；告警和矛盾证据不进入 `ItemDoc`，概要的 `conflicts` 也只看剩余并发值。再次写入后，单头没有第二份矛盾内容可供比较，告警会消失。除此以外，rev 是祖先只证明该节点存在于路径，不证明值和 HLC 真的是那一修订写下的。

**复现：** 两个头分别携带同一 rev、同一 HLC、不同标题，首次合并有 `integrity_issues`；把合并文档保存为父包含两头的新修订，再读取这个单头，告警列表为空。`r2_integrity_issues_should_survive_unrelated_write` 确认。另一个单头测试保留合法祖先 rev、替换该祖先原始值，当前代码同样不告警。

**影响：** “检测到了矛盾”在普通写入后不再可见，不能把空告警列表解释为来源或历史内容已认证，也不能声称覆盖了所有不一致。直接调用格式 API 时，头在图中缺失、Live／Deleted 身份冲突等也不属于此列表的检测范围。正常存储与未来同步验证必须另行保证它们。

**严重程度与置信度：建议／已确认。** 这里不把持钥恶意设备重新列为密码学完整性威胁，也不把已登记的 M2 历史认证摘要工作重复作为漏洞；需要修正的是新告警接口的含义和持久化决策。

**建议：** 明确 `integrity_issues` 只表示“本次候选中观察到的特定矛盾”。若产品要求用户查看并确认，应持久化待处理状态或审计证据，直到明确处理，不把任意编辑视为自动解决。未来接收层若要证明复制内容的出处，应验证对应版本的认证摘要；仅加祖先成员检查不能实现这一目标。

### 4.2 ADR-0003：Secure Enclave 文件的实际保护范围

本轮独立程序使用无用户在场要求的 SE P-256 协商密钥，把合成数据经 ECDH、HKDF-SHA256、AES-GCM 包裹后落到临时文件。随后另一个代码标识与 cdhash 均不同的临时签名程序恢复 blob、协商并解密成功，无认证提示。两个程序都启用了 Hardened Runtime。因此 spike 中原来未测的“其他进程能否使用”已在本机这个配置下得到肯定答案；正式生物识别策略没有由此得到验证。

| 材料／主张 | 本轮判断 | 需要改进的表述或设计 |
|---|---|---|
| SE 自身 P-256 私钥不以原始私钥输出 | 成立；应用得到的是硬件封装的表示 | 不要把这一属性转移到“被它包裹的 AUK、SK、Noise 私钥永不离开普通内存”。这些值解包后仍由应用处理。 |
| 复制 blob 到其他 Mac 不能恢复原 SE 密钥 | 符合 Apple 的设计说明，本轮未用第二台 Mac 实测 | 这比普通明文文件多提供离机复制保护；备份可携带 blob，只是新机不能用它，不能表述成文件本身不会迁移。[Apple CryptoKit 文档](https://developer.apple.com/documentation/cryptokit/storing-cryptokit-keys-in-the-keychain) |
| 无用户在场的账户 SK 包裹文件能阻止同用户进程取得 SK | 不成立，跨进程解包已实测；ADR 第 43 行实际上已承认这一点 | ADR 此行的边界正确，应同步到 security A7，明确 SK 泄露后安全性退化为主密码与 KDF；“密钥受 SE 保护”不能让读者误以为同用户调用被隔离。 |
| 无用户在场的服务静态密钥与账户 SK 具有“同上”的安全影响 | 不准确 | 服务 Noise 私钥被取出后，没有“还需主密码”这第二步来保护服务身份；它可以用于冒充 responder。对保险库内容是否进一步有影响需结合 socket、扩展与授权流程，未验证完整攻击链。 |
| 配对记录与服务静态密钥一律按同一无用户在场文件方案保存 | 与 IPC 规范冲突 | ADR 第 44 行写“同上”，IPC §4.2 第 116 行及 `PairingStore` 文档要求与保险库同等保护、放加密数据库。若前者还保护授权记录，同用户既能解包也能重包，不能提供本机授权完整性。**修改 ADR，或重新设计并明确独立的授权记录认证边界。** |
| 用户在场／仅当前指纹集的 AUK 包裹 | 本轮无法确认完整流程 | spike 的 `userPresence` 只验证创建，没有验证实际使用；它允许登录密码，不等于 `biometryCurrentSet`。创建成功不足以证明 Touch ID 解锁、取消、锁屏、指纹变更和失效恢复均正确。 |
| SE 设备标记“比钥匙串标记更可靠” | 缺乏比较依据 | 可明确说它可检测换硬件后的不可恢复；删除、损坏、设备恢复也可导致解不开，并不唯一证明换机。不能发现同一台 Mac 的数据库克隆。删除不经证明的比较级。 |

对于无用户在场的方案，新增保护主要是硬件密钥不可原样导出以及离机副本的不可用性；没有增加同用户应用身份隔离、用户授权或文件新鲜度。攻击者在原机上有调用能力时，可以解包出被包裹的对称密钥，也能为自己选择的内容生成新的封装。`0600` 区分用户，不区分同一用户的进程。这里验证的是合成数据的可调用性，没有读取实际账户秘密。

正式本机包裹格式仍需定义版本、用途、账户／材料身份、临时公钥编码、HKDF salt/info、AEAD AAD、长度限制和失败行为。spike 用空 salt、单一 `keevo/v1/se-wrap` info、未附用途 AAD，适合可行性实验，不能自动成为全部本机材料的规范。若本机格式明确不属于本次共享格式冻结范围，应明确隔离其版本与迁移责任。

### 4.3 临时签名、Hardened Runtime 与 Library Validation

ADR 第 47 行及 `docs/security.md:167` 混淆了“没有 Team ID，因此不能放行自家团队动态库”和“Library Validation 无法启用”。**Hardened Runtime 默认启用 Library Validation**，允许 Apple 签名库或符合相同 Team ID 条件的库；本轮 adhoc 程序实测能加载 Apple 系统库，而另一个 adhoc dylib 被拒绝。静态链接 Rust 可以避免加载自己的第三方动态库，与保持 Library Validation 相容。[Apple Library Validation 文档](https://developer.apple.com/documentation/BundleResources/Entitlements/com.apple.security.cs.disable-library-validation)

因此应修改 ADR 与 security 为：“启用 Hardened Runtime，保留默认 Library Validation，不设置禁用它的 entitlement；将不能通过动态库身份要求的自有 Rust 核心静态链接。”静态链接是减少动态依赖的工程选择，并不等价于系统对 `dlopen`、插件、将来引入的 framework 的代码身份强制检查；阻止 `DYLD_*` 注入又是另一项运行时措施。不能因静态链接而放弃 Library Validation，也不能把小型 CLI 实验当作整个 SwiftUI 应用打包已验证。

ADR 第 17 行“不使用任何团队的……entitlement”还应区分需要团队授权的受管能力与可在 adhoc 签名中声明的本地 entitlement／运行时例外。项目可以自行决定不使用任何例外，但不要写成所有 entitlement 都需要团队签发。

### 4.4 发布完整性与两张能力表

SHA-256 校验和可检查损坏或与一个**已可信**摘要的一致性；若二进制和摘要同在被攻破的发布渠道，攻击者可一起替换。ADR 第 48 行“核对校验和或签名”把两者当成等价来源保证，应该修改。Sigstore 可以支撑发布来源与完整性，但验证必须固定期望身份和 OIDC issuer，核验对应产物及 bundle／透明日志证明；不能只接受“任意有效 Sigstore 签名”。官方 `verify-blob` 用法也明确要求身份与 issuer。[Sigstore 验证文档](https://docs.sigstore.dev/cosign/verifying/verify/)

还应指定可信验证工具的取得方式、发布 workflow／仓库及版本约束、离线验证材料、版本回退政策，以及 Sparkle EdDSA 更新公钥如何在首次安装时得到可信绑定。可复现构建用于核对源码与产物，不单独证明源码或构建者可信；取消公证也取消了相应的 Apple 发布检查，签名并不等价于恶意软件检测。这里评审的是设计前提，不因 M3 尚未发布而报告发布流水线缺失。

| ADR“做不了的功能”行 | 核查结论 |
|---|---|
| 公证／Gatekeeper 直接放行 | 在坚持不使用 Developer ID／团队的决定下，不能走正常公证路径，方向正确。“仍要打开”应作为待验证安装流程，不能保证所有 macOS 策略、管理配置和拦截原因都可手动放行。[Apple 公证说明](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution/) |

另外有三处由本轮决定留下的直接文本矛盾，应改相应文档／注释：`spec/ipc.md:65` 仍写“取得签名证书”才可处理真实数据；`docs/security.md:114` 仍说账户密钥保存在设备钥匙串；`noise.rs:87` 仍说服务静态密钥存于钥匙串。ADR 生效后应改成实际采用的本机方案及其上线条件。

## 5. 仍未覆盖的部分

本轮补上了普通 DAG 的独立随机验证、两类删除反例、跨对象父引用、重复修订元数据、HLC 极值、合并总大小、存量 schema 迁移和 SE 跨进程使用。能力边界如下：

- **输入校验分层：** `Store::insert_revision` 先查同对象父节点，再插入新节点，正常调用能排除跨对象父引用、缺失父节点和通过该路径建立的环；重复 rev 无论内容是否相同均拒绝。`RevisionGraph::insert` 只新加了重复元数据一致性检查，接受环和未知父并不等于 Store 也接受。它把父列表作为有序 Vec 比较，父顺序不同也会冲突；同步格式仍应定义排序、去重和幂等重传规则。
- **修改 SQLite 后的图：** 原始数据库元数据被直接改写后的再加载并不自动获得 Store 插入时的保证。完整元数据认证、日志和接收校验属于已登记的 M2 范围，本轮未完成从同步文件到实际接受记录的整链验证。循环图测试是格式 API 的边界探测，不把未实现同步重新报为漏洞。
- **HLC 极值：** 实测 `observe(Hlc(u64::MAX), …)` 后 `next` 饱和，不再严格递增，来源为 `hlc.rs:74`、`:80`。极值接收策略已明确留给 M2，故不另编号。必须在写入本机持久化时钟前拒绝／隔离不合理远端时间；极端本机时钟也要有显式失败策略。没有验证未来接收端已经做到。
- **SAS：** 没有穷举 48 位、证明完整协议或实际测量攻击搜索吞吐；提供的是两个独立编码测试与具体概率推导。未验证正式词表、跨实现承诺向量和完整双端 UI。
- **macOS 产品集成：** 未运行实际 Chrome 与正式发布包的 F2 整链；未测试包内 cdhash 提取、更新时旧服务生命周期、受管安装权限、通用二进制各架构策略。小型 adhoc + runtime 程序验证不替代 SwiftUI/Rust 发布构建。
- **生物识别：** 未使用真实 AUK，未执行 Touch ID、`biometryCurrentSet`、指纹变更、锁屏及取消流程；未拿第二台 Mac 验证 blob 迁移失效。没有为了验证能力表而改写用户钥匙串、安装 Safari 扩展或改变系统设置。
- **资源与恢复：** 做了有限的约 20 MB 合并与子进程描述符测试，没有破坏性内存耗尽、长期性能曲线、长时间模糊测试或堆取证；没有验证大量并发值经过真实冲突 UI、恢复导出、清理与同步的全流程。
- **浏览器页面与未改格式：** 首轮 URL 输入已重测，但 DOM 导航竞态、iframe、手势与页面可见性未补齐。未重新全面审计未改动的所有密码学原语、附件 STREAM、同步签名、设备撤销和恢复；独立 Python 向量不覆盖 Noise、修订合并或 OS 身份来源。

未将 `spec/REVIEW.md` §5、作者处理记录 §6 中已登记的 UI、同步、Noise 清零、24 小时会话上限等仅因未实现而另列漏洞。本文要求的是新设计的前提和格式边界先成立，不是要求所有 M1／M2 功能现在就完成。

## 6. 给作者的问题

1. §5.3 的承诺是否包含对象“存在／永久删除”状态？若包含，准备持久化哪一种删除与恢复因果信息；若不包含，是否接受撤回整个对象的分组结合律声明？
2. `settle_for_write` 产生的恢复是否视为用户明确操作？编辑无关字段时，界面是否告知正在确定恢复决定，而不是仅保存原字段？
3. 合法并发版本总量超过 16 MiB 时，是否允许新格式把版本拆开存储？若只拒收，如何保证用户能无损访问、导出和解决当前状态？
4. 90 天指实际经过时间还是本机日历时间？是否同意对旧 schema 的未知年龄采取保守迁移，并在异常前跳后暂停清理？
5. 配对的“每次尝试”究竟从何时计数，如何限制未发第 3 条的中止尝试与并发连接？是否采用唯一的第 3 条编码，并给出跨实现向量？
6. ADR 第 44 行是否真的要把配对及站点授权记录放在无用户在场的 SE 文件中？若是，如何阻止同用户进程重包伪造授权；若否，请明确它与 IPC 加密数据库要求的关系。
7. 启动时读取 helper cdhash 的信任锚是什么？安装目录是否保证同用户不可改；更新是否强制重启服务；是否把包内任意文件替换明确排除在 A7 之外？
8. 完整性告警是否必须保持到用户明确处理？若是，需要保存哪些证据或状态；若否，如何避免用户把写入后的空告警误解为历史已认证？
9. 是否要把“同进程一次 KDF”作为库和 FFI 也必须保证的契约？如果是，哪个共享组件负责跨 Vault 实例限流，并把用户确认绑定到具体参数？
10. Sigstore 的期望发行身份、issuer、workflow、产物和版本约束分别是什么，首次安装如何获得可信验证入口及 Sparkle 更新公钥？这些需要在发布前形成可执行验证步骤。
