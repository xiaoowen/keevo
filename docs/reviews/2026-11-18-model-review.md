# Keevo v0.1 规范独立评审结果

## 1. 评审版本与总体结论

**评审提交：`35c649b5bedeb3b5a95d1caf5e09af214a5ce283`。**

- 评审日期：2026-11-18
- 评审对象：该提交的 v0.1 规范草案及对应实现
- 威胁模型：`docs/security.md` §3
- 严重程度：采用 `spec/REVIEW.md` §7 的分级
- 证据标准：实际运行结果或可逐步复现的推导记为“已确认”；尚缺关键验证的攻击链记为“疑虑”

最值得担心的已确认问题是：**撤销配对后，已有 IPC 会话仍能读取密码，甚至能跨越一次锁定、解锁继续使用**。父进程代码签名校验也存在身份替换问题：已验证 `fork → exec` 可以让攻击者创建的子进程通过对“当前父进程”的签名检查，但尚未完成真实 Chrome 与正式签名 host 的整链验证。密码学字节格式及独立测试向量未发现差异；合并规范的结合律、不丢数据承诺则有可复现反例。建议继续受控原型开发，但在解决 IPC 撤销、明确父进程认证边界并修正规范承诺之前，**不应将 v0.1 视为安全评审通过或冻结格式**。

## 3. 发现

### F1．高：撤销配对不撤销已有会话

**位置：** `spec/ipc.md` §4.4；`crates/keevo-ipc/src/service.rs:276`、`:318`；`crates/keevo-service/src/server.rs:97`。

**问题与前提：** 攻击者已控制一个建立完成的扩展会话。配对记录只在 IK 握手时检查；进入 `Established` 后，处理请求不再查询它。服务也没有按扩展公钥管理、关闭活动连接的机制。

**攻击步骤或复现方法：**

1. 正常完成配对，保留客户端及服务端连接。
2. 调用 `store.revoke(client.public_key())`，确认记录已经不存在。
3. 在旧连接发送匹配 GitHub 条目的 `fill`。
4. 服务仍返回密码。
5. 将后端锁定再解锁，同一连接仍可取得密码。

新增测试 `review_revoked_session_still_releases_password` 已确认上述行为。原测试 `revoked_pairing_blocks_new_sessions` 只覆盖“撤销后不能建立新会话”。

**影响：** 用户执行解除配对后，已被撤销的扩展仍具有秘密读取能力。此问题独立于已知的 24 小时会话上限未实现。

**严重程度与置信度：高／已确认。**

**建议的修改：** 建立按配对身份索引的连接注册表，撤销时立即关闭全部连接；处理敏感请求前复核配对有效性或授权代数，避免撤销与请求处理之间的竞态。

### F2．高：父进程的当前签名不能证明 host 由浏览器创建

**位置：** `spec/ipc.md` §3.2、§5.4、§6；`crates/keevo-macos/src/lib.rs:167`；`crates/keevo-native-host/src/main.rs:36`。

**问题与前提：** 同用户恶意进程可以创建进程、设置参数和管道。`parent_browser()` 检查的是父 PID 当前运行的程序，而非创建子进程时的身份；host 又把命令行来源参数视为可信来源。

**攻击构造：**

1. 恶意控制进程建立由自己持有的 stdin/stdout 管道。
2. 中间进程创建一个暂缓执行 host 的子进程。
3. 中间进程 `exec` 成受信任浏览器，PID 保持不变。
4. 子进程执行真实 host，提供 Keevo 扩展来源参数。
5. host 观察到的父进程已是签名浏览器，但管道和来源实际上由攻击者选择。
6. 若攻击者已读取扩展落盘私钥，可尝试以原配对身份建立 IK 会话。

**验证边界：** 已用原 `verify_pid` API 和 Apple 签名的 `/bin/sleep` 验证第 2–4 步机制：父 PID 在 `exec` 前后相同，签名检查返回 `Ok(true)`。**没有运行真实 Chrome、正式签名 host 和真实保险库的完整攻击链。** 该构造不需要 root、进程注入或 PID 复用。

基础机制可以在临时仓库副本中重建。创建 `crates/keevo-macos/examples/review_parent.rs`：

```rust
fn main() {
    let pid = std::os::unix::process::parent_id();
    let result = keevo_macos::verify_pid(
        pid,
        r#"anchor apple and identifier "com.apple.sleep""#,
    );
    println!("current parent PID {pid}, signed sleep accepted: {result:?}");
    assert_eq!(result, Ok(true));
}
```

执行 `cargo build --offline -p keevo-macos --example review_parent` 后，用下面的脚本启动检查程序：

```python
import os
import sys
import time

checker = sys.argv[1]
broker = os.fork()
if broker == 0:
    child = os.fork()
    if child == 0:
        print("original parent", os.getppid(), flush=True)
        time.sleep(1)
        os.execl(checker, checker)
    os.execl("/bin/sleep", "sleep", "20")
os.waitpid(broker, 0)
```

传入参数 `target/debug/examples/review_parent`。在允许动态代码签名查询的 macOS 环境中，本轮实测输出的两个 PID 相同，检查结果为 `Ok(true)`。此演示将信任对象设置为 `/bin/sleep`，仅用于验证身份检查语义，不能替代 Chrome 完整攻击链测试。

**影响：** 若完整链成立，§3.2 无法作为“扩展私钥被窃取之后仍安全”的第二道身份保证；来源 prologue 也只绑定双方提供的字符串。

**严重程度与置信度：高／疑虑；基础身份替换机制已确认，产品整链待验证。**

**建议的修改：** 不再把“当前父 PID 是浏览器”等同于“该管道属于指定扩展”。评估能够绑定创建者身份、进程实例及通信端点的 OS 机制；在证明之前，按“落盘扩展私钥可能足以冒充”设计原生端授权。仅在查询时给父进程取 audit token，并不能自动解决创建者身份已被 `exec` 替换的问题。

### F3．中：未认证输入仍能触发过大的资源开销

**位置：** `spec/crypto.md` §5.2、§8.5；`crates/keevo-crypto/src/kdf.rs:46`；`crates/keevo-core/src/vault.rs:221`；`crates/keevo-crypto/src/envelope.rs:175`。

**问题与前提：** 不可信文件进入解锁／解密路径。认证发生在昂贵操作之后：

- 合法范围内的参数允许申请 4 GiB Argon2 工作内存并执行 32 次迭代。
- `open()` 在验证 tag 前复制全部密文 body；信封解析仅检查最小长度，没有根据最大明文长度检查密文上限。

**攻击步骤或复现方法：**

1. 将账户 KDF 参数修改为 `m_kib=4194304,t=32,p=16`，保留原密钥集信封。
2. 触发解锁：参数校验通过，先执行 KDF，随后才因认证失败拒绝。
3. 对信封路径，使用合法版本、算法和可见 kid，附加超大 body；代码会先执行 `body.to_vec()`，再验证 tag。

上述执行顺序可以直接逐步复核；**未执行耗尽内存测试**。对同步攻击的适用性依赖未来同步入口是否允许这些文件到达该路径；同步入口尚未定稿，不能把缺少入口防护视为已验证事实。

**影响：** 内存压力、长时间占用计算资源或进程退出。没有证据表明能降低原密文的破解难度。

**严重程度与置信度：中／已确认输入处理缺口；具体设备上的资源耗尽后果未压测。**

**建议的修改：** 区分格式允许上限与本机自动执行预算；异常增大的 KDF 参数要求明确处理，限制并发 KDF。在读取／复制信封前检查 `42 + padded_len(4 + MAX_PLAINTEXT_LEN) + 16` 上限，并在文件入口同样执行大小限制。

### F4．中：合并视图不满足所声明的结合律

**位置：** `spec/revisions.md` §5.3、§9；`crates/keevo-format/src/merge.rs:154`。

**问题：** 胜出视图丢弃了后续合并所需的候选信息。以下三个同键记录版本即可构成反例：

| 版本 | 值 | HLC | 因果关系 |
|---|---|---:|---|
| A | `"A"` | 20 | B 的祖先 |
| B | 墓碑 | 30 | 在 A 后删除 |
| C | `"C"` | 15 | 与 A、B 并发 |

另建 A 的后继头 A′，只修改其他记录，继续携带 A，使 A′、B、C 成为合法并发头。

**攻击步骤或复现方法：**

- 一次合并 A′、B、C：A 被 B 因果覆盖；C 胜过并发墓碑 B，得到 **C**。
- 先合并 B、C：得到 C；再将该视图与 A′ 合并：A 和 C 并发，HLC 较大的 A 胜出，得到 **A**。

新增测试 `review_grouping_changes_winner` 已确认。这里的分组合并是使用中间结果的胜出记录映射替代原始候选；没有把这次计算当作产生新修改的用户编辑。

**影响：** 实现者若依据 §5.3 进行增量合并、缓存压缩或分组合并，可能得到不同结果。当前“始终收集完整头集合再计算”的路径不因此自动失去收敛性，不能将此夸大为现有所有合并均错误。

**严重程度与置信度：中／已确认。**

**建议的修改：** 将结合律明确限定为保留完整候选的状态集合合并；禁止用胜出视图替代原始状态。若需要视图可组合，必须保留足够的因果候选信息，并增加真正的分组测试。

### F5．中：伪造记录出处可破坏确定性

**位置：** `spec/revisions.md` §4.2、§5.1；`crates/keevo-format/src/merge.rs:144`。

**问题与前提：** 持钥设备提交不符合写入规则的记录。实现没有验证复制记录的值是否与所声称的原始版本一致；去重时只保留同 rev 的一个候选。

**攻击步骤或复现方法：**

1. 根修订 r1 写入 `title="base", rev=r1, hlc=10`。
2. 两个并发子修订分别携带原记录，以及 `title="forged", rev=r1, hlc=10`。
3. 交换两个头的输入顺序调用 `merge_heads`。
4. 得到不同结果。

新增测试 `review_forged_record_version_changes_with_input_order` 已确认。

**影响：** 不同到达顺序可能导致不同视图，且伪造值可能以“同一版本去重”的方式消除冲突提示。这需要持钥恶意设备或等效的已认证坏数据，不是无密钥密文篡改攻击。若产品明确将已登记持钥设备的恶意行为排除在保证之外，应将本项作为输入健壮性与确定性契约问题处理，而不是对外宣称未授权解密漏洞。

**严重程度与置信度：中／已确认，属于强前提下的完整性和健壮性问题。**

**建议的修改：** 接收时验证记录出处、祖先归属及复制一致性；同一记录版本标识对应不同值时明确拒绝或隔离。修订元数据重复但内容不一致也应报错，不能简单“首次为准”。历史内容清理前，应明确后续验证所需的认证摘要如何保留。

### F6．建议：“不丢数据”的承诺与清理规则矛盾

**位置：** `spec/revisions.md` §1、§7、§9；`crates/keevo-core/src/vault.rs:485`；`crates/keevo-store/src/lib.rs:500`。

**问题与复现方法：** 创建标题为唯一旧值的条目，再写入 21 个使用新标题的修订。首修订变成 `pruned=true`，概要、详情和包裹密钥被清空；保留的 20 个修订都没有旧标题。新增测试 `review_old_value_disappears_from_retained_revisions` 已确认。

**影响：** “任何被覆盖值都能在某个保留修订中找到”并不成立；并发落选值在收敛、随后清理后也没有永久保留保证。有限历史保留本身可以是合理产品选择，问题是当前承诺没有限定。

**严重程度与置信度：建议／已确认。**

**建议的修改：** 将承诺限定为“保留期内可恢复”，明确冲突落选版本的保留策略；如果要求直到用户明确解决前都不能丢失，则必须固定这些版本，不受普通最近 20 项清理影响。

## 4. 规范与实现的不一致

### 已核对一致的字节级行为

- **AAD：** 132 字节，依次为 12 字节标签、version、alg、16 字节 kid、object_type、part、4 字节大端 part_index、四个 16 字节 ID、32 字节 binding。
- **HKDF：** `K_s`、AUK、kid 的 IKM 顺序、account_id salt 和 info 均与规范一致；SAS 使用完整握手 hash、空 salt、规定 info。
- **binding：** 标签后接大端 8 字节 epoch、完整 29 字节 KDF 参数。
- **填充：** 长度前缀为大端；长度越界、非规范桶长度和非零填充均被拒绝。
- **prologue：** 精确为 `keevo/v1/ipc`、NUL、用途、NUL、来源字节，没有额外结尾 NUL。
- **截断、扩展和上下文改动：** 原有测试及代码检查支持拒绝这些信封修改。

AAD 的零起始字节偏移如下，便于后续跨语言实现核对：

| 字节区间（左闭右开） | 字段 |
|---|---|
| `[0,12)` | `keevo/v1/aad` |
| `[12,13)`、`[13,14)` | version、alg |
| `[14,30)` | kid |
| `[30,31)`、`[31,32)` | object_type、part |
| `[32,36)` | part_index，大端 |
| `[36,52)` | account_id |
| `[52,68)` | vault_id |
| `[68,84)` | object_id |
| `[84,100)` | rev_id |
| `[100,132)` | binding |

### 需要修改的差异

| 差异 | 应修改哪一方 |
|---|---|
| `ipc.md` §4.4 要求撤销时立即断开全部会话，代码只删除配对记录。 | **代码**，见 F1。 |
| `revisions.md` §5.1 按 `(rev,hlc)` 去重，代码按 `rev` 去重；二者都未定义同标识不同值如何处理。 | **规范与代码**共同明确并拒绝矛盾版本。 |
| `revisions.md` §5.1 多个并发候选即标记冲突；代码仅在落选值与胜出值不同的时候报告冲突。 | **规范**明确“版本并发”与“需要展示的值冲突”的区别，或调整代码。 |
| `revisions.md` §9 要求分组结合律与不丢数据测试；现有随机测试实际验证排列、重复头及清理后的视图一致性。 | **规范、测试**，见 F4、F6。 |

| 配对 60 秒超时被委托给调用者；当前终端提示使用阻塞 `read_line`，没有超时。 | **集成代码**落实截止时间，避免仅有注释契约。 |
| `ipc.md` §3.1 指定 `SecCodeCreateWithAuditToken`；实际采用携带 audit-token 属性的 `SecCodeCopyGuestWithAttributes`。 | **规范**更新实际 API；这本身不是发现的认证绕过。 |
| `keyset.rs:145` 注释称 epoch binding 防旧版本回放，但函数只认证传入 epoch，未检查可信历史最大值。 | **注释与规范边界说明**；真正的新鲜度检查属于上层。未把已知尚未实现的同步机制另报为漏洞。 |

最后一项的检查对象为 `Cargo.lock` 锁定的 snow 0.10.0，以及其 `src/resolvers/default.rs` 中的 `Dh25519`、`CipherChaChaPoly`。Keevo 自己用 `Zeroizing` 包装原始静态私钥，并不自动清除传入依赖后产生的内部副本。

此外，`crates/keevo-service/src/pairing.rs` 中的 `FilePairingStore` 当前使用未认证 JSON 保存授权记录，代码注释已经承认其可篡改并计划迁移。它不能作为正式版本的可信授权存储；这里记为发布集成差距，不把开发模式演示等同于正式产品已被攻破。

## 5. 没有覆盖到的地方

- **正式签名链路：** 未验证真实 Chrome、正式 Keevo Team ID、发布版 host、沙箱及 Hardened Runtime 组合；F2 的完整可利用性仍需这一环境。
- **SAS 主动搜索：** 没有完成 48 位碰撞搜索，也没有证明该协议具备所声称的“一次机会”界限；需要分析可控 transcript 字段、承诺时点、计时和重试策略。
- **浏览器实际页面行为：** 本轮验证了 Rust URL 匹配和服务检查，没有完整测试页面导航竞态、iframe、可信手势、隐藏表单、点击劫持及 DOM 填充过程。
- **同步与恢复：** 未把尚未定义的同步签名、高水位线、设备证书、附件 STREAM 当作已实现保证；因此不能确认整体 G2 的回滚、删除检测性质。
- **资源与内存：** 没有运行破坏性的内存耗尽实验、堆取证或长期模糊测试。
- **历史真实性：** 当前测试与审查不足以证明对恶意 DAG、跨对象父引用、重复修订身份及 HLC 极值的完整接收验证。
- **独立性边界：** Python 向量提供不同密码库的交叉验证，但不是完整独立协议实现，尤其不覆盖 Noise、合并及实际来源获取链路。

`spec/REVIEW.md` §5 已列出的附件、同步签名格式、24 小时会话上限、Touch ID、开发签名策略、Swift 字符串、serde 临时缓冲、词表、浏览器白名单和 PSL 等问题，没有仅因其尚未实现而重复作为新漏洞报告。涉及这些机制时，报告明确区分已有边界与本轮新增证据。
