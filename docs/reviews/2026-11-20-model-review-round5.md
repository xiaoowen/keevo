## 1. 冻结结论

**不建议按当前状态整体冻结 M1.5 草案。** 本轮确认 **8 项发现：5 项中、3 项低**；没有证据支持“无需凭据即可解密保险库”或“突破 AEAD”的结论。主要阻塞来自恢复后的时间与图不变量、SSH 授权的失败路径、导出口令强度门槛，以及导入过程中未声明的数据改变。

原有测试全部通过，但新增反例中有 17 项失败。不能用“预审回归测试已绿”代替这些边界条件的检查。

### 冻结前必须修改的规范条文

| 编号 | 条文 | 必须明确的内容 |
|---|---|---|
| **C1** | export §3“导出密码” | 强度判定必须针对**与 KDF 相同的 NFKD 后字节所代表的口令**。不得把未分析的后缀直接当作独立随机熵。“zxcvbn 4 分”是估计门槛，不能承诺至少具有某个真实猜测成本。参见 L1。 |
| **C2** | export §1、§3；sync §2 的恢复后状态 | **所有格式**都需为导出重新验证，包含操作者自选密码的加密导出。授权应是单次、有期限、绑定当前解锁代次的；任何进入锁定状态的路径均失效。恢复失败是否保持解锁，还是统一锁定，必须选择一种完整语义，不能只清除核心 session。参见 L8；当前 export §1 仍只写“明文导出前”。 |
| **C3** | sync §2“备份是不可信的输入”“恢复”第 2、3 步 | 不可信保存时间不能提供历史年龄证据：对导入的内容采用保守的新接收时间，或使用恢复前可信的匹配记录。写明恢复验证包括 DAG、拓扑顺序、有效头，不能只检查父 ID 存在。删除“被改写的备份最多等同一份更旧备份”的无条件承诺；结构检查不会认证内容完整性、来源或新鲜度。参见 L2、L3。 |
| **C4** | revisions §7.3；crypto §8.9“回收” | 清理历史与回收附件之间的失败必须可恢复：用同一事务、持久待办或可重复扫描，不能仅在“本次 prune 数量大于零”时尝试。将“无修订/全部头是墓碑即启动删除”明确限定为 **M1 单机、已验证图**；M2 必须服从因果稳定与同步接收完整性条件，不能把缺头、尚未收到引用或未稳定墓碑等同于可删除。参见 L5、L3。 |
| **C5** | ssh-agent §4.1 | 明确“关闭/撤销策略”也是必须持久保存的决策，迁移重试不得把它解释为“尚未迁移”。永久删除、重建中的旧条目删除与授权撤销必须有一致提交点。迁移中断时允许什么状态、何时可使用迁移出的策略，需明写。另建议明确明文是裸 ASCII `ask/session/unlocked`，作为 crypto §8.8“UTF-8 JSON”的按种类例外，避免实现者写成 JSON 字符串。参见 L4。 |
| **C6** | export §2、§4；product §5.7 导入承诺 | 明确 Keevo 自有 JSON 中分区以**数组位置**为身份，同名不合并；明确标签/标题/分区名的限制与超限行为。不得在未告知时截断合法输出。多行字段经所有导入路径均保留原值；非法 CSV 的闭引号后出现普通字符应拒绝，或定义不改变原值的兼容规则。参见 L6。 |
| **C7** | governance §5；泄露检查结果语义 | 把“k-匿名保证不知道哪个密码”“复用连接后看不出请求个数”改为有限保证：发送 20 位前缀、不发送完整哈希；仍可候选匹配、跨次交集分析与流量估计。请求档位是不同前缀数的档位，不是条目数。结果必须区分“当前密码已查询且未匹配”“尚未查询/响应无效”，不得由旧批次的全局 complete 推出新密码安全。参见 H1、L7。 |

这些修改大多不需要改变加密信封或 v2 的字节布局。不要为了修复本机授权、清理与缓存生命周期而无谓提升共享格式版本。

### 预审处理记录 §4 的未决事项

没有把原未决项重新编号为发现。

- **独立实现生成的导出向量（S7）建议在冻结前完成**：现有加密导出的 round-trip 共用同一个 KDF、HKDF、头部实现，不能排除双方共同犯错。固定口令、NFKD 等价输入、KDF 编码、62 字节 AAD 和认证失败样例，是冻结新交换格式的直接验收证据。当前两项 Python `--check` 通过并不覆盖导出封装。
- **v1/v2 混合头的独立合并向量（S6）仍值得补，但本轮不把它单独升级为冻结阻塞**：版本是内容的派生属性，不进入记录冲突排序；本轮新增的混合头/并发附件/删除后回到 v1 测试通过。它不能替代独立向量，但降低了此处的不确定性。
- 备份总大小、立即彻底删除附件、来源专有内容、附件表明文条目 ID：保持原处理决定；本报告没有把它们作为新发现。

## 2. 逐题回答

本节“成立”指该题所期望的安全/一致性保证成立，不是指攻击成立。

### A1 附件的绑定：有条件成立

在**可信的条目引用、正确的调用上下文，以及附件 ID 永不复用**的条件下，未发现无密钥攻击者使读取成功返回不同明文的路径。

- VK 包裹 AK 的信封、AK 加密元数据的信封及块，均绑定账户、保险库、附件 ID、类型和 part；不同用途不能互换。
- 块位置进入 `part_index`，总数进入 binding；存储层检查连续下标和总数，解密层检查非末块/末块长度、总明文长度，再核对摘要。
- 所属条目虽然不直接放在块 AAD 中，但被认证元数据的 `item` 和请求条目核对；名称、大小与已认证条目引用核对。移植不能只靠改明文 `item_id` 成功。
- `rev_id = 0` 在每个 ID 只封装一次的模型下没有新增替换空间。重建使用新 ID、新 AK；旧的合法同一密文被重放只会得到同一内容。
- `sha256` 是对**既定引用**的明文承诺，不是独立的签名。如果攻击者能同时重写被信任的条目引用，不能靠摘要声称仍能发现一切替换；本题无密钥攻击者没有这项能力。

对照测试 `review5_a1_attachment_context_and_chunk_binding_controls` 通过，覆盖跨账户/保险库/条目/附件、换序、截断、追加、重复块及错误摘要。现有独立附件向量也通过。

这不构成历史新鲜度保证：能回放整套旧修订和数据库元数据的人仍可能让用户看到旧引用。备份整体未认证是已知边界；L2、L3 讨论的是此外的本机状态处理错误。

### A2 附件的回收与删除：不成立

正常 M1 路径的添加、永久删除、重建已把附件增删与修订提交正确组合；历史扫描也包含 `concurrent`，没有发现“只扫当前字段”导致的提前删除。

但 prune 先提交，附件删除失败后没有持久待办，下一次仅在又清理了历史时才重试，启动扫描也不覆盖“条目还活着但已经无引用”的附件（L5）。因此内容可能无限期残留。恢复接受错误图还可能使启动扫描将完整附件误当孤儿（L3）。M2 中启动删除的例外须受因果稳定约束，见 C4。

### V1 条目详情 v2：成立

`ItemDoc::version`（`crates/keevo-format/src/item.rs:204`）同时扫描 records/concurrent，检查“kind 为附件 **或** data 为附件”。decode 先重新编码再做语义检查，故：

- 无附件的 v2 文档与带附件的 v1 文档均不是规范编码；
- kind/data 只有一方是附件时，v1 输入按非规范编码返回 malformed，与只认识 v1 的读取方一致；
- v2 输入的 kind/data 不配对可在语义层返回 value_kind_mismatch；
- 只认识 v1 的实现先看到不支持的文档版本，整个条目不可读，不能静默跳过附件字段；
- v1/v2 合并不比较版本号，只比较记录版本及修订图；结果版本由合并后内容重算。

本轮混合头测试中，当前字段为文本、并发输家为附件，结果仍为 v2；删除该键覆盖全部版本后回到 v1。顺序交换结果相同。这里只是针对新增格式边界的检查，不是重新声称对所有任意输入完成形式证明。

### E1 导出文件：不成立

封装设计本身有条件成立：随机 salt/nonce，口令 NFKD，Argon2id 后经用途独立的 HKDF，全部 62 字节头作为 AAD；open 在派生前检查参数预算和长度，错误认证不会区分错误口令与改动密文。本轮未找到更弱派生或未认证头部被接受的路径。

不成立之处：

1. 强度门槛可被长重复口令、NFKD 等价弱口令通过（L1）。单纯“代码返回 4 分”不够。
2. 正常 FFI 路径已经要求所有格式单次重新验证，但失败恢复路径保留旧标记，不能称为对所有锁定路径都完备（L8）。
3. Keevo 自有导出再导入仍有无提示改变（L6）。

修正 L1 后也不能把估计分数当作可证明的熵下界。本轮尊重作者“不自动生成口令、不加账户密钥第二因子”的决定，不将该产品取舍重报为漏洞。

### B1 恢复与本机状态：不成立

拒绝主动 schema 对象、导入 Keevo 自建数据库、保留当前 meta/local_record、一次性换入的方向正确；正常失败不会把备份的旧配对表先提交回主库，K2 的原问题已修复。

但仍有以下能力或后果：

- 只降低某个新修订的 stored_ms，即使所有时间均不超过恢复前有效时间，也可使其立即满足清理条件（L2）。
- 父 ID 都存在并不说明是 DAG；自环会导致没有头。仅调换未认证 seq 也会恢复出后续图加载不能接受的顺序（L3）。
- SSH 授权本机记录若在此前删除/重建/迁移失败中残留，恢复保留这些记录恰会复活授权（L4）。
- 逐行导入失败可能使核心锁定但 FFI 秘密句柄与导出验证仍存活（L8）。

**只核对同一账户 ID 不足以保证这些性质。** 它也不是认证：攻击者仍可删去对象、改写未认证图或回放旧账户行。后两类能力的根本认证属于原定 M2 边界，不能把它们描述为已由结构检查消除。另外，`Vault::restore_from:1033` 的账户核对与 Store 中真正导入不在同一个快照；建议在导入事务内核对期望账户 ID，而不是依赖路径两次打开相同。这项竞态仅做代码路径提示，本轮没有做竞争调度实验，未另列 L 编号。

### I1 不可信导入文件：不成立（数据保真）；资源安全有条件成立

检查了 zip、CSV、1PUX、Bitwarden JSON、Keevo JSON 和 Bitwarden 解密路径，未发现已证实的越界 panic。zip 使用 checked_add/get，Deflate 输出限长，校验输出大小与 CRC；JSON 预扫描节点，条目在构造输出时限数；分区与标签去重已用哈希集合。

但 L6 的数据改变可稳定复现，因此不能作整体通过结论。

资源边界方面：

- 上限是**有界**而非“低内存”：输入最多 512 MiB，1PUX 展开最多 256 MiB，节点最多 400 万；输入、展开数据、解析结构、输出条目可能共存。没有依据把整个进程峰值概括为“解析树至多约 200 MB”。
- Bitwarden PBKDF2 上限 200 万次、Argon2id 上限 1 GiB/10 次/16 lane，且共用进程级 KDF gate；作为兼容范围是有限的。它仍可能明显阻塞其他解锁/导出任务，不能用“匹配来源软件上限”代替本机预算。
- Keevo 本轮的自动预算本身也是 1 GiB/10 次（p 上限为 8），因此没有把相近的 Bitwarden 上限单独重报为新的漏洞。建议统一设备预算和取消能力；本轮没有运行顶格耗内存实验，也不声称排除了所有拒绝服务。
- CRC 不提供恶意输入认证；它只对意外损坏有效。这与导入来源不可信的前提一致。

### H1 泄露检查：有条件成立

“正常请求只含 SHA-1 前 5 位、Add-Padding、在 Rust 本机比对”成立；“因此运营方不知道密码、网络观察者看不出个数”不成立。

运营方还能看到 IP、时间、Keevo User-Agent、整批前缀；有候选密码时可筛选候选。去重与 64 桶填充隐藏的是**一次请求中不同前缀的精确数量**，不能持续隐藏真实集合。

一个直接的反例推理：只有一个真实前缀时，每次补 63 个均匀随机假前缀。两次假集合交集的期望约为 `63²/(2²⁰−1) ≈ 0.0038`，真实前缀却必然重复。因此两次检查通常就能从交集识别稳定的真实前缀。密码集合大致不变时同样可进行交集分析。随机假前缀不等于抵抗重复观察。

网络观察者通常看不到 TLS 内路径，但仍能观察服务地址、连接活动、总字节数与时序。复用 URLSession 既不是固定一条连接的协议承诺，也不是固定带宽填充；即使确实只用一个连接，也不能推出无法估计批次数量。

建议保留明确 opt-in，准确披露上述残余风险，允许用户主动检查并控制频率；若未来要求抵抗多次交集分析，需要稳定的掩护集合、缓存或其他专门设计，不能只换一批随机假前缀。结果正确性需先修 L7。上述结论来自代码和集合运算推理，没有查询 HIBP 或使用真实密码。

“到位”限于该行列明的修复目标与本轮检查范围，不代表对应整个功能无问题。原回归测试的结果来自干净提交的工作区测试。

| K 编号 | 结论 | 检查依据 |
|---|---|---|
| **K1** | **部分到位** | `restore.rs:45` 起拒绝触发器/视图/虚拟表、检查普通列，自建 staging，不导入任意表/索引。原 schema 攻击被阻断；但时间下调、循环图与 seq 信任仍破坏恢复后的行为，L2、L3。 |

## 4. 发现列表

### L1．中：导出强度检查接受明显弱口令及规范化后弱口令

- **位置**：`spec/export.md` §3；`crates/keevo-core/src/export.rs:52`；`crates/keevo-core/src/strength.rs:86`、`:91`；`crates/keevo-crypto/src/export.rs:32`。
- **问题**：评分只分析前 64 个字符，余下每字符乘以 10 的猜测次数。80 个相同的 a 因后 16 个重复字符获得至少 10¹⁶ 倍虚构强度。另一条路径是评分原字符串、KDF 使用 NFKD：`ｐaｓsｗoｒd１２３` 被接受，实际加密口令却是被检查器拒绝的 `password123`。
- **前提**：用户选择这种口令并依赖“很强”反馈；导出文件被他人获得。不需要攻击者拥有主密码或账户密钥。
- **影响**：导出内容仅有口令保护，攻击者可用少量常见模式猜测验证；“最高档”失去应有筛选作用。没有发现 Argon2id 或 AEAD 失效。
- **严重程度**：**中**。需要用户选取弱口令和文件泄露，不能归类为任意保险库无凭据解密。
- **建议**：先按实际 KDF 规则规范化再评分；使用对全部输入保守的评估，不给未分析后缀虚构熵；加入长重复、长序列与兼容字符回归。
- **证据**：`review5_l1_repeated_tail_is_not_export_entropy`、`review5_l1_export_strength_uses_kdf_normalization` 均失败。后者先确认 NFKD 恰为 `password123`，再断言弱口令应被拒绝；失败发生在拒绝断言。

### L2．中：恢复时间只做上限截断，仍能让新历史立即过期

- **位置**：`docs/sync.md:93` 的恢复时间规则；`crates/keevo-store/src/restore.rs:397`；`crates/keevo-store/src/lib.rs:803`、`:1033`。
- **问题**：恢复采用 `stored_ms.clamp(0, effective_before)`，年龄却是恢复后 `max(stored_ms) - stored_ms`。上限约束没有限制攻击者把某条时间调小。
- **前提**：保险库已有超过保留期的累计运行时间；用户恢复可被修改的备份。攻击者仅改 stored_ms，无需修改任何密文、父关系或本机状态。
- **影响**：保留期内的新历史在恢复后被 Keevo 自己清除。若该历史是附件最后一个引用，后续正常回收也会删除附件。不只是“攻击者已经把历史删掉”的已知未认证备份问题。
- **严重程度**：**中**，可导致数据丢失，需要用户恢复被修改备份。
- **建议**：对备份内容保守记为恢复时新接收；如要保留原年龄，必须使用当前数据库中仍可信且确切匹配的修订年龄或另行认证的年龄依据。不要从同一批不可信时间同时推导起点和各记录年龄。
- **证据**：`review5_l2_restore_must_not_age_fresh_history` 用夹具模拟合法运行 100 天后新写 25 个修订；原库 prune 为 0。备份中只把第一条时间改为 0，恢复后 prune 实际为 **1**，期望 **0**。没有等待现实中的 100 天，也没有访问真实数据。

### L3．中：恢复没有建立后续读取所需的有效修订图

- **位置**：`docs/sync.md:92`；`crates/keevo-store/src/restore.rs:380`、`:420`；`crates/keevo-store/src/lib.rs:715`、`:871`；`crates/keevo-core/src/vault.rs:1970`。
- **问题**：父 ID 只需在同一对象的 known 集合中存在，允许自环/环；另一方面，导入按未认证的 seq 排序，后续 `RevisionGraph::insert` 却要求父修订先出现。
- **前提**：备份被改写，用户恢复。不需要密钥；两种反例均不改密文。
- **影响**：自环可以让头集合为空，对象从基于 head 的列表消失；重开时附件还可能被无主清理删除。仅反转 seq 的有效 DAG 被成功换入后，条目读取因缺少已插入父节点而失败。这不是一份正常旧备份会产生的存储不变量。
- **严重程度**：**中**，数据不可访问，且可能触发进一步删除。
- **建议**：换入前验证 DAG 并按拓扑顺序写入（或者拒绝不能接受的顺序）；拒绝自父、环以及不可能的头/内容状态。启动孤儿清理只能依赖已验证图。不能仅因 `PRAGMA integrity_check` 通过就认为应用层图合法。
- **证据**：`review5_l3_restore_rejects_parent_cycle` 期望拒绝但返回成功；`review5_l3_restore_does_not_trust_revision_sequence` 只执行 `UPDATE revision SET seq = -seq`，恢复和解锁成功，随后“条目应可读取”断言失败。后者使用正常加密生成的账户与条目。

### L4．中：SSH 策略迁移与删除的生命周期仍可重新授予已撤销授权

- **位置**：`spec/ssh-agent.md` §4.1；`crates/keevo-core/src/vault.rs:664`、`:681`、`:1704`、`:1790`。
- **问题**：三个独立入口违背同一个授权不复活契约：
  1. 迁移先写本机策略，再删除旧属性，最后写全局迁移标记。中途失败后用户设置 None 会删除本机记录；下一次迁移将“已明确关闭”误认作“尚未迁移”，再次导入旧 unlocked。
  2. purge 先提交墓碑/附件删除，再删除 local_record；后一错误被 `let _ =` 忽略。
  3. rebuild 直接永久删除旧条目，没有对应的 SSH 本机授权清理。
- **前提**：旧策略为 unlocked；迁移清理中断、永久删除时撤销语句失败，或执行重建。后两条再恢复旧备份；迁移路径不需要恢复。
- **影响**：用户已关闭或永久删除的密钥再次在 Agent 中按 unlocked 提供；保留恢复前 local_record 本身无法修复已经残留的授权。持有该条目内私钥不是利用所需前提，但真正签名仍受其他 Agent 来源规则约束。
- **严重程度**：**中**。授权意图被突破，存在失败/恢复等较强前提；测试证明策略复活，没有伪称完成真实 SSH 攻击。
- **建议**：记录持久的显式关闭/已处理状态；迁移按每条授权可重入且不覆盖之后的用户决策；purge/rebuild 的旧策略撤销进入同一事务。撤销失败不得作为删除成功静默吞掉。
- **证据**：三个测试均失败：`review5_l4_failed_migration_does_not_regrant_revoked_policy`、`review5_l4_purge_revokes_policy_atomically`、`review5_l4_rebuild_revokes_old_policy`。触发器只用于模拟本机语句失败，未作为恶意备份导入；重建反例不需要故障注入。

### L5．低：附件回收失败后没有持久重试条件

- **位置**：`spec/revisions.md` §7.3；`crates/keevo-core/src/vault.rs:1416`、`:1631`；`crates/keevo-store/src/lib.rs:871`。
- **问题**：prune 已提交后才 collect_attachments；collect 失败留下附件。下次只有新 prune 数量大于 0 才再次扫描，重开时只删除无头/墓碑条目的附件，不删除仍活着条目的无引用附件。
- **前提**：最后引用已经按保留政策清理，附件删除遇到 I/O/SQL 错误；此后不再有新的可清理历史，例如条目停止编辑。
- **影响**：不再可恢复或可访问的附件密文可能无限期残留，并进入之后的备份。不是明文泄露，也不包含已经接受的 APFS/WAL 安全删除局限。
- **严重程度**：**低**，秘密密文留存及存储占用，读取仍需密钥。
- **建议**：prune 与引用扫描/删除形成可恢复事务；或者维护清理待办，在解锁/维护任务重试；回收函数失败不能使后续重试永久依赖另一条历史刚好过期。
- **证据**：`review5_l5_attachment_gc_retries_after_failure` 先确认所有保留内容修订均无附件引用，注入一次删除失败，移除故障，重开并成功编辑后，附件行仍存在，期望不存在的断言失败。测试不宣称此后任何操作都不能删除；永久删除条目或未来再次发生 prune 仍可能清掉它，问题是缺少保证执行的重试路径。

### L6．低：导入仍会静默改变有效内容，且非法 CSV 可被拼成新密码

- **位置**：`spec/export.md` §2、§4；`crates/keevo-core/src/import/mod.rs:426`、`:450`、`:488`、`:554`；`crates/keevo-core/src/import/keevo.rs:102`；`crates/keevo-core/src/import/csv.rs:23`、`:58`。
- **问题**：
  - 合法 201 字节字段标签导出后再导入，被截到 200 字节，没有丢失提示；标题和分区名共用类似限制。
  - Keevo JSON 的两个不同 section 下标只因名称相同被合并，字段的分区归属改变。
  - Bitwarden 等来源的 notes 经过 `Builder::note`，仍调用 trim_end，绕过已修复的多行 add 路径。
  - CSV 读到闭引号后回到普通字段状态，接受 `"abc"def` 并生成 `abcdef`，没有 malformed。
- **前提**：前三项正常导入即可；CSV 项为损坏或恶意文件。不涉及原未决的密码历史、passkey、1PUX reference。
- **影响**：名称和结构丢失、多行值改变、凭据在“成功导入”时已经不是原值。用户若据此移除来源副本，会失去保真数据。
- **严重程度**：**低**。没有凭空获得秘密的远程能力，但不符合本轮数据不静默改变的目标，应在冻结前修。
- **建议**：Keevo 自有格式使用保真路径，按 section 下标映射；超限拒绝或明确报告，不能悄悄 clip；所有多行入口保留空白；CSV 增加“已闭引号”状态，只允许分隔符/行尾/EOF。
- **证据**：`review5_l6_own_export_preserves_field_labels`、`review5_l6_export_section_indices_preserve_distinct_sections`、`review5_l6_bitwarden_multiline_whitespace_is_preserved`、`review5_l6_csv_rejects_data_after_closing_quote` 均失败。分别观测到 201→200、2→1、尾部空格与换行丢失，以及非法 CSV 被接受。

### L7．低：泄露查询把未查询或无效响应当作“已检查”

- **位置**：`crates/keevo-core/src/security.rs:287`、`:320`、`:395`；`crates/keevo-ffi/src/security.rs:270` 的 `breach_count` 初始化；`apps/macos/Sources/KeevoUI/SecurityCenter.swift:78`。
- **问题**：
  - complete 只针对 prepare 时的 wanted。修改/新增密码后，analyze 仍把旧 complete 复制到新报告。
  - 非 35 字符或非十六进制的后缀被跳过，但 prefix 最后仍进入 done；空正文也可被记为成功。Swift 还忽略 record 的 false 返回。
  - FFI 对没有匹配记录的条目按全局 breach_checked 赋予 `Some(0)`，把“没有查过当前密码”转成“查过且没有出现”。
- **前提**：完成一次查询后更新密码，或收到格式错误/不完整响应；测试全部使用本地字符串，不需要网络攻击。
- **影响**：安全中心给出错误的完成/未泄露状态，用户可能误信新密码已有检查。不会因此把完整哈希发送出去。
- **严重程度**：**低**，安全反馈不可靠。
- **建议**：查询状态绑定密码哈希和批次；当前密码不在已验证批次中则为 unknown；先完整验证响应再原子提交计数/done，调用方传播失败。无法证明远端数据完备时，文案只能说“本次响应未匹配”，不能证明从未泄露。
- **证据**：`review5_l7_changed_password_is_not_already_checked`、`review5_l7_malformed_range_is_not_success` 均失败。前者新增一个未请求过的密码后报告仍 breach_checked；后者接受 `not-a-sha1-suffix:1`。

### L8．中：恢复失败只锁定核心，秘密句柄和导出验证仍存活

- **位置**：`crates/keevo-core/src/vault.rs:1031`；`crates/keevo-ffi/src/backup.rs:135`；`crates/keevo-ffi/src/lib.rs:1162`；`crates/keevo-ffi/src/import.rs:241`；`apps/macos/Sources/KeevoUI/BackupSupport.swift:108`。
- **问题**：Vault 在逐行恢复之前先清 session；Store 恢复失败后，FFI 的 `?` 直接返回，后面的 KeevoVault::lock 没有执行。因此核心处于 Locked，已发出的 SecretValue、搜索/导入缓存和 reverified 却没有经过完整锁定清理。Swift 恢复错误分支也在调用 AppModel.lock 前返回。
- **前提**：用户已打开过秘密字段；备份通过初步结构/账户检查，但在逐行验证时失败。导出子情形还要求此前两分钟内签发过未消费的导出标记。
- **影响**：核心“已锁定”后，旧句柄仍可 expose 先前秘密；重新解锁后可消费旧会话的导出验证。攻击者仅制作备份不会自动收到明文，暴露边界是本机已持有句柄的调用方/界面，不能夸大为远程解密。
- **严重程度**：**中**，锁定后的秘密生命周期与敏感操作门槛不一致。
- **建议**：统一锁定状态转移；若失败要锁定，使用无论成功/失败都会执行的完整清理，通知界面状态变化。导出能力绑定 unlock_epoch，并在同一临界区校验/消费，避免只靠一个时间戳。
- **证据**：`review5_l8_failed_restore_clears_secret_handles` 确认 items 返回 Locked，但旧秘密句柄非空；`review5_l8_failed_restore_invalidates_export_reverification` 在失败恢复、再次解锁后未重新验证仍成功导出 JSON。两个期望安全行为的断言均失败。

## 6. 向作者提出的问题

1. **恢复年龄**：能否接受所有从不可信备份导入的内容从恢复时重新计算保留年龄？这会延后清理，但比使用未经认证的旧时间更容易维持“不提前清理”承诺。
2. **恢复失败状态**：选择保持原解锁状态，还是统一完整锁定？两种都可实现；需要使 core、FFI 句柄、搜索/导入缓存、导出能力和 Swift phase 一起变化。
3. **SSH 关闭策略的表示**：是否采用持久的显式 off/已迁移标记，并把它与旧属性清理或删除事务统一？仅删除本机记录无法区分撤销与尚未迁移。
4. **自有格式往返**：是否承诺除 export.md 明确列出的遗漏及变换外，合法本机条目经 Keevo JSON 往返保持字段值、名称与分区身份？建议以此约束 Builder 的来源专有规整行为。
5. **不可读附件与重建**：当前规则“读不出的附件不保留引用”会让重建成功时直接丢弃用户未显式选择删除的字段。是否至少返回未复制附件清单，要求用户明确接受；遇到暂时 I/O 错误是否应中止重建？这是对现有明确政策的确认，不作为本轮已复现的新漏洞。
6. **泄露检查的产品保证**：是否接受跨次交集分析这一残余风险，并将“查过/未查过”绑定到当前密码？是否计划为运行中的检查提供取消及响应体上限？本轮没有请求外部服务，也没有测量实际网络流量。
7. **独立导出向量**：是否把 S7 的跨实现已知答案列为本次冻结验收项？建议完成后连同 L1/L6/L8 的修复回归一起确认，再冻结导出格式。
