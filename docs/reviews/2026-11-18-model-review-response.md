## 4. 逐条处理

### 4.1 发现

#### F1：撤销配对不撤销已有会话 — 已确认，已修复

- **复现**：配对 → 填充成功 → 撤销 → 同一会话再次填充，修复前仍返回密码。
- **修复**（`crates/keevo-ipc/src/service.rs`、`crates/keevo-service/src/server.rs`）：
  - 会话层在处理**每个**请求前重新核对配对记录（公钥存在、来源一致），撤销后的请求返回 `not_paired` 并断开。这一层不依赖服务层的连接管理，不存在撤销与请求之间的竞态。
  - 服务层登记已建立的会话；`VaultService::revoke` 删除记录后立即 `shutdown` 该扩展的全部连接。登记前再核对一次，覆盖握手与撤销同时发生的情况。
  - `PairingStore` 增加 `revoke`，写盘失败时返回错误：内存中的撤销已经生效，但调用方必须提示"重启后可能失效"。
- **回答评审者的问题 2**：撤销由 Vault Service 执行。重新解锁不会恢复被撤销的配对，因为配对记录已删除，与锁定状态无关。

#### F2：父进程的当前签名不能证明 host 由浏览器创建 — 机制已确认，整链待验证

- **核实**：我们认可评审给出的机制：`parent_browser()` 检查的是父 PID **当前**运行的代码，fork→exec 可以在 PID 不变的情况下把父进程换成签名浏览器。评审已用 `/bin/sleep` 验证了这一步。
- **没有做的**：在真实 Chrome 与按发布方式签名（临时签名、固定 cdhash，ADR-0003）的 host 上验证完整攻击链。
- **处理**：
  - `spec/ipc.md` §3.2 明确父进程检查**只是纵深防御，不是身份证明**。协议改为假设落盘的扩展私钥可能被同用户进程读取并冒充。
  - 兜底措施按产品决定采用按站点授权（§3）。
  - `docs/security.md` A7、`docs/architecture.md` §6 同步更新。
- **回答评审者的问题 1**：正式版本目前**无法**证明管道属于指定扩展。在找到能绑定创建者身份、进程实例与通信端点的 OS 机制之前，安全性由按站点授权与频率限制保证，不由父进程检查保证。调研与整链验证列入 M1.3。

#### F3：未认证输入触发过大的资源开销 — 已确认，已修复

- **信封**：新增 `MAX_ENVELOPE_LEN = 42 + padded_len(4 + 16 MiB) + 16 = 17301562`，在 `body.to_vec()` 与认证**之前**检查（`crates/keevo-crypto/src/envelope.rs`），并用测试确认它与填充规则一致。
- **KDF**：区分格式上限与**本机自动执行预算**（1 GiB / t ≤ 10 / p ≤ 8，`spec/crypto.md` §5.3）。
  - 超出预算时 `Vault::unlock` 返回 `KdfNeedsConfirmation`，不执行派生。
  - 用户确认后改用 `unlock_confirmed_expensive_kdf`。
  - FFI 与 Swift 已能识别这个错误；确认界面放到 M1.1。
- **并发 KDF**：`unlock` 需要 `&mut Vault`，服务对 `Vault` 加了互斥锁，同一进程同一时刻只会执行一次。
- **文件入口的大小限制**：同步入口尚未实现，已写入 `docs/sync.md` §5 的接收流程。

#### F4：合并视图不满足结合律 — 已确认，实际影响高于评审判断

- **复现**：评审的反例（A′、B、C）。一次合并得到 C；先合并 B、C 并写成合并修订、再与 A′ 合并，修复前得到 A。
- **为什么影响更高**：评审认为当前"始终收集完整头集合"的路径不受影响。但写时收敛（`revisions.md` §5.4）会把合并结果写成修订，而同步时其他设备可能还没收到全部头，**分组合并在产品路径上会自然发生**，不只是实现者做增量合并时才有的风险。
- **修复**（多值寄存器）：
  - 条目详情新增**并发版本映射**（`concurrent`，`revisions.md` §4.3、`vault-format.md` §2）。合并时，当前版本放进 `records`，其余极大元放进 `concurrent`。
  - 合并结果因此是"各头版本并集的极大元"，满足结合律。
  - 写入某个键时清除该键的并发版本；用户可以用 `Vault::resolve_conflict` 选择保留某个版本。
- **随机检验**：300 组多设备模拟，每组都随机分组合并、写成合并修订，直到只剩一个头。每一步的合并状态都必须与一次合并全部头相同。
- **修复过程中发现的连带问题**（评审未报告）：
  1. **撤销删除时直接删掉 `attr:trashed`**，分组合并后更早的回收站版本会失去"已被覆盖"的信息而重新生效。改为把这些版本移入并发版本，不再作为当前值，但仍是之后合并的候选。
  2. **在"已撤销删除"的视图上编辑后，条目可能重新进入回收站**：如果引发撤销的那次并发修改后来被覆盖，删除就会重新生效。改为写时收敛先写入 `attr:trashed` 墓碑，把撤销确定下来（`ItemDoc::settle_for_write`）。回归测试：`restore_by_concurrent_edit_is_settled_when_written`。
  3. 冲突不再随编辑自动消失。单头条目的列表只解密概要，可能漏标冲突，因此概要新增 `conflicts` 标记。
- **随机检验暴露的两处语义**（已写入 `revisions.md` §5.3，不属于缺陷）：
  - `resurrected` 是对本次合并的提示：对象墓碑头并入合并修订后不再出现；
  - 合并结果为"已删除"时不写回。墓碑只由用户的永久删除写入。
- **回答评审者的问题 3**：结合律针对**合并状态**，即记录映射加并发版本映射。允许缓存或写回合并视图，但必须连同并发版本一起保存，不得只保存胜者。

#### F5：伪造记录出处破坏确定性 — 已确认，已修复

- **复现**：同一 `(rev, hlc)`、不同值，交换头的顺序得到不同结果；另构造了记录声称写于非祖先修订的情况。
- **修复**（`revisions.md` §5.1 步骤 0–1）：
  - 版本的 `rev` 必须是其所在头的祖先，否则丢弃；
  - 同一 `rev` 出现不同内容时，按 `(hlc, 值的规范 JSON)` 取最大者，保证结果与顺序无关；
  - 这两种情况都记为 `integrity_issues`，条目在列表中标出，提示用户查看历史；
  - 修订图中同一 `rev_id` 的元数据不一致时拒绝（`RevisionConflict`），不再"首次为准"。
- **回答评审者的问题 5**：
  - 出处与重复内容由合并层核对；
  - 父修订是否存在、`rev_id` 是否重复由存储层核对；
  - 设备签名、设备是否已登记、HLC 极值由 M2 的同步接收流程核对（`docs/sync.md` §5）。
  - 历史清理后如何继续验证真实性，列为 M2 未决事项（保留认证摘要）。

#### F6："不丢数据"的承诺与清理规则矛盾 — 已确认，已修复

- **复现**：评审的方法（21 次覆盖后旧标题消失）成立。
- **修复**：
  - **并发落选版本**保存在头修订的并发版本中，不受清理影响，直到用户处理。回归测试先制造冲突，再做 25 次无关编辑并模拟 90 天后的清理，确认落选版本最初所在的修订已被清理、落选值仍可取得、处理后冲突消失。
  - **顺序覆盖的旧值**：按产品决定改为"最近 20 个 + 90 天"。`keevo-store` schema v2 记录本机写入或收到每个修订的时间，并附带 v1 → v2 迁移与测试。
  - **承诺范围**：`revisions.md` §1、§7 与 `docs/product.md` 改为"保留期内可恢复"，不得承诺永久保留全部历史。
- **回答评审者的问题 4**：只承诺历史保留期内；并发落选版本必须由用户处理（编辑该字段或在冲突面板中选择）后才可能进入普通清理。

## 5. 回答评审者的问题

| # | 问题 | 回答 |

| 1 | 正式版本如何证明管道属于指定扩展？ | 目前无法证明。父进程检查降为纵深防御，安全性由按站点授权与频率限制保证（F2） |
