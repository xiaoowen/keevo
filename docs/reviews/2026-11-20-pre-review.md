## 1. 冻结结论

**结论：有条件可以冻结。**

**密码学构造站得住**：
- 附件的密钥层次与 AAD 绑定能防住无密钥攻击者的调换、截断、追加与跨附件、跨保险库、跨账户的移植；
- 导出文件的 Argon2id + HKDF + XChaCha20-Poly1305、AAD 覆盖全部头部，都没有问题。

**问题集中在两处**：
- 几条规范没有写清，或写法会在 M2 造成数据丢失；冻结后再改就要提升版本或迁移；
- 恢复与导入路径的实现。

## 2. 逐题回答

### A1 附件的绑定

**结论：担心不成立**——没有密钥的攻击者做不到。但有三个前提需要写进规范，另有一个拒绝服务。

**理由**：
- **三层上下文都绑定 `object_type = Attachment`、`account_id`、`vault_id` 与 `object_id = 附件 ID`**：
  - 被包裹的 AK；
  - 元数据（`part = Content`）；
  - 每块（`part = Chunk`，`part_index = i`，`binding = be32(n) ‖ Z(28)`）。
- **各种攻击都会被发现**：
  - **调换**：块序号不对，认证失败；
  - **截断**：`chunks` 来自已认证的元数据，存储中的块数与之不符；
  - **追加**：块数同样不符，而且 `binding` 中的 `n` 不同；
  - **删去最后一块**：同上；
  - **移植**：移到另一个附件或另一个账户时，`object_id` 或 `account_id` 不同；移到另一个保险库时，`vault_id` 不同；
  - **换到同一保险库的另一个条目**：元数据中的 `item` 不符，返回 `Tampered`。`crates/keevo-core/src/vault.rs:1425` 起的 `attachment_data` 先比对未认证的 `item_id` 列，再比对已认证的 `meta.item`，两者都核对。
  - 作者自己的测试已覆盖调换（`attachment.rs` 的 `add_read_tamper_and_collect`），我复核了代码路径。
- **`rev_id = 0` 目前没有问题**：AK 对每个附件随机生成，每个部分只封装一次。同一 (附件 ID, part, index) 只存在一个合法密文，因此谈不上"重放旧版本"。

**前提与遗留**：
1. **"每个部分只封装一次"没有写进规范**（K13）。将来若出现以下任一操作，`rev_id = 0` 就让新旧两份元数据都能通过认证，攻击者可以换回旧的一份：
   - 重新封装元数据，例如重建时迁移附件、改 `item`；
   - 用同一把 AK 重新封装块。
2. **持有 VK 的一方可以整体替换内容而不改动任何条目修订**：附件引用中没有内容承诺。这包括 M2 中已撤销、但在 VK 轮换前仍持有旧 VK 的设备。按 R2 的立场，已登记设备是可信的，但这一点应在冻结前决定（K13）。
3. **块长度只按通用信封上限检查，可以触发认证前的大块分配**（K3）：
   - 通用信封上限为 17,301,562 字节，而一块的合法信封至多 67,642 字节；
   - 800 块最坏约 12.9 GiB，全部读入内存之后才开始认证；
   - 证据：`r5_oversized_chunk_rejected_before_read`。

### A2 附件的回收与删除

**结论：担心成立。**
- 存在**永远不被删除**的路径：K5、K6；
- M1 中没有找到**提前删除**的路径；
- 但规范的写法会在 M2 造成提前删除（K14）。

**永远不删除的路径**：
- **重建条目**（`vault.rs:1589` 起的 `rebuild_item`）：
  - 把当前视图中的附件字段原样复制进新条目，引用指向的附件的 `item_id` 仍是旧条目，所以新条目里的附件读不出来（`NotFound`）；
  - 旧条目随即写墓碑，但它的附件既没有删除，以后也不会被回收：`collect_attachments` 只在旧条目的 `revise` 中调用，而旧条目已不能再编辑；
  - 内容永远留在数据库与以后的每一份备份中。这与 §8.9"条目永久删除时删除全部附件"不符；
  - 证据：`r5_rebuild_leaves_attachment_content`。
- **永久删除不是原子的**（`vault.rs:1567` 起的 `purge_item`）：
  - 先在一个事务中写墓碑，再逐个调用 `delete_attachment`（各自一个事务）；
  - 中间崩溃、断电或磁盘满时，条目已删除，附件永久残留；再调用 `purge_item` 会因为 `self.item()` 返回 `NotFound` 而直接退出；
  - 证据：`r5_failed_purge_leaves_attachments_forever`，用触发器注入第二步失败。
- **添加附件中断**（`vault.rs:1334` 起的 `add_attachment`）：
  - 先写附件，再 `update_item`；中间崩溃会留下孤儿附件，失败分支中的 `delete_attachment` 错误也被忽略；
  - 孤儿只会在这个条目下一次"清理了至少一个修订"时被回收（`revise` 中的 `if pruned > 0`），历史短的条目可能永远等不到。

**提前删除**：
- **M1 未发现**：`collect_attachments` 扫描全部未清理、非墓碑修订的当前版本与并发版本，并在清理之后执行；"恢复到此版本"、精简与冲突处理都不会让仍被引用的附件被删。
- **M2 有风险**：§5.2 允许永久删除被并发修改撤销（`resurrected`）。规范却写"条目永久删除时删除全部附件"，没有区分"删除成立且不会再被撤销"。同步引入后，一台设备的清空回收站会删掉另一台设备上被撤销删除的条目的附件（K14）。

**另外**：
- 删除附件字段后，内容至少保留 20 个修订与 90 天有效时间（通常约为日历时间的 3 倍），之后仍在最多 30 份备份中；
- 界面有说明，但没有"立即彻底删除这个附件"的办法。误附上了私钥文件的用户只能永久删除整个条目（K22）。

### V1 条目详情 v2

**结论：有条件成立。**

1. **同一内容只有一种合法编码：成立。**版本是内容的纯函数，再叠加规范编码，编码唯一。
2. **接受集合与 v1 的关系：接受集合严密，但错误码不严密。**
   - v1 读取方：对 `"v":2` 返回 `unsupported_version`，对含 `kind = attachment` 的 `"v":1` 文档返回 `malformed`。新旧读取方在这两种文档上一致。
   - 但对 `"v":1`、`kind = text`、数据是附件引用的文档，两边结果不同：
     - 1.0 的 v1 读取方返回 `malformed`：未知的 data 变体属于结构错误；
     - v2 读取方（Rust 与新的 Python 参考实现）返回 `value_kind_mismatch`。
   - 同一份 v1 文档的错误码随读取方版本变化，与"v1 的解码规则不变"不符。原因是 §2.5 的"是 attachment 字段"实际只看 `kind`（`crates/keevo-format/src/item.rs:201`；Python 的 `doc_version` 同样如此），没有写进规范，而 v2 向量 `text_kind_with_attachment_data` 把它固定了下来（K11）。
   - 证据：
     - `r5_v1_document_error_code_unchanged`；
     - 用 1.0 的 v1 参考实现（`git show b3c0ea5:spec/reference/format_vectors.py`）与当前参考实现逐条解码 v2 向量（`scripts/cmp_v1_v2.py`，见 §4）。
3. **v1 读取方遇到 v2 文档：行为符合 v1 的规则**（`unsupported_version`，而且在结构检查之前），也是安全的方向（读不了，不会误写）。
   - 后果需要写进规范与界面说明：条目一旦有附件（哪怕只在并发版本中），旧客户端连其中的密码都读不出，也不能编辑或合并这个条目。M2 多版本共存时这会是用户可见的行为。
4. **v1 与 v2 头修订混合时的合并：确定性成立。**
   - 合并按记录进行，结果文档的版本由合并后的内容决定，与输入顺序无关；同 `rev` 不同内容时比较的规范编码，对附件值也有定义。
   - 但没有任何合并向量或随机模拟包含附件字段：`revisions-v1.json` 与 `--self-test` 都只生成 `text` 字段。另一实现在"合并后版本降回 1"（附件字段被因果上更晚的墓碑覆盖）或"附件只留在并发版本中"这两种情形上算错时，没有向量能发现（K12）。

### E1 导出文件

**结论：有条件成立。**构造足够；口令策略不够；"重新验证"有绕过。

**构造足够**：
- Argon2id（参数沿用 crypto §5.1 编码与 §5.2 界限）→ HKDF（`info = "keevo/v1/export"`，与其他标签不同）→ XChaCha20-Poly1305；
- AAD 是全部 62 字节头部，篡改版本或 KDF 参数都会导致认证失败；
- 超出本机预算的参数在派生之前就被拒绝。

预算之内的恶意文件最多让导入花费 1 GiB 内存、t = 10，约十几秒，是用户主动操作，可以接受。

**次要问题**：
- **明文长度不填充**，文件大小直接反映导出内容的大小（建议）；
- **非密钥承诺的 AEAD** 在这里没有实际影响：离线文件，没有分区预言。

**"至少 10 个字符"太弱，应该按强度评估要求**（K4）：
- **导出文件去掉了 2SKD 中的账户密钥这一因子**：保险库的离线破解至少要面对 128 位的账户密钥，而导出文件只靠导出密码与一次 Argon2id（256 MiB、t = 3）。导出文件又恰恰最常放在不受控的地方：邮件、U 盘、网盘。
- **10 个字符的口令可以毫无保护作用**：实现只做 `chars().count() < 10`（`crates/keevo-core/src/export.rs:74`），10 个空格、`aaaaaaaaaa` 都被接受（`r5_export_rejects_trivial_password`）。
- **计数口径前后不一致**：Swift 按字素计数（`ImportExport.swift:451` 的 `password.count`），Rust 按 Unicode 标量计数，规范没有定义口径。
- **建议**：
  - 用已有的 `keevo_core::strength` 要求估计猜测次数 ≥ 10¹⁴ 左右，或至少 zxcvbn 风格的 4 分；
  - 更好的做法是默认生成随机口令（例如 6 个词的口令短语，约 77 位），并像应急包那样提示保存。

**"两分钟内重新验证、只能用一次"有绕过**（K15）：
- **机制本身没有问题**：`take()` 保证只用一次；锁定时清除；验证由主密码派生或 Touch ID 解开 AUK 完成，不能伪造。
- **加密导出不需要重新验证，而它对操作者等于明文导出**：导出密码由操作者自己选，拿到文件就能解开全部条目。作者测试中的注释写明了"加密导出不需要重新验证"（`crates/keevo-ffi/src/tests.rs`，`import_and_export`）。因此对"已解锁设备前的他人"这一类威胁，明文导出前的门槛被直接绕过。
- **验证标记不区分用途**：任何一次 `reverify` 都会调用 `note_reverified`（`crates/keevo-ffi/src/lib.rs:1580` 起），例如解除浏览器配对、开发者设置、重新保存应急包前的验证，之后两分钟内都可以明文导出。

### B1 恢复与本机状态

**结论：担心成立。**保留恢复前的 `meta` 与 `local_record` 的思路是对的，但实现与周边引入了新问题；"只接受同一账户的备份"不够。

1. **备份文件的结构不经任何校验就整体进入当前数据库**（K1，高）：
   - 恢复使用 SQLite 在线备份接口逐页复制，备份文件中的 schema 对象（触发器、视图、索引）连同所有明文列原样成为当前数据库的一部分。明文列包括 `head`、`parents`、`pruned`、`stored_ms`、`attachment.item_id` 等。
   - "同一账户"的检查只比对明文的 `account.id`。
   - 界面明确建议把备份文件夹放在"同步盘中的文件夹"（`BackupSupport.swift`），所以能写入这个文件夹、没有任何密钥的存储提供方（在威胁模型范围内）可以在备份中加一个触发器。
   - 实测：恢复后，编辑返回成功但条目消失，新建的条目也看不到（`r5_restore_rejects_foreign_schema_objects`）。
2. **恢复不是原子的**（K2）：
   - 在线备份接口先提交整个替换，之后才在另一个事务中写回恢复前的 `meta` 与 `local_record`（`crates/keevo-store/src/lib.rs:840` 起）；
   - 两步之间崩溃、断电、磁盘满，或者备份中有一个触发器，都会让数据库停在"备份内容 + 备份中的本机状态"：已撤销的配对重新生效，恢复前新增的配对丢失；
   - 这与 store 的文档注释"替换失败时数据库保持原样"以及 sync.md"在一个事务中替换"都不符；
   - 证据：`r5_failed_restore_keeps_revoked_pairing_revoked`。
3. **HLC 与设备 ID：没有问题。**
   - `meta` 保留下来，内存中的 `HlcClock` 也不变；
   - 合法备份中的 HLC 不会大于恢复前的值，之后的写入仍单调；设备 ID 不变也合理。
4. **有效时间与清理：对合法备份不会提前清理，对被篡改的备份可以。**
   - 实现中有效时间不在 `meta` 中，而是取 `max(stored_ms)`（`Store::effective_now`）。恢复后它回退到备份时的值，清理只会更晚。这与 sync.md 说的"有效时间保持恢复前的内容"不符，但方向安全。
   - 被篡改的备份可以把某个修订的 `stored_ms` 改到接近 2⁵³。下一次编辑时，除最近 20 个之外的历史全部被清理，只被这些历史引用的附件随之回收（K1 的变体）。
5. **已撤销的授权以其他方式复活：成立**（K17）。
   - SSH Agent 的授权策略 `attr:ssh_agent` 存在条目里，而不是本机记录中，会随旧备份回退。例如用户已经把某把密钥从 `unlocked` 改回 `ask`，或者从 Agent 中移除，恢复旧备份后它又以 `unlocked` 自动签名。已永久删除的（例如泄露后作废的）SSH 密钥也会复活。
   - 恢复旧备份同时会让主密码与 KDF 参数回到旧的 `epoch`：用户可能正是因为旧主密码泄露才修改了它，旧主密码又能解锁了。界面只提示"用备份时的主密码解锁"，没有说明这是一次口令回退。
   - 备份的时间只来自文件名（`backup.rs:133` 起的 `list`），改个名字就能把一份旧备份伪装成"今天的自动备份"。
6. **备份的清理只按文件名中的时间排序**（K7）：
   - 文件夹中有 30 个"未来时间"的文件时，每次备份之后的清理都会立即删掉刚创建的真实备份，界面却显示有 30 份。这些文件可能来自同步盘中的他人，或曾经错误的系统时钟。
   - 外部文件夹中别的账户的备份也会被计数，并被删除。
   - 证据：`r5_prune_keeps_newly_created_backup`。

**"只接受同一账户的备份"是否足够：不够。**至少还需要：
- schema 与列长度的完整校验，或者按已知表与列逐行导入一个由 Keevo 自己建的新库；
- 整体原子替换；
- 提示 `epoch` 回退；
- M2 中对备份文件做认证，例如用 ASK 派生的密钥对整个文件做 MAC，并记录可信的创建时间与最大 `epoch`。

### I1 不可信的导入文件

**结论：担心成立。**
- 没有找到 panic：zip 读取、CSV、1PUX、Bitwarden 的所有下标都经过 `get` 与 `checked_add`，数值转换都有检查；
- 但存在过量内存、过量 CPU 与静默改变字段的问题。

- **zip**：
  - CRC-32、声明大小与解压后大小都有核对；
  - Deflate 解压有上限（`decompress_to_vec_with_limit`），能防住传统意义上的解压炸弹；
  - 遇到 ZIP64 或加密条目时拒绝；同名条目取第一个（建议在规范或注释中写明）。
- **过量内存**（K10）：
  - 上限只限制了解压后的字节数（1PUX 为 256 MiB），而 `serde_json::Value` 每个节点至少 32 字节，再加上 `Vec` 增长时的重新分配。
  - 实测：31 KiB 的 1PUX 展开为 32 MiB 的 `export.data`，进程峰值 644 MB。按比例，约 250 KiB 的文件就能把内存推到约 5 GiB。
  - Bitwarden 与 Keevo 的 JSON 文件上限为 512 MiB，同样整体解析为树。
  - `MAX_ITEMS` 在全部条目都构造完之后才检查。
- **过量 CPU**（K9）：
  - `Builder::section` 与 `Builder::tag` 用线性查找去重，而且分区与标签都没有个数上限，`MAX_FIELDS` 只限制字段。
  - 实测（release）：16 万个分区名的 1.4 MiB 文件解析需要 14.6 秒，耗时随个数平方增长；512 MiB 的文件上限允许远多于此。
  - 证据：`r5_import_sections_are_bounded`。
- **静默改变或丢失字段**（K8）：
  - `Builder::add` 对除多行文本与 SSH 私钥之外的值一律 `trim`（`import/mod.rs:380`），首尾有空格的密码被静默改变，连 Keevo 自己的导出再导入也是如此（`r5_export_import_round_trip_keeps_password`）。product.md §5.7 承诺"字段保留"。
  - 一个条目超过 1000 个字段时，多出的字段被静默丢弃。
  - "与已有登录完全相同的跳过"实际只比较主机（去掉 `www.`，忽略协议与端口）、用户名与密码，导入条目中的一次性密码、备注与其他字段随之被跳过。
  - Bitwarden 的 `passwordHistory`、`fido2Credentials`，1PUX 的密码历史与 `reference` 字段被静默丢弃；`archived` 不在 Keevo 导出中。
- **Bitwarden 的 KDF 上限：合理**：
  - PBKDF2 ≤ 200 万次；Argon2id ≤ 1024 MiB、10 次、并行度 16。这与 Bitwarden 自身允许的范围一致：PBKDF2 60 万–200 万，Argon2id 15–1024 MiB、2–10 次、1–16。
  - 但 Bitwarden 的 Argon2id 直接调用 `argon2` crate，没有经过 `KdfParams::argon2id` 中的进程级互斥（crypto §5.3"同一进程内的 KDF 一律串行"），可以与解锁同时占用 1 GiB 以上内存（K21）。

### H1 泄露检查

**结论：担心成立。**k-匿名与填充挡住了"哪个密码"，但挡不住以下这些。

对 HIBP 运营方（Cloudflare）：
1. **保险库中不同密码的个数**：每个不同的 SHA-1 前缀发一次请求；在 2²⁰ 个前缀中，几千个密码以内几乎不会重合，所以请求数约等于密码数。
2. **一个稳定的指纹**：每次完整检查发出的前缀集合基本相同，可以跨 IP、跨时间把同一个用户关联起来。
3. **哪个密码在什么时候改过**：两次检查之间前缀集合的差异暴露这一点，精确到检查的时间。
4. **针对性猜测的线索**：每个前缀泄露密码 SHA-1 的 20 位。运营方手里有用户的候选口令时（例如这个用户在其他站点泄露过的密码及其变体），可以确认或缩小范围，这是 k-匿名方案已知的局限（Li 等，CCS 2019；Pal 等，2022）。
5. **"忽略这个条目的提醒"的条目照样被查询**（`security.rs` 的 `prepare` 只排除回收站与归档）。

对网络观察者：
- `fetchRange` 每个请求都新建 `URLSession(configuration: .ephemeral)`（`SecurityCenter.swift:99`），每个前缀一个新的 TCP + TLS 连接，连接数就等于密码数。
- 请求路径长度固定，响应有填充，这两点没有泄露。

是否需要缓解：需要，而且成本很低（K16）：
- 每次加入随机的伪前缀，把总数补到固定档位，例如向上取到 64 的倍数，或固定的最小值；
- 打乱顺序，复用同一个连接；
- 每次都查询全部前缀与伪前缀，不做增量查询，否则改密码的时机更明显；
- 让"忽略提醒"的条目也不被查询，或者在开关旁说明；
- governance.md §5 的表中补上"同时会泄露密码个数，以及多次检查之间的变化"。

## 3. 发现列表

严重程度按 REVIEW.md §7。"证据"中的测试都在 `r5_tests.rs` 中，结果见 §4。

### K1 恢复时，备份文件中的 schema 对象与未认证的明文结构原样进入当前数据库（高）

- **位置**：
  - `crates/keevo-store/src/lib.rs:810–878`（`inspect_backup`、`restore_from`）；
  - `crates/keevo-core/src/vault.rs:955–975`；
  - `crates/keevo-core/src/backup.rs:215`；
  - `apps/macos/Sources/KeevoUI/BackupSupport.swift`：选择文件夹时的提示"例如外部硬盘或同步盘中的文件夹"；
  - `docs/sync.md` §2。
- **问题**：
  - 备份是一个普通的 SQLite 文件。校验只有三项：`user_version` 不大于当前版本、不为 0，存在 `account` 行，`account.id` 等于当前账户，而这一列是明文。
  - 随后用在线备份接口逐页复制，`sqlite_master` 中的一切都进入当前数据库，包括触发器、视图、被改写的表定义。所有未认证的明文列也一并进入：`head`、`parents`、`deleted`、`pruned`、`stored_ms`、`attachment.item_id`、`chunk_count`。
  - 打开时没有启用 `SQLITE_DBCONFIG_DEFENSIVE`，也没有设置 `trusted_schema = OFF` 或做 `integrity_check`。
- **前提**：攻击者能写入备份文件夹，例如同步盘的提供方，或同一网盘的其他使用者；用户从这个文件夹恢复。攻击者不需要任何密钥：拿一份真实的备份，往里加 SQL 即可。
- **影响**：
  - 实测：加一个触发器 `AFTER INSERT ON head BEGIN DELETE FROM head WHERE rev_id = NEW.rev_id; END`。恢复之后，`update_item` 返回 `Ok`，但条目随即消失；`create_item` 返回 `Ok`，但列表为空。此后的每一次编辑都会静默丢失。
  - 同类手段（推断，未逐一测试）：
    - `BEFORE DELETE ON local_record … RAISE(IGNORE)` 让"解除配对"变成空操作，已撤销的扩展继续有效；
    - 改写 `head` 把单个条目回滚到旧修订，例如回退一次改密码；
    - 把 `stored_ms` 改到接近 2⁵³，触发全部历史的清理与附件回收；
    - 把 `account` 换成递归 CTE 的视图，会卡住在主线程同步调用的 `backupProblem`。
  - 按 §7"静默篡改数据"可以归为严重；这里需要用户执行恢复这一步，所以定为**高**。
- **建议**：
  - 不要对外来文件使用页级复制。先以只读、`SQLITE_DBCONFIG_DEFENSIVE`、`trusted_schema = OFF` 打开，比对 `sqlite_master` 与这个 `user_version` 应有的 schema（名称与 SQL 文本完全一致，不允许多余对象），并运行 `PRAGMA integrity_check`。
  - 再在一个由 Keevo 自己建立的新库中，按已知的表与列逐行 `INSERT … SELECT`，同时检查每列的长度与取值（与 §8.5 的读取检查相同），最后整体原子替换（同时解决 K2）。
  - 恢复后从修订图重算 `head`，而不是信任备份中的 `head` 表。
  - M2 考虑用 ASK 派生的密钥对整个备份做认证。
  - 在 sync.md §2 写明备份文件的完整性边界。
- **证据**：`r5_restore_rejects_foreign_schema_objects`，失败。输出：

  ```
  恢复被篡改的备份：Ok
  编辑返回 Ok，之后读取条目 = Err(NotFound)
  新建返回 Ok，列表中的条目数 = 0
  ```

### K2 恢复分两个事务，中途失败会让已撤销的配对重新生效（中）

- **位置**：
  - `crates/keevo-store/src/lib.rs:840–878`；
  - `docs/sync.md` §2"在一个事务中替换"；
  - store 文档注释"替换失败时数据库保持原样"。
- **问题**：`Backup::run_to_completion` 提交之后，才在另一个事务中删除并写回恢复前的 `meta` 与 `local_record`。
- **前提**：第二步失败。可能的原因有：崩溃、`kill -9`、断电、磁盘满、`SQLITE_BUSY`，或备份中的触发器（K1）。
- **影响**：
  - 数据库停在"备份内容 + 备份中的 `meta` 与 `local_record`"；
  - 已撤销的浏览器配对、命令行与 SSH 授权重新生效，恢复前新增的配对丢失；
  - 这恰好是保留本机状态这一设计要防止的结果；
  - `restore` 返回错误，但内容已经被替换了。
- **建议**：先把备份复制到临时库，在临时库中写入当前的 `meta` 与 `local_record`，最后用一次在线备份把临时库替换进主库。也可以在一个连接中 `ATTACH` 之后，在单个事务中完成全部步骤。
- **证据**：`r5_failed_restore_keeps_revoked_pairing_revoked`，失败。输出：

  ```
  恢复返回 Err(Store(Sqlite("r5")))
  之后的配对记录 = ["pk-old"]
  ```

  已撤销的 `pk-old` 回来了，新增的 `pk-new` 丢失。

### K3 附件各部分只按通用信封上限检查，可以在认证前读入约 12.9 GiB（中）

- **位置**：
  - 规范：`spec/crypto.md` §8.9，没有给出各部分的长度；
  - 实现：`crates/keevo-store/src/lib.rs:935–1000`（第 957 行 `length(ct) > MAX_ENVELOPE_LEN`）；`insert_attachment` 同样如此。
- **问题**：
  - 各部分的合法长度：
    - 一块：至多 42 + Padmé(65540) + 16 = 67,642 字节，非最后一块恰好是这个长度；
    - 被包裹的 AK：恰好 314 字节；
    - 元数据：很小。
  - 但存储层对每块、元数据与被包裹的 AK 都只检查是否不超过 17,301,562 字节，然后把全部块读进一个 `Vec<Vec<u8>>`，之后才开始逐块认证。
- **前提**：能写入数据库或备份。数据库可由本机同一用户的进程写入；备份可经 K1 的路径写入。
- **影响**：
  - 800 块 × 17.3 MB ≈ 12.9 GiB，打开附件即可耗尽内存、使应用崩溃；
  - 违反 §8.5"防止未认证的输入触发大块内存分配"的意图；
  - M2 中附件进入同步文件夹后，所有读取方都需要这条上限，因此属于格式。
- **建议**：按 S1 把各部分的精确长度写进 §8.9，读取方在读入之前、在同一快照中检查：

  ```
  非最后一块      = 67642
  最后一块        ≤ 67642
  wrapped_key    = 314
  meta           ≤ 定值
  ```

- **证据**：`r5_oversized_chunk_rejected_before_read`，失败：4 MiB 的块，`store.attachment()` 返回 `Ok`。

### K4 导出密码只要求 10 个字符，导出文件去掉了账户密钥这一因子（中）

- **位置**：
  - `spec/export.md` §1、§3；
  - `crates/keevo-core/src/export.rs:73–76`；
  - `apps/macos/Sources/KeevoUI/ImportExport.swift:449–453`。
- **问题**：
  - 不评估强度：10 个空格、`aaaaaaaaaa` 都被接受；
  - 计数口径不一致：Swift 按字素，Rust 按标量。
- **前提**：导出文件落入他人之手，这正是导出文件最常见的风险。
- **影响**：
  - 保险库的离线破解需要 128 位的账户密钥，导出文件只需猜导出密码；
  - 用户自选的 10 字符口令常在 2³⁰–2⁴⁰ 次猜测以内，每次猜测只需一次 256 MiB 的 Argon2id。
- **建议**：
  - 默认生成随机的导出口令短语，至少 6 个词；
  - 用户自选时用 `strength::estimate` 设下限，例如估计猜测次数 ≥ 10¹⁴；
  - 写明计数在 NFKD 之后、按 Unicode 标量计算；
  - 拒绝全是空白的口令。
- **证据**：`r5_export_rejects_trivial_password`，失败：两种口令都返回 `Ok`。

### K5 重建条目留下悬空的附件引用，旧附件内容永不回收（低）

- **位置**：`crates/keevo-core/src/vault.rs:1589–1621`（`rebuild_item`）；`spec/crypto.md` §8.9"已知限制"与"删除"。
- **问题**：
  - 规范写"附件引用不随之迁移"，实现却把附件字段复制进新条目。新条目里的附件读不出来，因为附件属于旧条目。
  - 旧条目写墓碑后，它的附件既不删除，也不会再被 `collect_attachments` 处理。
- **前提**：条目超出键数或头数上限，需要重建。键数可能因反复添加、删除附件而达到 4096。
- **影响**：
  - 秘密内容（密文）永久留在数据库与以后的每一份备份中；
  - 这些附件经 `attachment_data(旧条目, ID)` 仍能解密，用的是旧条目墓碑头上的 `vault_id`；
  - 新条目中的附件显示正常，打开时才失败。
- **建议**：
  - 重建时不复制附件字段；或者在同一事务中为新条目重新封装元数据，使用新的附件 ID（见 K13，不要重用 ID）；
  - 同一事务中删除旧条目的全部附件。
- **证据**：`r5_rebuild_leaves_attachment_content`，失败：

  ```
  新条目中的附件引用 [d933…]
  读取 = NotFound
  旧条目残留的附件 1
  ```

### K6 永久删除与添加附件都不是原子的，会留下永不回收的附件（低）

- **位置**：`crates/keevo-core/src/vault.rs:1567–1581`（`purge_item`）、`1398–1416`（`add_attachment`）。
- **问题**：
  - `purge_item`：墓碑与附件删除不在一个事务中，第二步失败后再也没有路径回收。
  - `add_attachment`：先写附件，再 `update_item`；失败时清理附件的错误被忽略，崩溃时的孤儿只在下一次"清理了至少一个修订"时才被回收。
- **前提**：两步之间崩溃、断电或 I/O 失败。
- **影响**：秘密内容的密文永久残留，并随备份复制。
- **建议**：
  - 墓碑与附件删除放在同一个事务中，`Store` 提供一个组合操作；
  - 打开数据库时清扫两类附件：所属条目已永久删除的，以及不被任何修订引用的。
- **证据**：`r5_failed_purge_leaves_attachments_forever`，失败：

  ```
  第一次 Err(Store(Sqlite("r5")))
  第二次 Err(NotFound)
  条目已删除 = true
  残留附件 1
  ```

### K7 备份清理按文件名中的时间排序，未来时间的文件让真实备份被立即删除（低）

- **位置**：`crates/keevo-core/src/backup.rs:133–209`（`list`、`prune`、`auto_due`）。
- **问题**：
  - 列表与清理只解析文件名，不检查内容，也不检查属于哪个账户。
  - 30 个名为 `keevo-2099…-auto.keevo-backup` 的文件就会让每次新建的备份在清理时被删掉。`auto_due` 还会因为"未来时间"认为每次都到期。
  - 外部文件夹中别的账户的备份也会被计数并删除。
- **前提**：备份文件夹在同步盘上被他人写入，或曾经的系统时钟错误。
- **影响**：
  - 用户实际上没有新的备份，界面却显示有 30 份；
  - 共享文件夹中别的账户的备份会被删除。
- **建议**：
  - 清理永远不删除刚创建的那份；
  - 对时间晚于当前时间的文件只提示，不参与排序与清理；
  - 只清理检查过属于本账户的文件；
  - 每个账户使用单独的子文件夹。
- **证据**：`r5_prune_keeps_newly_created_backup`，失败：清理删除 1 份，刚创建的备份不在了。

### K8 导入会静默改变或丢弃字段（低）

- **位置**：
  - `crates/keevo-core/src/import/mod.rs:352–389`：`Builder::add` 中的 `trim`、`MAX_FIELDS`；
  - `248–296`：`duplicates`；
  - 各来源的解析器。
- **问题**：
  - 首尾有空格的密码、令牌被 `trim`；
  - 超过 1000 个字段的部分被丢弃；
  - 重复判定只看主机、用户名与密码，被跳过的条目可能带有已有条目没有的一次性密码与备注；
  - 密码历史、通行密钥、引用字段、`archived` 被丢弃，预览中没有任何说明。
- **前提**：正常导入，不需要攻击者。
- **影响**：
  - 导入后密码静默错误，登录失败，用户却以为导入完整；
  - 连 Keevo 自己的导出再导入也会改变密码；
  - 与 product.md §5.7"字段保留"不符。
- **建议**：
  - 秘密字段与 Keevo 自己的格式一律不 `trim`，只对标题、标签名与网址做规范化；
  - 超出上限时报错，或在预览中列出被丢弃的内容；
  - 重复判定要求全部字段相同，或在预览中显示"将跳过，但它有已有条目没有的字段"。
- **证据**：`r5_export_import_round_trip_keeps_password`，失败：导出前是 `"  correct horse battery  "`，导入后是 `"correct horse battery"`。

### K9 导入时分区与标签的去重是平方复杂度，且没有个数上限（低）

- **位置**：`crates/keevo-core/src/import/mod.rs:340–350`（`section`）、`434–439`（`tag`）；`keevo.rs:101`；`onepux.rs:195`。
- **问题**：
  - 分区和标签都用线性查找去重，没有个数上限；
  - 1PUX 中即使字段已满 1000 个，`section()` 仍然对每个字段都会调用。
- **前提**：用户导入一个恶意文件。
- **影响**：
  - 文件约 1.5 MB 就需要 15 秒，10 MB 量级需要数十分钟 CPU；

- **建议**：
  - 分区与标签的个数设上限，例如与 `MAX_FIELDS` 相同，超出时报 `too_large`；
  - 用 `HashMap` 去重。
- **证据**：`r5_import_sections_are_bounded`，失败。release 构建的耗时：

  | 分区个数 | 文件大小 | 耗时 |

  | 1 万 | 77 KiB | 0.10 s |
  | 2 万 | 165 KiB | 0.23 s |
  | 4 万 | 340 KiB | 1.13 s |
  | 16 万 | 1454 KiB | 14.62 s |

### K10 导入的内存放大：压缩文件经 `serde_json::Value` 可以放大约 20 倍（低）

- **位置**：
  - `crates/keevo-core/src/import/onepux.rs:25–27`；
  - `bitwarden.rs:27–35`；
  - `import/mod.rs:195–211`：`MAX_ITEMS` 在解析完成之后才检查。
- **问题**：只限制了解压后的字节数，没有限制解析树的大小与条目数。
- **前提**：用户导入一个恶意文件。
- **影响**：约 250 KiB 的 1PUX 可让进程占用约 5 GiB，导致崩溃。
- **建议**：

### K11 v2 的版本判定只看 `kind`，同一份 v1 文档在新旧读取方得到不同的错误码（低；冻结前修改规范）

- **位置**：

- **问题**：
  - 规范没有说明"attachment 字段"是指 `kind` 还是数据形态；两个实现都只看 `kind`。

### K12 §8.9 没有测试向量；元数据编码与一致性未定义（低；冻结前修改规范）

### K13 `rev_id = 0` 依赖未写明的"只封装一次"前提；附件引用没有内容承诺（低；冻结前决定）

- **位置**：`spec/crypto.md` §8.9；`spec/vault-format.md` §2.5 的附件引用结构。
- **问题**：
  - 附件的三个部分不带修订信息，正确性完全依赖于"每个部分只用同一把 AK 封装一次"。规范没有这样要求。
  - 附件引用只有 `id`、`name`、`size`、`added`，没有内容承诺。任何持有 VK 的一方都可以用新的 AK 在同一 ID 下封装完全不同的内容，读取方无从发现。持有 VK 的一方包括：已登记设备，以及 M2 中已撤销、但在 VK 轮换前仍持有旧 VK 的设备。
- **影响**：
  - 将来的迁移（重建、换条目 ID、重新封装元数据）会让新旧版本都通过认证，可以互相替换；
  - M2 的附件同步无法单凭条目修订确认内容就是当初附上的那份；
  - 引用结构冻结之后再加字段需要 v3。
- **建议**：
  - 在 §8.9 写明"只封装一次，任何改变使用新的附件 ID 与新的 AK"；
  - 在引用中加入 `sha256`（明文的 SHA-256，随条目详情一起加密，不额外泄露），读取时核对。即使决定不加，也应在规范中记录理由。
- **证据**：阅读规范与代码。

### K14 回收规则的写法在 M2 会造成附件的提前删除（低；冻结前修改规范）

- **位置**：`spec/crypto.md` §8.9"删除"；`spec/revisions.md` §5.2、§6、§7.2。

### K15 "明文导出前重新验证"可被加密导出绕过；验证标记不区分用途（低）

- **位置**：

### K16 泄露检查泄露密码个数、前缀集合与修改时机（低）

### K17 恢复会回退 SSH Agent 策略、主密码与 KDF 参数；备份时间可被伪装（低）

- **位置**：
  - `crates/keevo-core/src/backup.rs:133–157`；
  - `spec/ssh-agent.md` §4.1（`attr:ssh_agent` 在条目中）；
  - `BackupSupport.swift` 的 `restore`；
  - `docs/sync.md` §2"有效时间"。
- **问题**：

  - 账户行（`epoch`、KDF 参数、密钥集）回到旧值，用户已经废弃的主密码重新有效；
  - 备份的"时间"只来自文件名；

### K18 CSV 导出没有防公式注入（低）

- **位置**：`crates/keevo-core/src/export.rs:218–262`；`spec/export.md` §4。
- **问题**：以 `=`、`+`、`-`、`@` 开头的值原样写出。网页通过扩展的"保存"可以影响用户名或标题等字段。
- **前提**：用户把明文 CSV 用电子表格打开，并点击了公式生成的链接。

### K19 附件的明文元数据暴露哪些条目有附件及其大致大小（低）

### K20 导出与导入规范中没有写清的地方（建议）

- **位置**：`spec/export.md`。
- **问题**：
  - **未知成员**：Rust 的 serde 默认忽略，与"v1 没有扩展点"的原则不一致，而规范没有写；
  - **`value`、`entries`、`codes` 出现多个时**：实现取第一个；
  - **`kind = attachment` 或 `kv_list` 却带 `value` 时**：整次导入失败，规范没有定义；
  - **`archived`、`ssh_agent`、`security_alerts`**：不导出，没有写明；
  - **口令的计数口径**：没有定义；
  - **写出方 KDF 参数与读取方预算的关系**：crypto §5.2 允许客户端上调默认值。若写出方上调到另一台设备的预算之外，对方会直接拒绝这个文件。应规定写出方必须使用 §5.2 的默认值，或使用不超过最低预算的值；
  - **测试向量**：没有独立实现生成的导出向量。
- **建议**：按 S7 补齐。

### K21 Bitwarden 的 Argon2id 不经过进程级 KDF 互斥；读取文件前后存在大小检查的竞态（建议）

- **位置**：
  - `crates/keevo-crypto/src/bitwarden.rs:74–97`，对照 `kdf.rs:158–162`；
  - `crates/keevo-ffi/src/import.rs:111–119`；
  - `crates/keevo-ffi/src/attachment.rs:30–39`。
- **问题**：
  - Bitwarden 的 Argon2id 可以与解锁并发执行，违反 crypto §5.3"同一进程内的 KDF 一律串行"；
  - FFI 先 `metadata` 检查大小再 `fs::read`，文件在两步之间变大时，读入没有上限。
- **建议**：
  - Bitwarden 的派生也经过同一把互斥锁；
  - 用 `File::open` 打开后，基于同一个句柄检查大小，并用 `take(limit + 1)` 读取。

### K22 秘密的残留（建议）

- **明文导出的临时文件**（`import.rs:271–292` 的 `write_new_file`）：
  - 临时文件是 `.<名称>.keevo-tmp`，写在用户选择的目录中，例如桌面；
  - 崩溃后它作为隐藏文件留下全部明文；
  - 下次导出时 `create_new` 会因为文件已存在而失败。附件的写法会先删除残留，这里没有。
- **附件预览**：明文写在数据目录的 `preview` 中，结束时删除，但不是安全删除；Quick Look 可能缓存缩略图。
- **WAL**：`secure_delete` 只覆盖主库页，WAL 中更早写入的帧在被覆盖之前仍有已删除附件的密文。
- **已删除的附件**：在 30 份每日备份中再留存一个月。每份备份都是完整副本，50 MiB 级的附件乘以 30 份，磁盘占用会增长很快。
- **建议**：
  - 导出先清理残留的临时文件；
  - 提供"立即彻底删除附件"：删除字段，并重写引用它的历史修订，或标记为清理；
  - 备份的保留策略按总大小控制；
  - 在 security.md 中记录上述残留。

### K23 块的 AAD 中带 `vault_id`，跨保险库移动需要重新加密全部块（建议，冻结相关）

- **位置**：`spec/crypto.md` §8.9 的 `ctx`。
- **问题**：
  - 块与元数据已经由只有 VK 才能解开的 AK 保护，`vault_id` 进入块的 AAD 并不增加安全性；
  - 但它让"把条目移到另一个保险库"必须重新封装最多 800 块，而不只是重新包裹 AK。
- **建议**：若 M2 计划支持跨保险库移动（共享保险库时很可能需要），冻结前考虑只在被包裹的 AK 中绑定 `vault_id`，块与元数据只绑定附件 ID。或者在规范中写明，移动即复制为新附件。

## 5. 向作者提出的问题

1. **备份的完整性**：界面建议把备份放在同步盘中，M2 之前是否打算对备份做认证（例如用 ASK 派生的密钥对整个文件做 MAC，并记录创建时间与 `epoch`）？还是只做 schema 校验与逐行导入？这决定 K1 修复的范围。
2. **附件在 M2 的形态**：附件在 M2 是否作为独立的同步对象？如果是，K13 的内容承诺与"只封装一次"、K14 的回收条件，以及 K23 的 `vault_id` 绑定，都应在这次冻结前定下来。
3. **重建时的附件**：重建条目时复制附件字段，是有意让用户看到"附件打不开"吗？规范写的是不迁移。
4. **导出口令**：导出是否考虑默认生成随机口令，或允许把账户密钥作为第二因子？
5. **泄露检查的范围**："忽略这个条目的提醒"的条目，是否应该同时排除在泄露查询之外？
6. **SSH Agent 策略的归属**：export.md 把"SSH Agent 的授权与策略"列为本机状态，`attr:ssh_agent` 却存在条目中，会随同步与备份流动。哪一种是预期？这决定 K17 的处理方式。
