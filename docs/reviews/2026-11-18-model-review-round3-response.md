## 2. 产品决定

| 问题 | 决定 |
|---|---|
| 精简也无法恢复的极端状态（H2） | **提高上限，超出时只读并可重建**：普通修订的父修订上限从 256 提高到 4096，每个条目最多 4096 个记录键。超出时条目只读，可以导出或重建为新条目。M2 引入设备日志后，在所有设备都已体现某个墓碑时回收它 |
| 90 天怎么计时（H1） | **按 Keevo 的累计运行时间**：用进程的单调时钟计时，关机、睡眠、Keevo 未运行的时间都不计，墙上时钟不参与。保证不会早于真实经过的 90 天清理；代价是通常保留得更久 |

## 3. 冻结前必须解决的四件事

| 评审要求 | 处理 |
|---|---|
| 1. 大小策略的闭合性（H2） | 规范给出上限表，并证明上限之内"处理全部冲突并删除全部字段"一定放得进一个信封：最坏情况约 6.3 MiB，有测试锁定这个界限。超出上限时只读，可重建；墓碑修订的父修订上限为 65,536，保证重建之后旧条目总能被永久删除 |
| 2. 删除状态的合法表示与纯合并的适用范围（H4） | 客户端不能写入或删除 `attr:purged`；解码只接受规范允许的两种形态。§5.3 写明只有未删除的中间结果可以写回，并改正了 `resurrected` 生命周期的描述 |
| 3. 规范编码与解析边界（H7） | 规范编码只用于单个记录版本的值，墓碑编码为 `null`，`val: null` 与省略等价；整数范围同样适用于概要；写入前重新校验全部不变量 |
| 4. 共享格式与本机包裹格式分开 | `crypto.md` §8.6 明确单独保持草案、M1.1 定稿，并补齐评审列出的各项：各用途的明文布局、ECDH 输出、公钥检查、长度上限、可访问性、各用途的恢复、用户取消、`device_id` 变化时的重新包裹顺序 |

## 4. 逐条处理

| 编号 | 评审给出的级别 | 结论 | 处理 | 回归测试 |
|---|---|---|---|---|
| H1 有效时间会被时钟往返反复推进；元数据缺失或损坏时不保守 | 中 | **已确认** | 有效时间改为累计运行时间：进程首次使用时以已有修订的最大保存时间为起点，此后按单调时钟推进。不再有任何时钟元数据，因此元数据缺失、损坏、只写一半的情形都不复存在。保存时间超出合理范围时暂停清理 | `review3_h1_retention_follows_running_time_only`、`review3_h1_restart_does_not_count_downtime`、`review3_h1_unreasonable_stored_time_pauses_pruning` |
| H2 合法状态既无法保存、也无法精简恢复 | 中 | **已确认** | 见 §2 与 §3。新增 `CoreError::ItemNeedsRebuild` 与 `Vault::rebuild_item` | `review3_h2_parent_limits_depend_on_revision_kind`、`review3_h2_item_beyond_key_limit_must_be_rebuilt`、`review3_h2_all_tombstones_within_key_limit_fit_one_envelope` |
| H3 长度预检与读取不在同一快照；元数据与头表入口未限长 | 低 | **同意** | 读取修订、头、历史、修订图、账户、对象列表时，预检与读取都放在同一个读事务里；元数据在同一条语句中先比较长度；头表的 ID 先检查长度 | `review3_h3_meta_and_head_ids_are_length_checked`。评审是用 SQLite trace 精确安排两个连接的先后来复现竞态的，仓库里没有引入这一测试依赖。修复是结构性的：两条语句处于同一快照 |
| H4 保留键的格式边界未落实 | 低 | **已确认** | 见 §3 第 2 项。合并时只把 `hlc = 0`、值为 `true` 的版本当作删除候选 | `review3_h4_reserved_purged_key_is_enforced` |
| H5 相对读超时挡不住逐字节拖延 | 低 | **已确认** | 改为按绝对截止时间读取：每次底层读取前都重新计算剩余时间。规范同时要求原生确认界面在截止时间关闭 | `review3_h5_deadline_is_absolute_across_partial_reads` |
| H6 XX 确认后 `paired` 先于登记发送 | 低 | **已确认** | 用户确认、会话建立之后，先登记，再发送 `paired` | `review3_h6_confirmed_pairing_registers_before_paired_is_sent` |
| H7 整数约束遗漏读取入口；规范编码没有覆盖墓碑 | 低 | **已确认** | 见 §3 第 3 项 | `review3_h7_overview_ints_and_write_validation` |
| H8 Q · 2⁻⁴⁸ 的统计单位与跨重启范围 | 建议 | **同意** | 规范区分两种界限：单次固定尝试为 Q_s · 2⁻⁴⁸；一段时间内的全部尝试为 Q_s · Q_e · 2⁻⁴⁸。计数只在一次服务运行内有效，并说明原因：能拦截本机 IPC 的同用户进程既能结束 Keevo，也能改写计数文件，真正的防护是每次尝试都对用户可见。扩展不得自动重试。完整的多会话证明列为未决事项 | —（规范） |

## 5. §4 中的其他事项

| 事项 | 处理 |
|---|---|
| "墓碑头并入合并修订后 `resurrected` 不再出现"一句与新机制不符 | 改为：只要被撤销的删除版本还在并发版本中，每次合并都会给出提示；写时收敛确定恢复之后才消失 |
| 两个不同的回收站时间被撤销后，仍作为字段冲突报告 | 删除状态键一律不算字段冲突（`review3_suppressed_trash_is_not_a_field_conflict`） |
| 两端显示同一个清洗后的名称 | 库函数一致已核实。扩展界面目前固定传入 "Chrome"，也没有显示名称，属于 M1.3 的界面工作 |
| `hlc.rs` 中 `restore` 的注释 | 改为与规范 §3 一致：只取物理时间不超过本机时钟 + 24 小时的修订 |
| `RevisionGraph::insert` 没有父修订数量上限 | 新增上限 65,536（`TooManyParents`）。存储层仍按修订种类执行更细的上限 |
| 首次解锁前能否配对、锁定后能否撤销、保存失败怎么办（评审 §4.4） | 配对只在解锁时进行，锁定时 XX 返回 `locked`（`review3_pairing_requires_unlocked_vault`）；配对记录保存成功才发送 `paired`，`PairingStore::save` 改为返回结果，开发用的文件存储先写盘再更新内存（`review3_pairing_save_failure_is_a_rejection`）；撤销只在解锁时进行，写盘失败的撤销作为"待提交的撤销"留在内存中，每次解锁先应用（规范，M1.3 实现） |
| §4.3 "会话不跨越锁定"与"不断开"矛盾 | 改为：传输会话可以跨越锁定保留，授权不能；锁定期间只回答 `status` |
| 处理记录对不采用 RFC 8785 的理由不准确 | **更正**：RFC 8785 只规定输出规则，并不要求先转换成通用 JSON 值。真正的理由是：本格式的模式固定，定制规则更简单，也便于让秘密只出现在会清零的缓冲区里。第二轮处理记录 §5 的那句话以此为准 |

**处理中发现的问题**（评审未报告）：
- `Vault` 的移入回收站与恢复走的是一个独立的写入函数，没有经过写时收敛的 `settle_for_write`，也没有清理历史。已改为与其他编辑一样经由 `revise`。
- 改为运行时间计时后，现有测试暴露出一个边界错误：累计运行时间不足 90 天时，截止时间饱和为 0，第一个修订（保存时间为 0）会被误清理。已修正：运行时间不足保留期时一律不清理。

## 6. 回答评审者的问题

| # | 问题 | 回答 |
|---|---|---|
| 1 | 257 个头、删除全部键仍超过 16 MiB 的状态怎么办？ | 上限提高到 4096 个头、4096 个键。在此之内精简总能成功；超出时只读，可导出或重建为新条目，旧条目随后被永久删除。M2 增加墓碑回收 |
| 2 | 90 天承诺什么？时钟元数据异常怎么办？ | 承诺不早于真实经过的 90 天：按 Keevo 的累计运行时间计。不再有时钟元数据；保存时间不合理时暂停清理 |
| 3 | `attr:purged` 是否只能由内部构造？墓碑的比较编码？已删除视图是否排除在纯合并之外？ | 都是。客户端写入返回 `reserved_key`；删除候选必须是 `hlc = 0`、值为 `true`；墓碑的规范编码是 `null`；已删除的视图不得写回 |
| 4 | "一次配对"的含义？计数是否跨重启？ | 一次配对是用户在扩展中主动发起的一次尝试，扩展不得自动重试。计数只在一次服务运行内有效；界限按单次尝试与一段时间内的全部尝试分别给出 |
| 5 | 锁定与授权记录的状态转移？ | 配对与撤销都只在解锁时进行；保存成功才发送 `paired`；写盘失败的撤销留在内存中，每次解锁先应用再重试写入 |
| 6 | §8.6 的冻结范围？ | 单独保持草案，M1.1 实现 Touch ID 时定稿。四个用途的明文布局、可访问性、各自的恢复方式，以及 `device_id` 变化时的重新包裹顺序，都已写入 |
